# RefCheck

Проверяет, что сборки, которые уезжают в каталог add-in, обращаются только к тем членам,
которые есть в копиях, реально загружаемых Revit.

## Три случая связывания, а не один

Инструмент долго исходил из одной модели: «Revit грузит свою копию первым, наша игнорируется».
Так бывает, но это только один из трёх случаев, и остальные два он либо выдумывал, либо не видел.

| Случай | Когда | Что верно |
|---|---|---|
| **Подмена** | идентичности совпадают, либо `bindingRedirect` в `Revit.exe.config` сводит нашу на ревитовскую | грузится ревитовский файл; сверка поверхностей осмысленна — это `RVTREF001..003` |
| **Раздвоение** | версии разные, ничто их не сводит — **только .NET Framework** | грузятся **обе**; наш код связан с нашей, сверка с ревитовской отвечает на вопрос, которого никто не задавал — это `RVTREF006` |
| **Висячая ссылка** | нужной идентичности нет нигде | отказ при первом обращении; **пока не проверяется**, см. ниже |

Случай 2 — не теория, а история этого репозитория: `Grpc.Core.Api` просил `System.Memory` 4.0.1.1,
`GrpcDotNetNamedPipes` — 4.0.2.0, загрузились обе, и это стоило форка библиотеки.

**Редиректы обязаны быть в модели.** Без них диагноз ошибается в обе стороны: `Newtonsoft.Json`
опасен *потому что* редирект сводит обе копии на одну идентичность, а
`System.ComponentModel.Annotations` безопасен *потому что* редирект его покрывает. Эталон теперь
хранит `redirects`, прочитанные из `Revit.exe.config`.

**Раздвоения на оси .NET не бывает.** Там одно простое имя на контекст загрузки: чей файл загрузился
первым, тот и обслуживает всех, второй не читается вовсе. Наблюдались оба исхода, и на одной версии:
ревитовский `Google.Protobuf` 3.23.1 ответил на наш запрос 3.29.3 и всё работало, а его же
`Configuration.Abstractions` 2.0.0.0 отказал нашему запросу 10.0.0.0 наотрез. В обоих случаях
в игре ровно одна сборка — значит сверять поверхности там правильно, и `RVTREF006` не выдаётся.

**Редиректы применяются только на оси .NET Framework.** На .NET их не существует вовсе: простое имя
достаётся загрузившему первым, и запрос более высокой версии не удовлетворяется низшей копией —
измерено, именно из-за этого add-in не загрузился на Revit 2026.

**Есть и четвёртый механизм, которого тул не видит и видеть не может: чужой `AssemblyResolve`.**
Revit возит `RevitAssemblyResolver`, сопоставляющий по простому имени по всем папкам add-in. В
замере он ответил на запрос `System.Memory` 4.0.2.0 файлом 4.0.1.1 из каталога **чужого плагина** —
Fusion такого не делает, под строгое имя без редиректа она файл другой версии не подставляет.
Отсюда правило чтения любых замеров: зелёный прогон доказывает «работает на этой машине с этим
набором плагинов», а не «работает».

### `RVTREF006` сообщает, но не предупреждает

Печатается обычной строкой, а не `warning`. Каждая такая находка верна и **ни одна не действие сама
по себе**: `System.Numerics.Vectors` грузится в двух копиях месяцами без вреда. Предупреждение на
каждой сборке про то, что обычно нормально, — верный способ приучить не читать журнал сборки,
а этому инструменту нужно, чтобы его читали.

Опасен только **шов между двумя нашими же сборками**: `Span<T>`, `Memory<T>`, `IBufferWriter<T>`
из разных копий — разные типы. Когда кто-то будет смотреть на `MissingMethodException` между
двумя своими сборками, этот список и есть ответ.

### Чего проверка ещё не делает

**Висячие ссылки.** Идентичность, которой нет ни у нас, ни у Revit, даёт отказ при первом
обращении — и сборкой это не видно. Проверка спроектирована, но не написана: чтобы не ошибаться,
ей нужны правила унификации OOB-сборок .NET Framework, а инструмент, который угадывает, хуже
отсутствующего. Пока это записанный пробел, а не забытый.

**Развёрнутую папку.** `RVTREF005` смотрит вывод сборки, а развёртывание только копирует и никогда
не удаляет, поэтому запрещённая сборка может пережить запретившее её правило.

## Зачем

Revit возит в каталоге установки собственные копии распространённых сборок и грузит их
раньше любого add-in. Наша копия в каталоге плагина после этого игнорируется до конца
жизни процесса: код компилируется против нашей версии, а исполняется против ревитовской.
Компилятор здесь не помощник — расхождение проявляется в рантайме как
`MissingMethodException` или `TypeLoadException` при первом обращении.

Проверено на живом процессе Revit 2025: из четырёх сборок в каталоге add-in **две
загрузились из `C:\Program Files\Autodesk\Revit 2025`** — `Grpc.Core.Api` и
`Google.Protobuf`. Наши копии не использовались.

Окно проблемы — Revit 2024 и 2025. На 2026+ спасает изоляция (`UseRevitContext=False`
плюс `ContextName` в манифесте), на 2024 её не существует.

Измеренные расхождения на момент написания:

| Сборка | У Revit | В пакете | Разница поверхности |
|---|---|---|---|
| `Grpc.Core.Api` | 2.59.0.0 | 2.67.0 | нет, 499 членов в обеих |
| `Google.Protobuf` | 3.23.1.0 | 3.29.3 | 307 добавлено, 21 удалено (в основном proto editions) |
| `Newtonsoft.Json` | 13.0.1 | 13.0.3 | нет `JsonCloneSettings`, `JToken.DeepClone(settings)`, копирующего конструктора `JsonSerializerSettings` |
| `System.Memory` | 4.0.1.1 | 4.0.1.2 | разные версии сборки, редиректа в `Revit.exe.config` нет |
| `System.Runtime.CompilerServices.Unsafe` | 4.0.4.1 | 6.0.0.0 | то же |
| `System.Collections.Immutable` | 1.2.5.0 | 8.0.0.0 | то же |

## Как подключается

Таргет импортируется в проект и работает после `Build`:

```xml
<Import Project="$(RepoRoot)build\RefCheck\RefCheck.targets" />
```

Включён по умолчанию, когда задано `RevitVersion` — то есть ровно для Revit-side TFM.
Выключить для одного проекта:

```xml
<RevitReferenceCheck>false</RevitReferenceCheck>
```

Проверяются все управляемые сборки в `$(TargetDir)`, а не только своя: конфликт может
принести и транзитивная зависимость.

## Что делать при срабатывании

| Код | Что произошло |
|---|---|
| `RVTREF001` | тип не существует в копии Revit |
| `RVTREF002` | тип есть, члена нет |
| `RVTREF003` | член есть, но с другим числом аргументов |
| `RVTREF004` | предупреждение: сборка есть у Revit, но её нет в watchlist, проверить не удалось |
| `RVTREF000` | предупреждение: для этой версии Revit нет эталона, ничего не проверено |
| `RVTREF999` | итоговая ошибка сборки |

По убыванию предпочтительности:

1. **Перестать использовать член.** Обычно есть эквивалент, который в версии Revit присутствует.
2. **Убрать зависимость из Revit-side сборки**, оставив её только на Win-side.
3. **Изолировать add-in** — только Revit 2026 и новее: `UseRevitContext=False` плюс
   `ContextName` в манифесте `.addin` дают собственный `AssemblyLoadContext`, и побеждает
   наша копия. Для 2024 и 2025 этого нет.

Отключение проверки — не решение: она описывает то, что произойдёт в рантайме,
а не искусственное ограничение.

## Эталоны

`baselines/revit-<версия>.json` — что возит каждая версия Revit. Собирается командой,
руками не правится.

`baselines/watchlist.json` — сборки, для которых хранится **полная поверхность членов**.
Для остальных пишется только идентичность (имя и версии). Так сделано из-за объёма:
индексировать всё, что лежит в каталоге Revit, — это около 5 МБ на версию, причём
основной вес дают `CefSharp`, `AWSSDK`, `System.ServiceModel` и подобные, которых
add-in никогда не повезёт. С watchlist выходит около 500 КБ на версию.

Пропуск не остаётся незамеченным: если сборка ссылается на что-то, что Revit тоже возит,
а в watchlist этого нет, выдаётся `RVTREF004` с именем сборки. Тогда — добавить имя
в watchlist, пересобрать эталоны, закоммитить.

Сборки самого Autodesk (определяются по `AssemblyCompanyAttribute`) не индексируются
никогда: мы ссылаемся на них через пакеты Revit API, которые переупаковывают эти же
файлы, поэтому расхождение версий невозможно.

Фасады .NET Framework (сборки без собственных типов, только с переадресацией)
распознаются автоматически и пропускаются: ссылка на них разрешается через переадресацию,
а не в файл из каталога Revit.

### Пересобрать эталон

Нужен установленный Revit соответствующей версии.

```powershell
dotnet build build\RefCheck\RefCheck.csproj -c Release

dotnet build\RefCheck\bin\Release\net10.0\RefCheck.dll collect `
    --revit-dir "C:\Program Files\Autodesk\Revit 2025" `
    --revit-version 2025 `
    --watchlist build\RefCheck\baselines\watchlist.json `
    --out build\RefCheck\baselines\revit-2025.json
```

Файлы отсортированы и отформатированы построчно, поэтому `git diff` показывает ровно то,
что Autodesk изменил между обновлениями. Это и есть штатный способ узнать, что поменялось.

### Добавить новую версию Revit

Собрать эталон командой выше с новой версией и закоммитить получившийся файл. Правок в
коде не требуется. Пока эталона нет, сборка выдаёт `RVTREF000` и ничего не проверяет.

## Запуск вручную

```powershell
dotnet build\RefCheck\bin\Release\net10.0\RefCheck.dll check `
    --baseline build\RefCheck\baselines\revit-2024.json `
    --input путь\к\каталогу\или\сборке
```

Код возврата: `0` — чисто, `1` — есть расхождения, `2` — ошибка запуска.

`--application <файл сборки>` (можно несколько) называет сборку, на которую указывает запись
add-in'а типа `Application`, и добавляет две проверки: `RVTRIB007` и `RVTENT004`. Сборка обязана
лежать в одном из `--input`; не нашлась — это ошибка запуска (`2`), а не пройденная проверка.
Сборка передаёт его сама, см. ниже.

## Проверки, которые не про Revit, а про нас самих

Три семейства отвечают не на вопрос «совпадает ли поверхность с ревитовской», а на вопрос «работает
ли то, что мы объявили». Живут они здесь по одной причине: и там, и там надо читать метаданные
собранной сборки, а метаданные внутри MSBuild — это `System.Reflection.Metadata` с пятью полифиллами
**внутри процесса сборки**, то есть то самое столкновение, которое в этом репозитории уже стоило
форка библиотеки. RefCheck — обычное приложение в отдельном процессе, где всё это в коробке.

**Каждая проверка печатает строку и когда проходит**, с числом того, что проверила:

```
RefCheck: 1 manifest(s), 3 button(s) checked - every class in the assembly its button names, no button name used twice, no tab in 1 Entry manifest(s).
RefCheck: 1 Entry assembly(ies) checked, 4 entry point(s), each empty and naming a feature or a rule from its own feature's declaration.
RefCheck: Application add-in BHS.FullEdition.dll has 1 ribbon manifest(s) beside it and names a module from the declaration of each of its 1 Entry manifest(s).
RefCheck: 1 declaration assembly(ies) checked, none reaches into an implementation.
```

Охраняют они то, что при поломке симптома не даёт: сборку, которая не загрузилась, кнопку, которой
просто нет. Молча пройденная проверка неотличима от переставшей выполняться — а сам RefCheck однажды
месяцами не выполнялся, пока CLAUDE.md описывал его как валящий сборку. Строка печатается только там,
где было что проверять: у проекта без манифестов строки про ленту нет.

### `RVTRIB001..007` — лента объявлена строками

Кнопка называет класс команды строкой, чтобы сборка фичи не грузилась, пока её не нажали. Цена в
том, что всякая ошибка, которую поймал бы компилятор, превращается в модальное окно перед человеком.
Каждый из первых пяти кодов — конкретное окно, виденное этим проектом вживую. Реализация —
`RibbonCheck.cs`.

| Код | Что ловит |
|---|---|
| `RVTRIB001` | класса нет в названной сборке |
| `RVTRIB002` | класс не `IExternalCommand` |
| `RVTRIB003` | нет `[Transaction]` на типе, который конструирует Revit |
| `RVTRIB004` | класс доступности лежит в другой сборке — `TypeLoadException` при показе вкладки |
| `RVTRIB005` | класс доступности не `IExternalCommandAvailability` |
| `RVTRIB006` | две кнопки с одним именем среди **всех** манифестов каталога |
| `RVTRIB007` | рядом с add-in'ом типа `Application` лежит `<P>.Entry.dll` без своего `<P>.Entry.features.json`, или нет ни одного `*.features.json` вовсе |

Последние два появились, когда кнопки фичи переехали из издания в её Entry-сборку и стали приезжать
в каталог издания связанным файлом. Окна за ними никто не видел, и названо это прямо.

**`RVTRIB006`** — межпроектный двойник `RVTRIB011` из SDK: тот видит item'ы одного проекта и не видит,
как в каталоге издания встретились два. `RevitAPIUI.xml` для 2024 и 2027 документирует, что
`RibbonPanel.AddItem` бросает `ArgumentException`, если на панели уже есть элемент с таким именем, а
хост бросок логирует и идёт дальше — то есть на общей панели вторая кнопка просто пропадает. **В Revit
не измерено.** Попадут ли две кнопки на одну панель, проверка не спрашивает: имя, уникальное по
случайности раскладки, перестаёт быть уникальным в день, когда фича переносит кнопку.

**`RVTRIB007`** ловит поток, отказавший молча. Манифест фичи попадает в каталог издания через
`AllowedReferenceRelatedFileExtensions` в корневом `Directory.Build.targets`, и если копирование
перестало происходить, не падает ничего: add-in грузится, стартует и не показывает ни одной кнопки
этой фичи, а в логе о ней ни строки — пропускать хосту нечего, манифеста нет.

**Спрашивается про каждую Entry-сборку, а не про число манифестов, и это поправка.** Первая версия
проверяла только, что в каталоге есть хоть один `*.features.json`, — и проба, у которой манифест свой
есть всегда, прошла с удалённым Entry-манифестом: воспроизведено на копии её вывода, RefCheck вернул `0`
и напечатал «no Entry manifest to match against Modules». Теперь для каждого `<P>.Entry.dll` рядом с
`Application` обязан лежать `<P>.Entry.features.json`; ветка «ни одного манифеста вовсе» осталась.

Проверено красным: сборка издания с `-p:AllowedReferenceRelatedFileExtensions=.pdb` — прежняя копия
манифеста исчезла из вывода сама, по инкрементальной чистке, и сборка упала с `RVTRIB007`. Правило
описывает add-in'ы, какие есть сегодня — у каждого `Application` в репозитории есть кнопки; издание
без кнопок, если оно понадобится, — повод пересмотреть правило по имени, а не выключатель.

`RVTRIB006` тоже показан красным: кнопка Entry-сборки пробы переименована в `BHS.Probe.Ping`, как
кнопка самой пробы. Сборка Entry-проекта прошла — в его каталоге манифест один, и `RVTRIB011` из SDK
промолчал, — а сборка пробы, куда оба манифеста приехали, упала с `RVTRIB006`.

### `RVTDEC001..002` — объявление фичи не тянет её реализацию

Сборка-объявление (`*.Declaration`) несёт то, что приложение обязано знать о фиче **до** первого
нажатия: идентификаторы регистраций, которые Revit разрешает делать только на старте. Поэтому она
грузится в `OnStartup` у каждого пользователя каждого издания — и поэтому обязана быть пустой от
всего остального: одна ссылка на сборку реализации молча отменяет ленивость, ради которой лента и
объявлена строками. На Revit 2024 загруженная сборка вдобавок держит своё простое имя в общем
AppDomain до конца сессии.

| Код | Что ловит |
|---|---|
| `RVTDEC001` | объявление ссылается на сборку `BHS.*` вне разрешённого списка |
| `RVTDEC002` | объявление ссылается на `RevitAPIUI` — значит перестало годиться DB-форме |

Разрешённый список лежит **в коде**, в `DeclarationCheck.cs`: расширять его — решение с именем на
нём, а не свойство, которое выставят в спешке и не снимут никогда. Проверка печатает строку и когда
проходит, потому что охраняет она **отсутствие** — сборку, которая не загрузилась, — а молча
пройденная проверка неотличима от переставшей выполняться.

**Оговорка, которую надо знать:** ловится **употребление**, а не строка в `.csproj`. Компилятор не
пишет в метаданные ссылку, которой никто не воспользовался, поэтому `ProjectReference` без единого
типа проверка не увидит. Это и правильно — незадействованная ссылка ничего не загружает, — но
демонстрировать проверку красной надо ссылкой **вместе** с `typeof`.

### `RVTENT001..004` — Entry-сборка фичи несёт имена и ничего больше

Revit разрешает `ClassName` и `AvailabilityClassName` кнопки внутри **одной** сборки, которую
кнопка называет, — прочитано в IL всех четырёх версий и измерено окном `TypeLoadException`. Поэтому
точки входа команд и классы доступности фичи лежат вместе, в `<P>.Entry`, а издание на неё ссылается.
Работа — в фиче, правило — в объявлении, поиск хоста — в дженерик-базе в `BHS.Revit.Abstractions`.
Классы Entry-сборки — это имена, которые Revit может разрешить, и больше ничего. Реализация —
`EntryCheck.cs`, кроме `RVTENT003`, который читает JSON и живёт в `RibbonCheck.cs`.

| Код | Что ловит |
|---|---|
| `RVTENT001` | в `*.Entry` есть что-то кроме пустых `public sealed` классов, наследующих **напрямую** `CommandEntryPoint<TFeature, TCommand>` или `AvailabilityEntryPoint<TRule>` |
| `RVTENT002` | в `<P>.Entry` правило доступности не из `<P>.Declaration` и не из `BHS.Revit.Abstractions`; фича команды не из `<P>.Declaration` или не `IFeatureModule`; тип, вложенный в аргумент любой из баз, из сборки каталога, которую не грузит старт |
| `RVTENT003` | кнопка в `*.Entry.features.json` называет вкладку |
| `RVTENT004` | рядом с `Application` add-in'ом лежит `<P>.Entry.features.json`, а сборка add-in'а не называет ни одного `IFeatureModule` из `<P>.Declaration` |

**Почему проверка, а не правило в документе.** Всё, от чего она охраняет, — законный C#: метод на
точке входа компилируется, поле компилируется, правило, написанное в сборке фичи, компилируется —
Entry-проект ссылается на фичу. А ломает каждое то, что видно только запуском: Entry-сборку Revit
грузит, как только показана вкладка с её кнопками, чтобы сконструировать класс доступности, — значит
всё, что она называет, грузится тогда же; а экземпляр класса доступности Revit держит **один** на путь
сборки и имя класса всю сессию (IL всех четырёх версий) — значит поле на нём протухает.

**Что считается «пустым» в `RVTENT001`.** Ни полей, ни свойств, ни событий, ни вложенных типов, ни
интерфейсов, ни методов, ни статического конструктора; только публичный конструктор без параметров, **и его тело
тоже проверяется**: «конструктор без параметров» — ровно то место, куда положили бы логику, которую
запрещено держать в методе. Тело, которое компилятор пишет пустому классу, вызывает конструктор базы
и возвращается: `02 28 tok 2A` в Release и `02 28 tok 00 2A` в Debug (один `nop`) — оба прочитаны с
Entry-сборки пробы, без локальных переменных и без областей исключений; токен обязан называть
конструктор самой базы. Публичный — потому что такой компилятор даёт пустому публичному классу;
как Revit конструирует класс по имени и сработал бы непубличный конструктор, **не измерено**, и
проверка от этого не зависит.

**Исключения — по точному признаку, а не «всё непубличное».** В сборке `net48-revit2024` обеих
Entry-сборок компилятор вписывает `Microsoft.CodeAnalysis.EmbeddedAttribute`, `NullableAttribute` и
`RefSafetyRulesAttribute`; в сборках оси .NET их нет. Каждый непубличный, верхнего уровня и несёт
**оба** атрибута — `[CompilerGenerated]` и `[Embedded]`. Пропускаются только такие и строка `<Module>`
(первая строка таблицы типов). Проверено красным: написанный руками `internal sealed class` в
Entry-сборке на `net48` даёт `RVTENT001`.

**Интерфейс на классе — тоже не пусто.** Членов и логики у него нет, а грузит он всё равно: при
конструировании класса разрешаются все объявленные им интерфейсы, и интерфейс из сборки фичи тянет её
при показе вкладки. Воспроизведено на одноразовой Entry-сборке, где такой класс проходил все прочие
части проверки. Ложных срабатываний нет: C# не повторяет интерфейсы базы на наследнике, и у обеих
Entry-сборок дерева строк `InterfaceImpl` ноль.

**`RVTENT002` — объявление своей фичи, а не любое, и аргументы на любой глубине.** Ожидаемая сборка
выводится из имени Entry-сборки: `<P>.Entry` → `<P>.Declaration`, потому что именно эту пару сверяет
хост. Первая версия принимала всякую сборку на `.Declaration`, и команда, назвавшая модуль **чужой**
фичи, проходила и здесь, и `RVTENT004`, кнопка строилась — а на нажатии команда отвечала «издание не
объявляет фичу», потому что издание перечисляло другую. Выведено из кода, не собрано. И вложенные
аргументы: загрузка класса загружает инстанс базы со **всеми** типами аргументов, так что
`AvailabilityEntryPoint<DocRule<T>>` с `T` из фичи тянет фичу при показе вкладки, а верхнеуровневый
вопрос это пропускал. Вложенный аргумент помечается, только если его сборка лежит в проверяемом
каталоге — это и отсекает типы фреймворка, которые туда не копируются, — и может быть из
`<P>.Declaration` или из того, что объявлению разрешено называть самому (`RVTDEC001`): и то и другое
грузит старт.

**Вложенный тип перестал давать ложное срабатывание.** `TypeFacts.Find` сравнивал пространство имён и
имя, а у вложенного определения своя строка пространства имён пуста, и декодер пишет его как
`NS.Outer+Inner` — так законный модуль, вложенный в статический класс объявления, получал `RVTENT002`
«не `IFeatureModule`» и `RVTENT004`. Теперь сравнивается полное вложенное имя; для типа верхнего уровня
написание прежнее. Обход цепочки баз через вложенную **базу** по-прежнему не поддержан — таких в дереве
нет.

Все три правки показаны красными, по одной поломке на проверку, с восстановлением и сверкой хешей
(ломались неотслеживаемые файлы пробы, `git diff` их не видит): интерфейс
`IExternalCommandAvailability`, повторно объявленный на `GateAvailability` (`RVTENT001`); команда пробы
на `CablingFeature` из `BHS.MEP.Cabling.Declaration` (`RVTENT002`, «declared in
'BHS.Revit.Probe.Declaration'»); `GateCommand` из фичи внутри аргумента обобщённого правила
(`RVTENT002`). `RVTRIB007` по Entry-сборке — сборкой пробы с `-p:AllowedReferenceRelatedFileExtensions=.pdb`:
свой манифест пробы остался, Entry-манифест исчез, и сборка упала, тогда как прежнее правило здесь
молчало. Ложное срабатывание на вложенном модуле показано зелёным на одноразовом наборе проектов.

**`RVTENT003` — вкладку выбирает издание, панель — фича.** Хост кладёт кнопку Entry-манифеста на
вкладку издания, что бы ни было написано в манифесте, и пишет предупреждение в лог. `<Tab>` в
Entry-проекте поэтому говорит неправду о том, куда кнопка попадёт.

**`RVTENT004` — статическая замена «перечислено в `Modules`», и заведомо слабее.** Хост строит кнопки
`<P>.Entry.features.json` только если в `Modules` издания есть модуль из `<P>.Declaration`, иначе
пропускает манифест с ошибкой в логе. Метаданные могут показать только то, что сборка add-in'а
**где-то** называет такой тип: список `Modules` называет (`new CablingFeature()` — это ссылка), но
назовёт и тип, упомянутый по любой другой причине. Значит «прошла» — это «могла быть перечислена», и
решает проверка хоста при старте; «не прошла» — «перечислена быть не может». Сборка передаёт
`--application` только для проектов с записью `RevitAddIn` типа `Application` (пустой `AddInType` —
тоже `Application`, как у `GenerateRevitAddIn`); проба объявляет и `Application`, и `DBApplication` в
одной сборке и попадает в список по первой.

**Все четыре показаны красными до того, как им поверили**, по одной поломке на проверку и с
восстановлением файла побайтно: метод на классе доступности (на `net8.0-revit2026` и на
`net48-revit2024`); правило и фича из `BHS.Revit.Probe.Feature` в аргументах баз (обе ветки
`RVTENT002` одной поломкой); `<Tab>` на кнопке кабельной Entry-сборки; `new CablingFeature()`,
убранный из `Modules` издания. Ветка «фича из объявления, но не `IFeatureModule`» красной не
показана: ограничение дженерика не даёт такому коду скомпилироваться.

**Оговорка про `RVTENT004`, найденная первым же прогоном цели.** Батчинг по пустому списку item'ов
всё равно выполняет элемент один раз с пустыми метаданными, и Entry-проект, у которого нет ни одной
записи add-in'а, получил собственную сборку как `--application`. Группа item'ов в `RefCheck.targets`
теперь под условием `'@(RevitAddIn)' != ''`.

## Границы применимости

Сравнение идёт **по имени и арности**, не по полным сигнатурам. Ловит удалённые и
переименованные члены и отсутствующие перегрузки; не поймает смену типа параметра при
сохранении их числа. Для protobuf и gRPC, где бинарная совместимость внутри мажорной
версии — заявленная цель, этого достаточно. Если понадобится больше, сравнение сигнатур
добавляется в `AssemblyIndex`.

Проверяется только то, что лежит в каталоге сборки. Загруженные из GAC или подтянутые
через `AssemblyResolve` сборки вне поля зрения.

## Устройство

| Файл | Назначение |
|---|---|
| `Program.cs` | разбор аргументов, команды `collect` и `check`, тексты сообщений |
| `AssemblyIndex.cs` | чтение метаданных: что сборка объявляет и что запрашивает у других |
| `Baseline.cs` | модель эталона и watchlist, сбор и сериализация |
| `ParameterCounter.cs` | декодер сигнатур, считающий только число параметров |
| `TypeFacts.cs` | вопросы о типах собранной сборки без загрузки: база, интерфейсы через соседние сборки, аргументы дженериков |
| `RibbonCheck.cs` | манифесты ленты против метаданных сборки и друг против друга: `RVTRIB001..007`, `RVTENT003` |
| `DeclarationCheck.cs` | объявление фичи не ссылается на реализацию: `RVTDEC001..002` |
| `EntryCheck.cs` | Entry-сборка несёт только пустые точки входа на объявленные фичу и правило; издание объявило фичу своего Entry-манифеста: `RVTENT001`, `RVTENT002`, `RVTENT004` |
| `RefCheck.targets` | интеграция в сборку |

Инструмент собирается под `net10.0` и **не имеет ни одного `PackageReference`** — читает
метаданные через `System.Reflection.Metadata` из состава фреймворка. От версий Revit и от
`BimHouse.Revit.Sdk` не зависит, поэтому собирается всегда.
