# RefCheck

Проверяет, что сборки, которые уезжают в каталог add-in, обращаются только к тем членам,
которые есть в копиях, реально загружаемых Revit.

## Три случая связывания, а не один

Инструмент долго исходил из одной модели: «Revit грузит свою копию первым, наша игнорируется».
Так бывает, но это только один из трёх случаев, и остальные два он либо выдумывал, либо не видел.

| Случай | Когда | Что верно |
|---|---|---|
| **Подмена** | идентичности совпадают, либо `bindingRedirect` в `Revit.exe.config` сводит нашу на ревитовскую | грузится ревитовский файл; сверка поверхностей осмысленна — это `RVTREF001..003` |
| **Раздвоение** | версии разные, ничто их не сводит | грузятся **обе**; наш код связан с нашей, сверка с ревитовской отвечает на вопрос, которого никто не задавал — это `RVTREF006` |
| **Висячая ссылка** | нужной идентичности нет нигде | отказ при первом обращении; **пока не проверяется**, см. ниже |

Случай 2 — не теория, а история этого репозитория: `Grpc.Core.Api` просил `System.Memory` 4.0.1.1,
`GrpcDotNetNamedPipes` — 4.0.2.0, загрузились обе, и это стоило форка библиотеки.

**Редиректы обязаны быть в модели.** Без них диагноз ошибается в обе стороны: `Newtonsoft.Json`
опасен *потому что* редирект сводит обе копии на одну идентичность, а
`System.ComponentModel.Annotations` безопасен *потому что* редирект его покрывает. Эталон теперь
хранит `redirects`, прочитанные из `Revit.exe.config`.

**Редиректы применяются только на оси .NET Framework.** На .NET их не существует вовсе: простое имя
достаётся загрузившему первым, и запрос более высокой версии не удовлетворяется низшей копией —
измерено, именно из-за этого add-in не загрузился на Revit 2026. На .NET Framework, наоборот,
удовлетворяется: замер показал `bind 4.0.2.0 -> 4.0.1.1`, причём файлом из папки чужого плагина.

### `RVTREF006` сообщает, но не предупреждает

Печатается обычной строкой, а не `warning`. Каждая такая находка верна и **ни одна не действие сама
по себе**: `System.Numerics.Vectors` грузится в двух копиях месяцами без вреда. Предупреждение на
каждой сборке про то, что обычно нормально, — верный способ приучить не читать журнал сборки,
а этому инструменту нужно, чтобы его читали.

Опасен только **шов между двумя нашими же сборками**: `Span<T>`, `Memory<T>`, `IBufferWriter<T>`
из разных копий — разные типы. Когда кто-то будет смотреть на `MissingMethodException` между
двумя своими сборками, этот список и есть ответ.

### Чего проверка ещё не делает

**Висячие ссылки.** Идентичность, которой нет ни у нас, ни у Revit, даёт отказ при первом
обращении — и сборкой это не видно. Проверка спроектирована, но не написана: чтобы не ошибаться,
ей нужны правила унификации OOB-сборок .NET Framework, а инструмент, который угадывает, хуже
отсутствующего. Пока это записанный пробел, а не забытый.

**Развёрнутую папку.** `RVTREF005` смотрит вывод сборки, а развёртывание только копирует и никогда
не удаляет, поэтому запрещённая сборка может пережить запретившее её правило.

## Зачем

Revit возит в каталоге установки собственные копии распространённых сборок и грузит их
раньше любого add-in. Наша копия в каталоге плагина после этого игнорируется до конца
жизни процесса: код компилируется против нашей версии, а исполняется против ревитовской.
Компилятор здесь не помощник — расхождение проявляется в рантайме как
`MissingMethodException` или `TypeLoadException` при первом обращении.

Проверено на живом процессе Revit 2025: из четырёх сборок в каталоге add-in **две
загрузились из `C:\Program Files\Autodesk\Revit 2025`** — `Grpc.Core.Api` и
`Google.Protobuf`. Наши копии не использовались.

Окно проблемы — Revit 2024 и 2025. На 2026+ спасает изоляция (`UseRevitContext=False`
плюс `ContextName` в манифесте), на 2024 её не существует.

Измеренные расхождения на момент написания:

| Сборка | У Revit | В пакете | Разница поверхности |
|---|---|---|---|
| `Grpc.Core.Api` | 2.59.0.0 | 2.67.0 | нет, 499 членов в обеих |
| `Google.Protobuf` | 3.23.1.0 | 3.29.3 | 307 добавлено, 21 удалено (в основном proto editions) |
| `Newtonsoft.Json` | 13.0.1 | 13.0.3 | нет `JsonCloneSettings`, `JToken.DeepClone(settings)`, копирующего конструктора `JsonSerializerSettings` |
| `System.Memory` | 4.0.1.1 | 4.0.1.2 | разные версии сборки, редиректа в `Revit.exe.config` нет |
| `System.Runtime.CompilerServices.Unsafe` | 4.0.4.1 | 6.0.0.0 | то же |
| `System.Collections.Immutable` | 1.2.5.0 | 8.0.0.0 | то же |

## Как подключается

Таргет импортируется в проект и работает после `Build`:

```xml
<Import Project="$(RepoRoot)build\RefCheck\RefCheck.targets" />
```

Включён по умолчанию, когда задано `RevitVersion` — то есть ровно для Revit-side TFM.
Выключить для одного проекта:

```xml
<RevitReferenceCheck>false</RevitReferenceCheck>
```

Проверяются все управляемые сборки в `$(TargetDir)`, а не только своя: конфликт может
принести и транзитивная зависимость.

## Что делать при срабатывании

| Код | Что произошло |
|---|---|
| `RVTREF001` | тип не существует в копии Revit |
| `RVTREF002` | тип есть, члена нет |
| `RVTREF003` | член есть, но с другим числом аргументов |
| `RVTREF004` | предупреждение: сборка есть у Revit, но её нет в watchlist, проверить не удалось |
| `RVTREF000` | предупреждение: для этой версии Revit нет эталона, ничего не проверено |
| `RVTREF999` | итоговая ошибка сборки |

По убыванию предпочтительности:

1. **Перестать использовать член.** Обычно есть эквивалент, который в версии Revit присутствует.
2. **Убрать зависимость из Revit-side сборки**, оставив её только на Win-side.
3. **Изолировать add-in** — только Revit 2026 и новее: `UseRevitContext=False` плюс
   `ContextName` в манифесте `.addin` дают собственный `AssemblyLoadContext`, и побеждает
   наша копия. Для 2024 и 2025 этого нет.

Отключение проверки — не решение: она описывает то, что произойдёт в рантайме,
а не искусственное ограничение.

## Эталоны

`baselines/revit-<версия>.json` — что возит каждая версия Revit. Собирается командой,
руками не правится.

`baselines/watchlist.json` — сборки, для которых хранится **полная поверхность членов**.
Для остальных пишется только идентичность (имя и версии). Так сделано из-за объёма:
индексировать всё, что лежит в каталоге Revit, — это около 5 МБ на версию, причём
основной вес дают `CefSharp`, `AWSSDK`, `System.ServiceModel` и подобные, которых
add-in никогда не повезёт. С watchlist выходит около 500 КБ на версию.

Пропуск не остаётся незамеченным: если сборка ссылается на что-то, что Revit тоже возит,
а в watchlist этого нет, выдаётся `RVTREF004` с именем сборки. Тогда — добавить имя
в watchlist, пересобрать эталоны, закоммитить.

Сборки самого Autodesk (определяются по `AssemblyCompanyAttribute`) не индексируются
никогда: мы ссылаемся на них через пакеты Revit API, которые переупаковывают эти же
файлы, поэтому расхождение версий невозможно.

Фасады .NET Framework (сборки без собственных типов, только с переадресацией)
распознаются автоматически и пропускаются: ссылка на них разрешается через переадресацию,
а не в файл из каталога Revit.

### Пересобрать эталон

Нужен установленный Revit соответствующей версии.

```powershell
dotnet build build\RefCheck\RefCheck.csproj -c Release

dotnet build\RefCheck\bin\Release\net10.0\RefCheck.dll collect `
    --revit-dir "C:\Program Files\Autodesk\Revit 2025" `
    --revit-version 2025 `
    --watchlist build\RefCheck\baselines\watchlist.json `
    --out build\RefCheck\baselines\revit-2025.json
```

Файлы отсортированы и отформатированы построчно, поэтому `git diff` показывает ровно то,
что Autodesk изменил между обновлениями. Это и есть штатный способ узнать, что поменялось.

### Добавить новую версию Revit

Собрать эталон командой выше с новой версией и закоммитить получившийся файл. Правок в
коде не требуется. Пока эталона нет, сборка выдаёт `RVTREF000` и ничего не проверяет.

## Запуск вручную

```powershell
dotnet build\RefCheck\bin\Release\net10.0\RefCheck.dll check `
    --baseline build\RefCheck\baselines\revit-2024.json `
    --input путь\к\каталогу\или\сборке
```

Код возврата: `0` — чисто, `1` — есть расхождения, `2` — ошибка запуска.

## Границы применимости

Сравнение идёт **по имени и арности**, не по полным сигнатурам. Ловит удалённые и
переименованные члены и отсутствующие перегрузки; не поймает смену типа параметра при
сохранении их числа. Для protobuf и gRPC, где бинарная совместимость внутри мажорной
версии — заявленная цель, этого достаточно. Если понадобится больше, сравнение сигнатур
добавляется в `AssemblyIndex`.

Проверяется только то, что лежит в каталоге сборки. Загруженные из GAC или подтянутые
через `AssemblyResolve` сборки вне поля зрения.

## Устройство

| Файл | Назначение |
|---|---|
| `Program.cs` | разбор аргументов, команды `collect` и `check`, тексты сообщений |
| `AssemblyIndex.cs` | чтение метаданных: что сборка объявляет и что запрашивает у других |
| `Baseline.cs` | модель эталона и watchlist, сбор и сериализация |
| `ParameterCounter.cs` | декодер сигнатур, считающий только число параметров |
| `RefCheck.targets` | интеграция в сборку |

Инструмент собирается под `net10.0` и **не имеет ни одного `PackageReference`** — читает
метаданные через `System.Reflection.Metadata` из состава фреймворка. От версий Revit и от
`BimHouse.Revit.Sdk` не зависит, поэтому собирается всегда.
