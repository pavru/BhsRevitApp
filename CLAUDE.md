## Статус репозитория

Набор плагинов (add-ins) для Autodesk Revit **плюс** собственный framework для них.
Каркас заложен и собирается; прикладного кода пока нет.

Directory.Packages.props      CPM; Revit-пакеты сюда НЕ вносятся, их даёт SDK
NuGet.config                  <clear/> + репозиторный фид + nuget.org
build/
  BHS.Revit.Sdk/              наш MSBuild SDK, форк BimHouse.Revit.Sdk
  RefCheck/                   проверка конфликтов сборок с самим Revit

  Shared/BHS.Shared           чистая ось .NET

  Revit/BHS.Revit.Common

**Порядок сборки двухэтапный.** MSBuild разрешает SDK-пакет до того, как хоть один проект
начнёт восстанавливаться, поэтому сначала собирается `build/BHS.Revit.Sdk` (кладёт пакет
в `artifacts/feed`), и только потом всё остальное. Обойти это нельзя.

**При правке SDK поднимайте его версию.** Пакет везёт сборку задач MSBuild, и любой процесс,
успевший оценить Revit-проект, держит `BHS.Revit.Sdk.dll` открытой — распакованная копия
в кэше не перезаписывается, а `dotnet build-server shutdown` узлы MSBuild не убивает.
Симптом старой копии — `Could not resolve SDK` или поведение, которого нет в текущих
исходниках SDK. Ссылки на версию правятся
в `build/BHS.Revit.Sdk/BHS.Revit.Sdk.csproj` и в шапках проектов `source/Revit/*`.

Разделы ниже описывают частью действующее устройство, частью — целевую модель. Актуализируйте
этот файл по мере появления кода: расхождение документа с деревом дороже, чем его отсутствие.

## Сборочная модель

Revit-side проекты собираются нашим **`BHS.Revit.Sdk`** из `build/`, а не ручными
`Directory.Build.props`-хаками, как в `BimHouseApp`/`BHS`. SDK подключается в заголовке
проекта и берётся из репозиторного фида `artifacts/feed`:

```xml
<Project Sdk="BHS.Revit.Sdk/1.5.2">
  <PropertyGroup>
    <TargetFrameworks>net48-revit2024;net8.0-revit2025;net8.0-revit2026;net10.0-revit2027</TargetFrameworks>
  </PropertyGroup>
</Project>
```

Что SDK делает за вас (детали — в `build/BHS.Revit.Sdk/readme.md`):

- **Кастомные TFM** `net48-revit2024`, `net8.0-revit2025`, `net8.0-revit2026`, `net10.0-revit2027`.
  Несоответствие версии .NET и Revit — ошибка сборки, а не тихая деградация. Моникёр **остаётся
  настоящим** `TargetFramework`: под ним идёт компиляция, под ним NuGet заводит проект, им же
  назван каталог вывода. SDK лишь доопределяет то, что базовый SDK иначе выводил бы из моникёра
  сам — идентификатор и версию фреймворка, профиль или платформу, `AssetTargetFallback`.
  Диспетчеризации нет: всё остальное делает базовый SDK, поэтому IDE видит обычный
  мультитаргет-проект.
- **Central Package Management поддержан**: под CPM неявные пакеты объявляются парой
  «`PackageReference` без версии + `PackageVersion`». Перечислять `Nice3point.Revit.Api.*`
  в `Directory.Packages.props` **нельзя** — это второй `PackageVersion` на тот же id (NU1506).
- **Ссылки между проектами** работают по обеим осям: Revit-проект → Revit-проект берёт
  соответствующую версию зависимости, Revit-проект → проект чистой оси берёт ближайший TFM
  (`net48` для 2024, `net8.0` для 2025–2026, `net10.0` для 2027). Зависимость чистой оси
  восстанавливается **один раз, на своих условиях**.
- **`LangVersion`** на Revit-TFM поверх .NET Framework подставляется как `latest`, иначе
  умолчание компилятора 7.3 конфликтует с `Nullable=enable`. Значение проекта выигрывает.
  Открывается только синтаксис: записи, `init`, индексы и диапазоны на `net48` требуют полифилла.
- **Константы препроцессора** `REVIT`, `REVIT2026`, `REVIT2025_OR_GREATER` и т.д. генерируются
  автоматически задачей `GenerateRevitDefineConstants`. Условная компиляция под версии Revit
  делается через них.
- **Пакеты Revit API** (`Nice3point.Revit.Api.*`) подключаются неявно по свойствам
  `UseRevitApi` (по умолчанию `true`), `UseRevitApiUi`, `UseRevitAdWindows`, `UseRevitApiIfc`,
  `UseRevitUiFramework`, `UseRevitAddInUtility`, `UserRevitTUnit`. Версии выравниваются по TFM —
  **не** прописывайте их вручную.
- **WPF/WinForms** работают через `UseWPF`/`UseWindowsForms`, включая компиляцию XAML. На
  `net48-revit2024` вопрос не возникает — WPF и WinForms там в коробке; на оси .NET SDK включает
  `ImportWindowsDesktopTargets` тем проектам, которые их запросили, и снимает проверку базового
  SDK «платформа обязана быть Windows» (у нас платформа — `revit`).
- **Зависимости кладутся рядом с add-in**: `CopyLocalLockFileAssemblies` включается на всех
  Revit-TFM. Библиотека на оси .NET по умолчанию не копирует пакетные сборки в вывод — их
  перечисляет `deps.json`, который ничего не значит для хоста, не являющегося .NET-приложением.
  Измерено: первая проба, развёрнутая в Revit 2026, везла только себя и `BHS.Transport` и не
  загрузилась вовсе. Reference-only пакеты Revit API внутрь не попадают — они исключены из
  runtime-ассетов.
- **Манифест `.addin`** генерируется задачей `GenerateRevitAddIn` из item-группы `RevitAddIn`
  (`FullClassName`, `AddInId`, `VendorId`, для 2025+ — `AllowLoadIntoExistingSession`, для 2026+ —
  `UnifyInAddInManager`, `UseRevitContext`, `ContextName`).
- **Публикация и деплой**: `PublishRevitAddIn=true` включает упаковку. Наличие `RevitVersion`
  переключает режим: version-specific пакет (с `.addin`) против common-пакета
  (`RevitVendorId`/`RevitPackageName`, без `.addin`). `RevitDeploy` = `Local` (`%AppData%`)
  или `System` (`%ProgramData%`/`%ProgramFiles%`).

### Обязательные глобальные настройки

- `global.json` — пин .NET SDK. Для TFM `net10.0-revit2027` нужна версия 10.x
  (на машине установлена 10.0.400); см. образец в `..\BimHouseApp\global.json`.
- **Только x64**: `<Platform>x64</Platform>`, `<PlatformTarget>x64</PlatformTarget>`,
  `<RuntimeIdentifier>win-x64</RuntimeIdentifier>`. Revit других разрядностей не бывает.
- **Central Package Management**: `Directory.Packages.props` с
  `ManagePackageVersionsCentrally=true` и `CentralPackageVersionOverrideEnabled=false` —
  версии пакетов правятся только централизованно.
- Формат решения — **`.slnx`** (как в `BimHouseApp`/`BHS`), с виртуальными папками по слоям.
- `Configurations` = `Debug;Release`, `LangVersion=latest`, `Nullable=enable`, `ImplicitUsings=true`.

## Правила проекта

- **Язык кода — английский.** Имена файлов, типов, членов, переменных, веток и коммитов — только на английском.
  Русский допустим в пользовательских строках (через ресурсы) и в документации для владельца проекта.
- **Стек** — .NET + C#. Решение по UI принято:
  - **Revit-side (в процессе Revit) — WPF, пакет `WPF-UI`, закреплённый на 4.0.3.** Единая линия от
    Revit 2024 до последней версии, один и тот же набор на всех четырёх TFM.

    **Набор урезан против исходного, и каждое исключение измерено:**

    | Пакет | Решение | Почему |
    |---|---|---|
    | `WPF-UI` **4.0.3** | берём, версия закреплена | с 4.1.0 ветка `net4x` требует `System.Memory` 4.6.3 = `AssemblyVersion` 4.0.5.0, а Revit 2024 везёт 4.0.1.1 — ту самую, ради которой форкнут `BHS.Grpc.NamedPipes`. На 4.1.0 полифиллов становится 7 вместо 4; на 4.0.3 все четыре **совпадают с ревитовскими точно** |
    | `Microsoft.Xaml.Behaviors.Wpf` | берём | Revit 2025–2027 возят свою с той же `AssemblyVersion` 1.1.0.0; имя добавлено в watchlist, расхождений на используемой поверхности нет |
    | `Lepo.i18n.Wpf` | берём | на `net48` привозит только себя и `Lepo.i18n` — ни полифиллов, ни `Microsoft.Extensions.*` |
    | `WPF-UI.DependencyInjection` | **нет** | тянет `Microsoft.Extensions.*` на всех четырёх TFM — под полным запретом, `RVTREF005` |
    | `CommunityToolkit.Mvvm` | **нет** | на 2024 даёт висячие ссылки (`System.Memory` 4.0.2.0, `System.Buffers` 4.0.2.0, `Unsafe` 6.0.0.0). Работало только потому, что `RevitAssemblyResolver` подставлял копию из папки чужого плагина |
    | `WPF-UI.Tray` | **нет** | покупает трей, которого в Revit не бывает |
    | `SharpVectors.Wpf` | **нет** | не нужен, и **никогда не восстанавливался**: прежняя запись «набор проверен сборкой» покрывала пять пакетов из шести |

    Проверено: RefCheck чист на всех четырёх версиях, живой Revit 2024 грузит `Wpf.Ui` 4.0.0.0 из
    нашей папки, прогон зелёный.

    > **Условие снятия пина, а не запрет:** когда Revit 2024 выйдет из поддержки или апстрим уберёт
    > зависимость. Запрет без срока — тот, который через год никто не решается тронуть.

    > **`AssemblyVersion` у `Wpf.Ui` заморожена по мажору-минору** (4.0.3 → `4.0.0.0`), а на этой
    > машине его не везёт ни Revit, ни один плагин — мы первые. Значит чужой плагин с любой 4.0.x
    > получит нашу идентичность, и на 2024/2025 победит загрузившийся первым. Имя внесено в watchlist
    > заранее; проверку стоит повторять — состав машины уже менялся между замерами.

    Заметьте: `WPF-UI` не публикует `net48` — на 2024 подтягивается `net472`.
  - **Win-side (нативные вспомогательные приложения, отдельный процесс) — `net10.0-windows` + WinUI 3.**
    Не мультитаргетится по Revit и не привязан к диапазону поддержки Revit.
  - WinUI 3 **не применяется** в Revit-side сборках, пока в поддержке остаётся Revit 2024 — см. ограничение ниже.
- **Диапазон поддержки Revit — с 2024 до последней версии**, с добавлением новых по мере выхода.
  Отказ от старой версии — отдельное осознанное решение, а не побочный эффект правки TFM.

### Матрица версий Revit → .NET

Соответствие фиксировано Autodesk, свободного произведения двух осей не существует.
Проверено по `ref/`-папкам пакетов `Nice3point.Revit.Api.RevitAPI` в кэше NuGet:

| Revit | Рантайм | TFM проекта | Год едет в | Ссылки берутся из | Версия пакета API |
|---|---|---|---|---|---|
| 2024 | .NET Framework 4.8 | `net48-revit2024` | никуда — см. ниже | `net48` | 2024.3.60 |
| 2025 | .NET 8 | `net8.0-revit2025` | платформе `revit` 2025.0 | `net8.0-windows7.0` | 2025.4.60 |
| 2026 | .NET 8 | `net8.0-revit2026` | платформе `revit` 2026.0 | `net8.0-windows7.0` | 2026.4.10 |
| 2027 | .NET 10 | `net10.0-revit2027` | платформе `revit` 2027.0 | `net10.0-windows7.0` | 2027.2.0 |

Пятая колонка — не во что превращается моникёр, а откуда `AssetTargetFallback` берёт содержимое
пакетов: под сам Revit-моникёр никто ничего не публикует.

Четвёртая колонка — та, где легко ошибиться, причём в обе стороны; это стоило двух заходов.

**На оси .NET год обязан входить в личность фреймворка**, а не только в его имя: именно по личности
IDE строит модель проекта. Пока эта ось объявляла платформу `windows`, 2025 и 2026 давали одну и ту
же личность `.NETCoreApp,Version=v8.0 / windows10.0.17763`, и Rider оставлял первую, а Revit 2026
из решения исчезал совсем.

**На оси .NET Framework год не едет никуда — намеренно.** Очевидная замена платформе,
`TargetFrameworkProfile`, работает ровно до первого пакета, у которого есть только netstandard:
NuGet отображает netstandard на .NETFramework лишь для фреймворка без профиля, и под
`Profile=revit2024` папка netstandard перестаёт подходить. `AssetTargetFallback` не спасает —
группа *зависимостей* netstandard всё ещё подходит, пакет считается совместимым, и вместо запасного
пути получается пустая группа компиляции. Измерено на одном restore, где рядом стояли `net48` и
`net48-revit2024`: `netstandard2.0` у первого, ничего у второго. `CommunityToolkit.Mvvm` — ровно
такой пакет, и он в принятом наборе Revit-side UI.

Потеря профиля стоит только ярлыка. Revit 2024 — единственный выпуск на .NET Framework и таким
останется, путать `net48-revit2024` не с чем; личность у него простая `.NETFramework,Version=v4.8`,
а моникёр по-прежнему называет каталог вывода и запись в assets.

Все четыре поддержаны и проверены сборкой. Добавление новой версии Revit — **одна строка**
`RevitSupportedReleases` в `build/BHS.Revit.Sdk/Sdk/targets/Revit.Identity.targets` вида
`<год>=<чистый моникёр>`; таблица валидации и список объявленных версий платформы выводятся
из неё.

Реальная вторая ось мультитаргетинга — **сторона процесса**, а не версия .NET:
Revit-side сборки собираются по Revit-TFM, а общий код и UI — по чистой оси `net48;net8.0;net10.0`.

> **Механика .NET Framework из `..\BHS` и `..\BimHouseApp` не нужна.** Подмена
> `TargetFrameworkProfile` и `FrameworkPathOverride` через `ToolLocationHelper` понадобилась бы
> только вместе с профилем, а профиля у нас нет: личность `net48-revit2024` — обычная
> `.NETFramework,Version=v4.8`, и reference-сборки разрешаются штатно.
>
> Утверждение переписывалось дважды, поэтому стоит зафиксировать, почему. Сначала оно было верным
> по другой причине — моникёр транслировался в обычный `net48`. Потом трансляцию убрали (она делала
> проект невидимым для IDE), появился профиль, и заметка была перевёрнута. Затем профиль убрали
> из-за netstandard-пакетов — и вывод вернулся к исходному, уже на третьем основании.

> **Ограничение WinUI 3.** Windows App SDK требует .NET 6+, а Revit 2024 — это `net48`.
> Общий UI-слой, обязанный собираться под 2024, на WinUI 3 не соберётся. Рабочий прототип
> WinUI-окна внутри Revit есть в `..\RevitWinUiTest` (ручной P/Invoke для владения окном и модальности,
> `DispatcherFrame` для цикла сообщений, ~10 свойств csproj для отключения MSIX/PRI/RID-графа).
> Отсюда и принятое разделение: Revit-side — WPF, Win-side — WinUI 3 на `net10.0-windows`.
> Прототип полезен как справка по интеропу окон, если Win-side приложению понадобится
> показываться поверх окна Revit.

## Взаимодействие Revit-side и Win-side

### Состав

- **Revit-side** — в процессе Revit: команды, апдейтеры, внешние события, лента, точка входа
  `IExternalApplication`. Мультитаргетится по Revit-TFM.
- **Win-side** — **фоновое приложение** (не служба Windows) для задач, трудно- или невыполнимых
  внутри Revit. Запуск возможен **с обеих сторон**: из Revit-side или из системы. Расширяется
  функциональными модулями. Обратный сценарий — Win-side сам поднимает Revit с нужной моделью —
  **сделан и измерен**: `BHS.WinSide` по команде `--launch 2026` поднял Revit, дождался
  регистрации за 29,2 с, показал экземпляр в реестре, закрыл его изнутри за 54,7 с и сам заметил
  уход процесса. Запуск с моделью есть параметром, но на модели ещё не проверялся.
- **GUI Win-side** — отдельное приложение на `net10.0-windows` + WinUI 3.

Служба Windows рассмотрена и отклонена: Revit требует **интерактивной сессии пользователя**
(рабочий стол, графический конвейер; сообщается о зависании Revit на открытии модели при запуске
из службы). Значит служба не может поднять Revit, когда никто не залогинен, — а это было её
единственным содержательным преимуществом. При существующей сессии она делает ту же работу, что
пользовательский процесс, но через `WTSQueryUserToken` + `DuplicateTokenEx` + `CreateProcessAsUser`
вместо одной строки `Process.Start`. Плюс LocalSystem не видит сетевые ресурсы пользователя, где
лежат модели. Если понадобится работа совсем без пользователя — правильная форма будет
«служба + пользовательский агент», и Revit поднимает именно агент.

> **Лицензионная оговорка, от выбора формы не зависящая.** Позиция Autodesk по автоматизированному
> использованию Revit без участия человека — «uncertain space as far as the official license is
> concerned», вплоть до «may violate the license agreement». Риск привязан к **режиму использования**,
> а не к номеру сессии, поэтому переход со службы на пользовательское приложение от него не спасает.
> Сценарий с MCP-агентом смягчается тем, что агент действует по запросу человека, сидящего за этой
> машиной, под его лицензией, — но если сценарий пойдёт в продукт, вопрос стоит задать Autodesk прямо.

### Симметричность и обнаружение

Инициатором может быть любая сторона, поэтому **роли симметричны: обеим сторонам нужен
серверный конец**. Revit-side обязан принимать входящие подключения, включая Revit 2024 (`net48`).
Обе стороны обязаны уметь обнаруживать запущенные экземпляры компаньонов.

Реализация: **обе стороны держат сервер канала.** Win-side — один канал с фиксированным именем;
каждый экземпляр Revit — свой канал, имя которого включает корреляционный токен. Альтернатива
(сервер только у Win-side, Revit подписан долгоживущим стримом) требует писать корреляцию
запрос/ответ руками — то есть строить второй RPC внутри первого.

Цена: `PoolSize` в библиотеке — жёсткая константа 4, каждый слушатель блокирует поток, значит
**+4 потока в каждом процессе Revit**.

Сопоставление свежезапущенного Revit — **по корреляционному токену**. Токен передавать
**переменной окружения, не командной строкой**: командная строка чужого процесса читается через
WMI другими пользователями машины.

> **Опасение про launcher не подтвердилось.** `Revit.exe` весит 1,6 МБ и выглядит как launcher, и
> здесь стояло предположение, что PID из `Process.Start` может не совпасть с процессом, где живёт
> add-in. Измерено на всех четырёх версиях: **совпадает всегда** — окно держит именно запущенный
> процесс, передачи другому процессу нет. Токен остаётся нужен по другой причине: отличить, какой
> из нескольких одновременно работающих Revit только что зарегистрировался.

Регистрация двухэтапная: в `OnStartup` документа ещё нет, поэтому сначала регистрация с токеном,
затем сообщение об открытии модели по `DocumentOpened`; у ожиданий разные бюджеты. Таймауты
библиотеки (30 с на подключение клиента, жёсткие 10 с на `RequestInit`) для холодного старта Revit
не годятся — ожидание живёт на стороне Win-side со сторожевым контролем процесса: если запущенный
процесс умер, падать сразу, а не по таймауту.

**Измеренный холодный старт** (чистый запуск, до готового главного окна, машина разработчика):

| Revit | Первое окно | Готов | Заставка при `/nosplash` |
|---|---|---|---|
| 2024 | 21,9 с | **71,6 с** | появляется (окно `Splash`) |
| 2025 | 19,3 с | **66,8 с** | появляется |
| 2026 | 9,8 с | **52,9 с** | подавлена |
| 2027 | 23,9 с | **57,9 с** | подавлена |

То есть бюджет ожидания — минута с небольшим на версию, а не «минуты» неопределённо; полный
проход по четырём версиям обходится примерно в пять минут чистого времени Revit.

Ключи `Revit.exe`: `/nosplash`, `/runhidden`, `/runmaximized`, `/language`, `/noninteractive`,
`/viewer` — строки присутствуют в `DesktopMFC.dll` всех версий 2024–2027, официальной документации
Autodesk нет. Из измеренного: `/nosplash` **принимается, но работает не везде** — на 2026 и 2027
заставки нет, на 2024 и 2025 окно `Splash` всё равно появляется. Про `/runhidden` снаружи судить
нельзя: по окнам он неотличим, нужен add-in, докладывающий изнутри.

**Закрывать Revit — изнутри.** `CloseMainWindow()` снаружи сработал один раз из четырёх (на
полностью простаивающем 2025) и был проигнорирован в остальных. Штатный путь —
`RevitCommandId.LookupPostableCommandId(PostableCommand.ExitRevit)` из add-in; член `ExitRevit`
присутствует в `RevitAPIUI` всех четырёх версий (проверено по метаданным). Убийство процесса —
запасной вариант, а не основной.

#### Соглашение об именах каналов

```
\\.\pipe\BHS.WinSide                          — синглтон, well-known
\\.\pipe\BHS.WinSide.<pid>                    — экземплярное, для диагностики
\\.\pipe\BHS.RevitSide.<pid>.<revitVersion>   — по одному на процесс Revit
```

**Штатный путь обнаружения — регистрация, а не сканирование.** Revit-side подключается к Win-side
по well-known имени и сам регистрируется, передавая имя своего канала, версию Revit, PID и
корреляционный токен; Win-side ведёт живой реестр. Перечисление `\\.\pipe\` с фильтром по префиксу
`BHS.` — только для восстановления (Win-side перезапустился и потерял реестр) и для диагностики.
Живость кандидата подтверждается коротким вызовом с дедлайном.

**Реестр сделан и проверен** — `RevitInstanceRegistry` в `BHS.Transport`, плюс `WinSideService`,
у которого `Register` запечатан и заведён на реестр: хост доопределяет только `Ask` и `Shutdown`.
Ключ — идентификатор экземпляра, поиск — по корреляционному токену. Что стоит знать:

- **`Expect(token)` объявляется до запуска процесса**, иначе быстро зарегистрировавшийся Revit
  приедет раньше, чем его ждут. Таймаута у ожидания нет намеренно: ждёт тот, у кого хэндл процесса,
  и он отличает «ещё стартует» от «умер на старте» — часами не отличает.
- **Второй слой доверия применён, а не только доступен**: при регистрации реестр спрашивает у
  системы, кто на самом деле обслуживает названный канал, и сверяет с заявленным PID. Проверка
  стоит одного короткого подключения внутри вызова, которого ждёт пир; это безопасно в ту сторону,
  в какую делается — регистрирующая сторона зовёт со своего потока, её пул из четырёх слушателей
  не блокируется. Не прошедший проверку **всё равно записывается**, но помеченным: занятый пир — не
  самозванец, а самозванец — повод доложить, а не спрятать.
- **Уход замечается сразу, а не по опросу**: запись называет процесс, а за процессом можно следить.
  `SweepAsync` — запасной путь для экземпляра, чей хэндл открыть не удалось; такие видны как
  разница между `Instances` и `Watched`.
- **Восстановление перечислением работает, но токен не восстанавливает** — он живёт в сообщении
  регистрации и в окружении запущенного процесса. Восстановленный экземпляр поэтому никогда не
  «наш», даже когда он наш.
- **У восстановления нет рукопожатия**, поэтому версию контракта теперь везёт каждый снимок
  конфигурации (`ConfigurationSnapshot.contract_version`). Пир, не назвавший контракт, при
  восстановлении отвергается — та же позиция, что у `Handshake.EnsureCompatible` к вызывающему,
  который контракт не назвал.

Измерено: 17 проверок реестра зелёные на `net48`, `net8.0-windows` и `net10.0-windows` (консольная
проба выросла с 20 проверок до 37, а с настройками с диска — до 65), и весь набор — против живого
Revit 2024, 2025 и 2027.

Несколько экземпляров Win-side сосуществуют по имени с PID, но «главный» один — победитель
дополнительно создаёт канал без суффикса. **Сделано и проверено** в `BHS.WinSide`; имя мьютекса
уточнено против первоначального плана:

```
Global\BHS.WinSide.<SID пользователя>
```

Обе половины имени намеренные. **Машинное**, потому что машинными являются имена каналов:
пространство `\\.\pipe\` не посессионное, и две сессии столкнутся на `BHS.WinSide` независимо
от того, что говорит посессионный мьютекс. **С ключом по пользователю**, потому что дескриптор
канала пускает ровно одну учётку: правильный вопрос не «кто владеет машиной», а «кто владеет
машиной для этого пользователя». Одно общее глобальное имя выбрало бы одного победителя на все
сессии и оставило бы остальных без возможности к нему подключиться.

Мьютекс **держится, но не захватывается** (`initiallyOwned: false`): владение привязано к потоку,
а асинхронный хост этого гарантировать не может; решает выборы сам факт существования именованного
объекта, а держать его существующим достаточно открытым хэндлом.

> Попутно измерено: **непривилегированный процесс создаёт `Global\`-мьютекс** на этой машине,
> хотя `SeCreateGlobalPrivilege` в его токене нет. Привилегия ограничивает объекты-секции, а не
> мьютексы. Проверить стоило: если бы не создавался, пришлось бы менять схему имён.

Защищённый префикс `ProtectedPrefix\Administrators\` **Revit-side недоступен никогда** — его может
создать только администратор или LocalSystem, а Revit работает под обычным пользователем. Держать
префикс отдельным необязательным сегментом конфигурации, чтобы возможный будущий переезд Win-side
в службу не ломал разбор имён.

#### Доверие к другому концу канала

Отличить свой канал по владельцу **нельзя**: чтения дескриптора безопасности канала по пути в .NET
нет, `Get-Acl` падает даже на собственном только что созданном канале. Перечисление даёт только
имена. Поэтому доверие строится тремя слоями, и проверка идёт **после подключения**:

1. `PipeSecurity` на сервере — кто вообще может подключиться;
2. проверка процесса на том конце — `GetNamedPipeServerProcessId` у клиента и `Peer` /
   `GetImpersonationUserName` у сервера, с резолвом полного пути к образу и сверкой с местом
   установки; в продакшене плюс проверка подписи Authenticode;
3. рукопожатие в протоколе — версия контракта, идентификатор экземпляра, корреляционный токен.

> **Асимметрия net48.** `PipeOptions.FirstPipeInstance` и `CurrentUserOnly` появились в .NET 6 и на
> Revit 2024 недоступны, а библиотека не выставляет `FirstPipeInstance` ни на одном TFM. То есть оба
> встроенных механизма — «создай канал, только если его ещё нет» и «подключайся только к серверу
> того же пользователя» — на нижнем крае диапазона отсутствуют, и защита от захвата имени держится
> целиком на слоях 1–3. По той же причине выбор главного экземпляра Win-side делается мьютексом,
> а не гонкой за именем канала.

### Транспорт — named pipes

`System.IO.Pipes` на всех версиях. Отвергнут TCP на loopback.

- Работает от `net48` до `net10` без единого пакета.
- Настоящая аутентификация вызывающего — DACL плюс PID и олицетворение, вместо разбора
  `context.Peer` регуляркой, как в BHS (тот фильтр пропускает любой локальный процесс
  любого пользователя).
- Проходит границу session 0, не занимает порт, не требует TLS ради локального обмена.
- **Обнаружение дёшево**: пространство `\\.\pipe\` перечисляется как каталог, а умерший процесс
  следа не оставляет — ядро удаляет канал при закрытии последнего хэндла, так что протухших
  записей практически не бывает. С TCP пришлось бы вести реестр портов в файле и чистить его.

### RPC поверх канала — GrpcDotNetNamedPipes

Сохраняется модель программирования gRPC и контракты `.proto`; заменяется только кадрирование
(вместо HTTP/2) и транспорт (вместо TCP). Меняются две строки: `NamedPipeServer` вместо `Server`,
`NamedPipeChannel` вместо `Channel`.

> **Это не совместимый gRPC.** Протокол на проводе свой, сторонний gRPC-клиент не подключится.
> Обе стороны обязаны быть на этой библиотеке. Точная формулировка: «модель программирования
> gRPC и контракты `.proto`, транспорт приватный».

Почему не обычный gRPC: **сервера gRPC на .NET Framework не существует** (хостинг требует
ASP.NET Core), а клиент на `net48` работает только по TLS, на Windows 11+/Server 2019+,
без client и duplex стриминга. Пока Revit 2024 в поддержке, gRPC поверх HTTP/2 неприменим.
Настоящий gRPC поверх именованных каналов (Kestrel `ListenNamedPipe`, .NET 8+) открывается
только при отказе от 2024.

**Библиотека форкнута — и не «на всякий случай», а по измеренной необходимости.**
`source/Shared/BHS.Grpc.NamedPipes` везёт исходники 3.1.0 дословно и меняет ровно одну вещь:
версию `System.Memory`, против которой они компилируются. Без этого канал не работает внутри
Revit 2024 — разбор в разделе про конфликт сборок. Обновление сводится к копированию каталога;
порядок описан в readme рядом.

Запасной вариант, если апстрим будет заброшен совсем: свой тонкий RPC на `System.IO.Pipes` +
MessagePack. Риск ограничен — 76 КБ под Apache 2.0, копирайт Google LLC.

### Конфликт сборок с самим Revit

**Revit 2025, 2026 и 2027 возят собственные `Grpc.*` и `Google.Protobuf`**
(`Grpc.Core.Api` 2.59.0.0, `Google.Protobuf` 3.23.1.0), причём это живая подсистема
(`ATFRevitGrpcInterface`, `grpcProtos`), а не забытые файлы. У Revit 2024 их нет.

Измерено на живом процессе Revit 2025: **наши копии подменяются копиями Revit** — из четырёх
сборок add-in две загрузились из `C:\Program Files\Autodesk\Revit 2025`. Побеждает
загрузившийся первым, а Revit грузится раньше add-in.

Про окно проблемы здесь **дважды стояло неверное утверждение**, и оба раза его снял живой
замер пробой (`source/Revit/BHS.Revit.Probe`):

- «на 2026+ спасает изоляция» — спасает, **только если её попросить**. Обычный add-in на
  Revit 2026 живёт в `DefaultDomain`, и его `Google.Protobuf` и `Grpc.Core.Api` — ревитовские,
  из `C:\Program Files\Autodesk\Revit 2026`. Изоляция включается `UseRevitContext=False` +
  `ContextName` в манифесте и по умолчанию не действует;
- «на 2024 конфликта нет» — конфликта с `Grpc.*` действительно нет, потому что Revit 2024 их не
  возит. Но там **фатальный конфликт по `System.Memory`**, и он ломает канал целиком: см. ниже.

Замеренная подмена на 2025 и 2026 (`Google.Protobuf` 3.23.1, `Grpc.Core.Api` 2.0.0.0 — обе
ревитовские вместо наших) **работе не помешала**: 20 с лишним проверок канала внутри Revit
зелёные на обеих версиях. То есть анализ метаданных, обещавший ноль расхождений на используемой
поверхности, подтверждён исполнением.

Проверено анализом метаданных: `GrpcDotNetNamedPipes` 3.1.0 обращается к 55 типам и 79 членам
ревитовских сборок, расхождений — ноль. Поверхности `Grpc.Core.Api` 2.59 и 2.67 **идентичны**
(499 членов, ноль добавленных) — это намеренно замороженная контрактная сборка, отсюда и
`AssemblyVersion 2.0.0.0` на всю ветку 2.x.

**Пиннинг версий не делаем.** Понижать нечего, а прямая ссылка на 2.59 даст `NU1605`,
подавление которого потом скроет настоящее понижение.

Вместо этого:

- **Правило: только `syntax = "proto3"`. Editions не использовать.** Код для editions ссылается
  на `Reflection.Edition` и `Features`, которых в ревитовской 3.23.1 нет — на Revit 2025 это
  `TypeLoadException` при первом вызове.
- **Проверка в сборке**: прогонять выходные сборки Revit-side против набора, который реально
  возит каждая поддерживаемая версия Revit, и падать при расхождениях. Закрывает весь класс
  проблемы, а не два пакета: Revit расходится с нами и по `System.Memory` (4.0.1.1 против 4.0.1.2),
  `System.Runtime.CompilerServices.Unsafe` (4.0.4.1 против 6.0.0.0), `System.Collections.Immutable`
  (1.2.5.0), причём `Revit.exe.config` для них binding-redirect'ов не содержит.
- **Логировать на старте** фактически загруженные сборки с путём и версией. **Сделано** — это
  заголовок лог-файла, см. раздел про логирование.
- **У RefCheck три модели связывания, а не одна.** Он исходил из того, что ревитовская копия всегда
  подменяет нашу; на деле случаев три, и остальные два он выдумывал или не видел:

  | Случай | Когда | Что делает тул |
  |---|---|---|
  | подмена | идентичности совпали, либо редирект свёл нашу на ревитовскую | сверяет поверхности — `RVTREF001..003` |
  | раздвоение | версии разные, ничто их не сводит; грузятся **обе** | `RVTREF006`, обычной строкой |
  | висячая ссылка | нужной идентичности нет нигде | **пока не проверяется** |

  Случай 2 — история этого репозитория: `Grpc.Core.Api` просил `System.Memory` 4.0.1.1,
  `GrpcDotNetNamedPipes` — 4.0.2.0, загрузились обе, и это стоило форка. Раньше на этом месте
  выдавалась ошибка про конфликт с Revit, которого нет.

  **Редиректы теперь в эталоне** (`redirects` из `Revit.exe.config`) и применяются только на оси
  .NET Framework. Без них диагноз ошибается в обе стороны: `Newtonsoft.Json` опасен *потому что*
  редирект сводит копии на одну идентичность, а `System.ComponentModel.Annotations` безопасен
  *потому что* редирект его покрывает.

  `RVTREF006` **сообщает, а не предупреждает**: каждая находка верна и ни одна не действие сама по
  себе — `System.Numerics.Vectors` грузится в двух копиях месяцами без вреда. Опасен только шов
  между двумя нашими сборками. Предупреждение на каждой сборке про то, что обычно нормально,
  приучает не читать журнал.

  Проверено: инструмент находит на сборке ровно тот шов, который до этого нашли запуском Revit —
  `System.Memory`, запрошенная и как 4.0.2.0, и как 4.0.5.0 при ревитовской 4.0.1.1.

- **Запрет проверяется сборкой, а не соглашением** — `RVTREF005`. В `watchlist.json` рядом со
  списком `assemblies` лежит список `denied`: простые имена, которых в выходе Revit-side проекта
  быть не должно ни в какой версии (`Microsoft.Extensions.*`, `Newtonsoft.Json`, `System.Text.Json`,
  `Serilog*`, `log4net`, `NLog*`). Проверка смотрит **готовый набор файлов** (`$(TargetDir)`), то
  есть ловит и транзитивную зависимость, приехавшую через `CopyLocalLockFileAssemblies`.

  Дискриминатор Revit-side/Win-side уже был и уже правильный: `RevitReferenceCheck` включается по
  `'$(RevitVersion)' != ''`, то есть ровно на проектах с Revit-TFM. Поэтому
  `BHS.Settings.Configuration`, `BHS.Transport.Configuration`, `BHS.WinSide` не проверяются вовсе,
  и **список исключений не нужен** — а список исключений это ровно то место, где запреты умирают.
  Ошибка в опасную сторону (ссылка из Revit-side проекта на Win-side сборку) как раз попадётся.

  Имя может стоять и в `assemblies`, и в `denied` — это не противоречие. Списки отвечают на разные
  вопросы: первый — «если Revit подменит нашу копию своей, все ли члены на месте», второй — «имеем
  ли мы право эту сборку везти вообще». **Приоритет за `denied`**, и урок случая с
  `Microsoft.Extensions.Configuration` именно такой: поверхности совпадали полностью, а add-in не
  загрузился. Escape hatch намеренно не предусмотрен: свойство «а этому проекту можно» будет
  выставлено в спешке и не снято никогда.

#### Revit 2024 и `System.Memory`: почему библиотека форкнута

Самый дорогой из найденных конфликтов, и единственный, потребовавший форка. Измерен пробой:
`BHS.Transport` зелёный на `net48` как консольное приложение и падал внутри Revit 2024 на первом
же вызове:

```
MissingMethodException: Method not found:
  'System.Buffers.IBufferWriter`1<Byte> Grpc.Core.SerializationContext.GetBufferWriter()'
```

Цепочка причин, каждое звено проверено на живом процессе:

1. `Grpc.Core.Api` собран против `System.Memory` **4.0.1.1** — так во всех версиях пакета,
   от 2.46 до 2.83; опубликованная `GrpcDotNetNamedPipes` 3.1.0 — против **4.0.2.0**. Пакеты
   между собой не согласованы и рассчитывают на binding redirect.
2. Revit 2024 **возит собственную `System.Memory` 4.0.1.1** в каталоге установки, то есть в
   application base. Ссылка на 4.0.1.1 связывается там, ссылка на 4.0.2.0 — на нашу копию.
   `System.Buffers.IBufferWriter<byte>` оказывается **двумя разными типами**, и сигнатура метода
   перестаёт совпадать.
3. Обычное лекарство — `bindingRedirect` — **add-in'у недоступно**. Своего `.config` у него нет,
   конфигурацией правит `Revit.exe.config`, а редиректов для `System.Memory` там нет. Именно этот
   редирект SDK генерирует в `.exe.config` консольной пробы, и только поэтому та зелёная.
4. `AppDomain.AssemblyResolve` **не помогает** — он вызывается только когда связывание
   провалилось, а здесь оно успешно, просто не туда. Проверено: обработчик за весь запуск ни разу
   не спросили про `System.Memory`.
5. Убрать наши полифиллы из поставки тоже не помогает: тогда 4.0.2.0 уезжает на **третью** копию,
   `Revit 2024\AddIns\PnIDModeler\System.Memory.dll`, и типы по-прежнему разные.

**Решение — `source/Shared/BHS.Grpc.NamedPipes`**: исходники `GrpcDotNetNamedPipes` 3.1.0
дословно, пересобранные против `System.Memory` **4.5.4** (сборочная версия 4.0.1.1). Все три
ссылки сходятся на одной идентичности — той, что возит Revit, — и `IBufferWriter<byte>`
становится одним типом. Понижением это не является: и `Grpc.Core.Api`, и `Google.Protobuf`
требуют не ниже 4.5.3. Подробности и порядок обновления — в readme того каталога.

Заодно сборка переименована в `BHS.Grpc.NamedPipes`: наша копия от стандартной отличается, а в
общем AppDomain Revit 2024 сборка с именем `GrpcDotNetNamedPipes` столкнулась бы с любым другим
вендором, взявшим готовый пакет.

**Результат измерен.** После форка проба зелёная на **всех четырёх** версиях Revit; на 2024
`System.Memory` и `System.Runtime.CompilerServices.Unsafe` загружаются из каталога Revit в
единственном экземпляре.

> Это и есть довод в пользу метрики «число полифиллов BCL, а не мегабайты». Каждый полифилл на
> `net48` — ссылка, которую кто-то в общем AppDomain уже связал по-своему, и ни компилятор, ни
> RefCheck этого не видят: RefCheck сверяет нашу поверхность с ревитовской, а здесь ломалось
> совпадение сигнатур **между двумя нашими же пакетами**.

#### UI-набор против форка: измерено на живом Revit 2024

Принятый Revit-side UI-набор и форк `BHS.Grpc.NamedPipes` спорят об одной сборке, и спор разрешён
замером, а не рассуждением.

`WPF-UI` 4.1.0 на ветке `net4x` зависит от пакета `System.Memory` **4.6.3**, `CommunityToolkit.Mvvm`
8.4.0 — от **4.6.0**. Идентичности:

| пакет | `AssemblyVersion` |
|---|---|
| 4.5.4 — против него собран форк | **4.0.1.1** |
| 4.6.0 — тянет `CommunityToolkit.Mvvm` | 4.0.2.0 |
| 4.6.3 — тянет `WPF-UI` | **4.0.5.0** |
| что везёт Revit 2024 | **4.0.1.1** |

NuGet унифицирует вверх, и **в выводе сборки оказывается 4.0.5.0** — то есть ровно то, чего форк
избегал. Сборкой это не видно: запись «набор проверен сборкой на всех четырёх TFM» верна и об этом
молчит, потому что отказ такого рода происходит при загрузке.

**Что показал живой Revit 2024** (проба с набором на борту, `LogBinding`):

```
bind 'System.Memory, Version=4.0.1.1' -> 4.0.1.1  C:\Program Files\Autodesk\Revit 2024\System.Memory.dll
bind 'System.Memory, Version=4.0.2.0' -> 4.0.1.1  ...\Revit 2024\AddIns\PnIDModeler\System.Memory.dll
bind 'System.Memory, Version=4.0.5.0' -> 4.0.5.0  ...\Addins4\...\BHS.Revit.Probe\Lib\System.Memory.dll
GetBufferWriter returns IBufferWriter`1 from System.Memory 4.0.1.1
```

- **Ничего не сломалось.** `Wpf.Ui` и `CommunityToolkit.Mvvm` загрузились, канал работает, все 148
  проверок прогона зелёные с набором на борту. Утверждение «WPF-UI отменяет форк и всё падает» —
  **неверно**.
- **Но обе копии живут в процессе одновременно.** Транспорт связан с 4.0.1.1, UI — с нашей 4.0.5.0.
  `Span<T>`, `Memory<T>`, `IBufferWriter<T>` из них — разные типы. Мина не сработала лишь потому,
  что UI и транспорт сегодня ничем таким не обмениваются.
- **Цена в полифиллах: 7 вместо 4.** Добавляются `Microsoft.Bcl.AsyncInterfaces` 8.0.0.0,
  `System.ComponentModel.Annotations` 4.2.1.0, `System.Threading.Tasks.Extensions` 4.2.0.1,
  а `System.Runtime.CompilerServices.Unsafe` поднимается до 6.0.3.0.

> **Поправка к поправке — и вторая версия верная.** Сначала здесь стояло, что на .NET Framework
> запрос более высокой версии удовлетворяется низшей копией, со ссылкой на строку
> `bind 4.0.2.0 -> 4.0.1.1`. **Это неверно.** Fusion не подставляет под строгое имя файл другой
> версии без редиректа, и никакого редиректа для `System.Memory` нет.
>
> Подстановку сделал **`RevitAssemblyResolver`** — Revit возит его во всех четырёх версиях
> (`AppDomain.AssemblyResolve`, сопоставление по простому имени), и это видно по самому пути в
> замере: файл пришёл из `Revit 2024\AddIns\PnIDModeler\`, куда Fusion для нашего add-in не
> заглядывает никогда.
>
> Следствие важнее самой поправки: **зелёный прогон доказывает «работает здесь», а не «работает».**
> На машине без этого чужого плагина та же ссылка стала бы висячей. Приносит её только
> `CommunityToolkit.Mvvm` — ещё один довод против него.

#### Выход из запрета: слияние зависимости внутрь себя (ILRepack)

У правила «не везти чужих сборок» есть **проверенный выход**, и его стоит знать до того, как он
понадобится. `ILRepack` с `Internalize=true` вплавляет зависимость в нашу сборку и делает её типы
внутренними: наружу не выходит ни ссылки, ни имени, и столкнуться становится не с чем.

**Измерено на нашем единственном воспроизводимом отказе.** `Microsoft.Extensions.Configuration`
10.0 вместе с `.Abstractions` и `Primitives` слит в одну сборку, код через неё **выполнен**:

```
merged configuration says: value
no Microsoft.Extensions assembly is loaded at all: True
```

- **На оси .NET (2025–2027) это полное решение.** Слитая сборка ссылается только на shared
  framework — ни одной сторонней ссылки. Отказ на Revit 2026 при таком устройстве невозможен.
- **На `net48` зависит от версии пакета**, и разница решающая:

  | `Microsoft.Extensions.Configuration` | `System.Memory` | `System.Buffers` | `Unsafe` |
  |---|---|---|---|
  | 10.0.11 | 4.0.5.0 | 4.0.5.0 | 6.0.3.0 |
  | 8.0.0 | 4.0.1.2 | 4.0.3.0 | 6.0.0.0 |
  | **6.0.0** | **4.0.1.1** | **4.0.3.0** | 6.0.0.0 |
  | *держит Revit 2024* | *4.0.1.1* | *4.0.3.0* | *4.0.4.1* |

  На 6.0 два полифилла из трёх совпадают с ревитовскими точно, включая `System.Memory` — значит
  `Span<T>` остаётся одним типом с транспортом. Расходится только `Unsafe`, а он статический хелпер
  и типов в сигнатурах не даёт, так что раздвоение там безвредно.

**Три правила, за которые выходить нельзя:**

1. **Только листовая зависимость.** Общий словарь сливать нельзя: `System.Memory` на `net48` — это
   `Span<T>`, `Memory<T>`, `IBufferWriter<T>`, общие с `Grpc.Core.Api` и `Google.Protobuf`, которых
   мы не сливаем. Внутренняя копия `Span<T>` — новый тип, `GetBufferWriter()` его не примет.
   Слияние здесь **создаёт** шов, а не убирает.
2. **Ничего из публичного API.** `Internalize` делает типы `internal`; если сборка публично отдаёт
   `IConfigurationSource`, после слияния это невозможно. `excludeFile` оставит их публичными, но
   тогда это **наш** `IConfiguration`, а не общемировой: внутри работает, а отдать его чужому
   `HostBuilder` уже нельзя.
3. **Не для WPF-пакетов.** XAML-ссылки вида `pack://application:,,,/Wpf.Ui;component/...` содержат
   имя сборки; переименование ломает словари ресурсов и стили по умолчанию.

> **Принятых решений это не меняет.** `BHS.Settings` и `BHS.Logging` уже без зависимостей и проще,
> чем сборка со слиянием. Но техника названа и проверена, и в первый же раз, когда понадобится
> настоящая сторонняя **листовая** библиотека — PDF, Excel, геометрия, — отвечать «нельзя» больше
> не придётся.

#### Раздвоение видно в логе, а не только в предсказании

Лог фреймворка подписан на `AppDomain.AssemblyLoad` и записывает поздние загрузки интересных
сборок. Первый же прогон после этого показал на Revit 2024:

```
assembly:System.Memory 4.0.1.1 | C:\Program Files\Autodesk\Revit 2024\System.Memory.dll
assembly:System.Memory 4.0.1.2 | C:\Program Files\Bim.com Design App\plugins
evit4\System.Memory.dll
```

Две `System.Memory` в одном AppDomain: наша связалась с ревитовской 4.0.1.1, чужой плагин привёз
свою 4.0.1.2. Это тот самый случай раздвоения, который `RVTREF006` предсказывает по сборке, — и
теперь он виден и в рантайме, без специального замера.

**Сторож — `AssemblyLoad`, и ни в коем случае не `AssemblyResolve`.** Первый только смотрит, и на
2024 видеть чужие загрузки безвредно. Второй в том же месте отвечал бы за чужие разрешения и
раздавал наши сборки другим вендорам — его из пробы сознательно убрали, и Revit, как выяснилось,
держит свой собственный (`RevitAssemblyResolver`).

**Заголовок лога — снимок, и одного снимка мало.** Обнаружилось при переносе логирования в host:
он поднимает лог раньше, чем кто-либо трогает транспорт, и заголовок перестал называть ту самую
сборку, о которой обычно и спрашивают. Снимок плюс запись поздних загрузок отвечают на вопрос
целиком.

#### Newtonsoft.Json — запрещён во framework-слое Revit-side

Здесь конфликт **реальный**, в отличие от gRPC. Revit 2024 возит `Newtonsoft.Json` 13.0.1
(3720 членов), пакет 13.0.3 даёт 3733; в ревитовской копии **отсутствуют** в том числе
`JsonSerializerSettings::.ctor(JsonSerializerSettings)`, тип `Linq.JsonCloneSettings` целиком,
`JToken::DeepClone(JsonCloneSettings)`, `UnixDateTimeConverter::AllowPreEpoch`.

Опаснее случая с gRPC по двум причинам: `AssemblyVersion` у обеих копий **одинаковая**
(`13.0.0.0`), и `Revit.exe.config` содержит редирект `0.0.0.0-13.0.0.0 → 13.0.0.0`. Копии
неразличимы, редирект сводит всё к одной, побеждает загрузившийся первым — то есть Revit.
Наша 13.0.3 из каталога add-in просто не будет использована.

Итог: код компилируется против 13.0.3 и падает в рантайме с `MissingMethodException`, если
тронет хоть один из этих членов. На Revit 2024 и 2025, где изоляции нет, это гарантировано.

Единственная причина, по которой он был во framework-слое BHS, — сериализация конфигурации;
переход на `map<string, string>` её убирает. Если Newtonsoft всё же понадобится в Revit-side,
ограничиваться поверхностью 13.0.1 и обязательно накрывать проверкой в сборке: компилятор здесь
не помощник.

> Это и есть довод в пользу проверки в сборке против пиннинга пакетов: gRPC оказался чист,
> а Newtonsoft — нет, и заранее это не было очевидно ни по одному признаку.

#### Microsoft.Extensions.* — запрещён в Revit-side

> **Правило переписано после живого замера.** Раньше здесь стояло «не запрещён, но у самого края»
> с оговоркой «не берите версии 2.2 и ниже». Оговорка верна и осталась ниже, но она описывает
> только `.NET Framework` и только нижний край. На оси .NET нашлось кое-что хуже, и оно свалило
> add-in целиком.

**Измерено на Revit 2026.** Проба, читавшая свои настройки через `Microsoft.Extensions.Configuration`
10.0, **не загрузилась вовсе**:

```
FileLoadException: Could not load file or assembly
  'Microsoft.Extensions.Configuration.Abstractions, Version=10.0.0.0, ...'
```

Причина в загрузчике .NET, а не в редиректах, которых там нет. `DynamoForRevit` лежит **в самом
каталоге Revit 2026** и везёт `Microsoft.Extensions.Configuration.Abstractions` **2.0.0.0**;
он грузится до любого add-in, занимает простое имя, и дальше запрос **более высокой** версии
не удовлетворяется ничем. Это не тихая деградация, как у Newtonsoft, — это отказ загрузки.
На этой машине для 2026 установлено **двадцать три** копии одной этой сборки, у восемнадцати
чужих плагинов.

Отсюда правило, и оно сильнее прежнего:

> **В Revit-side не должно попадать ни одной сборки `Microsoft.Extensions.*`.** Ни в какой версии.
> На оси .NET Framework вас съест binding redirect, на оси .NET — чужая копия, загрузившаяся
> первой. Обе половины конфигурации построены под это правило: `BHS.Settings` не имеет **ни одной**
> ссылки на пакеты, а `Microsoft.Extensions.Configuration` живёт в `BHS.Settings.Configuration` и
> `BHS.Transport.Configuration`, которые Win-side.

Сохраняется и прежняя, более узкая формулировка — она про `.NET Framework` и остаётся верной:
Revit 2024 и 2025 возят `Microsoft.Extensions.Configuration`, `.Configuration.Abstractions` и
`Primitives` версии **2.2.0.0**, а `Revit.exe.config` содержит редиректы `0.0.0.0-2.2.0.0 → 2.2.0.0`
для `Primitives`, `Options`, `Logging`, `Logging.Abstractions`, `DependencyInjection.Abstractions`,
`Caching.*`. Сборка версии 2.2 и ниже попадёт в диапазон, молча уедет на ревитовскую — и дальше
это случай Newtonsoft.

**Это не единичный случай, а состав процесса.** Просканированы каталог установки Revit и обе
папки `AddIns` (`%AppData%` и `%ProgramData%`) на машине разработчика; в скобках — версии сборок,
встреченные одновременно:

| Revit | `log4net` | `Microsoft.Extensions.Logging(.Abstractions)` | `Serilog` | `NLog` |
|---|---|---|---|---|
| 2024 | 7 копий (2.0.12, 3.0.3) | 7 копий (2.1.1, 2.2.0) | 2 копии (2.0.0) | — |
| 2025 | 4 копии (2.0.12, 3.0.3) | 6 копий (6.0, 7.0, 8.0) | 3 копии (2.0.0, 4.2.0) | — |
| 2026 | 3 копии (2.0.12) | 1 копия (6.0) | 2 копии (2.0.0) | — |
| 2027 | 4 копии (2.0.12) | 4 копии (3.1.6, 6.0, 8.0) | 3 копии (2.0.0, 4.2.0) | 1 копия (6.0) |

То есть **каждая ходовая библиотека логирования уже живёт в процессе Revit, причём в несовместимых
версиях сразу**. Это не риск на будущее — это то, что установлено сейчас. Отсюда следствие для
своего слоя логирования: ни `Microsoft.Extensions.Logging`, ни `Serilog`, ни `NLog`, ни `log4net`
в Revit-side взять нельзя, и мост `ILoggerProvider` → log4net из `..\BHS` неприменим обоими концами
сразу.

**RefCheck этого не поймал и не мог.** Он сверяет *поверхности* — какие типы и члены мы трогаем
против того, что возит Revit, — и по этой части расхождений не было ни одного. Отказ произошёл
уровнем ниже, при связывании имени со сборкой, и виден только исполнением. Ровно тот же зазор,
что и в случае с `System.Memory`: там компилятор и RefCheck тоже молчали.

**На Revit 2027 картина другая и измерена пробой** — причём дважды, с разным результатом, потому
что состав машины поменялся между замерами. Это само по себе вывод: **набор зависит от того, что
на машине доустановлено, а не только от версии Revit**, и разбираться по памяти нельзя.

- Первый замер: собственные `Microsoft.Extensions.*` лежали в `AddIns\IssuesManagement` и
  `AddIns\ExtendedAPIs`, версия **8.0.0.0**, и часть из них выигрывала загрузку у 10.0.11 из
  shared framework.
- Второй замер, после установки «Revit 2027 MCP Server Read-Tools Technical Preview»: почти весь
  набор `Microsoft.Extensions.*` приезжает уже из каталога этого превью и имеет версию
  **10.0.0.0**; в ревитовских папках остались только `Http` и `Http.Polly` версии 8.0.0.0.

То есть правило «не ниже 2.2» описывает только нижний край диапазона; на верхнем краю опасная
граница — **8.0.0.0**, но какие именно сборки на неё попадут, решает установленный набор.
RefCheck обе картины принял: расхождений на используемой поверхности нет.

**Ещё одно наблюдение с 2027, важное для планов по MCP.** Revit 2027 возит собственный
MCP-сервер: в процессе живут `ModelContextProtocol.Core` 0.5.0.0 и
`Microsoft.Extensions.AI.Abstractions`. Изначально он приезжал из `AddIns\Assistant`; после
установки превью read-tools сервер виден в логе прогона живым («message processing canceled» при
выходе). Прежде чем строить свой модуль MCP, стоит выяснить, что этот сервер уже умеет и расширяем
ли он — возможно, задача сводится к регистрации инструментов в чужом сервере, а не к своему.

По той же причине потребляющая половина канала (`BHS.Transport.Configuration`) вынесена в
отдельную сборку: тот, кто только **публикует** конфигурацию, не тащит `Microsoft.Extensions.*`
в общий AppDomain Revit вовсе. Тот же разрез сделан у конфигурации с диска — `BHS.Settings`
против `BHS.Settings.Configuration`.

### Логирование

Свой слой, `BHS.Settings`-образный: `BHS.Logging` без единой ссылки на пакеты, потому что внутрь
Revit едет она. Причина не в аккуратности — в таблице выше видно, что **каждая** ходовая библиотека
логирования уже загружена в процессе, и часть из них лежит в каталоге самой Autodesk.

**API.** `ILog` ровно из двух членов — `IsEnabled(level)` и `Write(level, message, error)`; весь
сахар в extension-методах `LogWriting`, как `ISettings` / `SettingsValues` рядом:

```csharp
_log.Info("registered as {0} after {1:F1} s", instanceId, elapsed.TotalSeconds);
_log.Error(error, "pipe {0} closed while streaming", pipeName);
```

- **Однометодный интерфейс — чтобы правило нельзя было нарушить.** Форматирование происходит
  только после проверки уровня, и гарантировать это можно единственным способом: не оставить
  реализации возможности сделать иначе.
- **Перегрузки на 0–3 аргумента, а не один `params`.** Массив `params` аллоцируется **до** входа
  в метод, то есть выключенный `Trace` всё равно стоит массива и упаковки. На `net48` в общем
  AppDomain это платят все add-in.
- **Уровни численно и по именам совпадают с `Microsoft.Extensions.Logging.LogLevel`** — без ссылки
  на него. Будущий мост станет приведением, а не таблицей; в `..\BHS` под ту же задачу написан
  транслятор на 42 строки.

**`LogRouter.Default` аддитивен и идемпотентен.** На Revit 2024 все add-in в одном AppDomain, то
есть два наших издания делят одну `BHS.Logging.dll` и один `Default`. Кто настраивает вторым, не
должен отменять первого: `Add` добавляет приёмник, `Apply` пересчитывает уровни, ни один ничего не
убирает. Выключенный приёмник — это `Minimum = None`, а не удаление. Ровно на допущении «я тут
один» погорел статический хост предыдущего поколения.

**Приёмники.** Файл (обязателен), journal Revit, `Trace`, консоль (Win-side).

- **Файл — `%LocalAppData%\BHS\Logs\<процесс>-<pid>-<время>.log`.** Не `%AppData%`, где настройки:
  логи не должны ездить по roaming-профилю. Не временный каталог Revit: у него в имени GUID сессии,
  и снаружи такой лог не найти — ровно тот случай, ради которого лог и существует.
- **Один файл на процесс.** Общий файл потребовал бы межпроцессной блокировки — открыть, дописать,
  закрыть на каждой строке; именно так настроен log4net в `..\BHS`, и это самый медленный путь.
- **Пишется синхронно, сбрасывается каждой строкой.** Интересные отказы — те, где процесс вот-вот
  убьют, и буфер теряет ровно их. Цена названа прямо: пишущий поток ждёт диск. Локально это
  микросекунды, **на сетевом ресурсе — нет**, поэтому пока приёмник синхронный, каталог лога
  обязан быть локальным.
- **Заголовок файла закрывает требование «логировать фактически загруженные сборки с путём и
  версией»** — оно осмысленно только рядом с тем запуском, который описывает.
- **Открыт с `FileShare.ReadWrite`**, поэтому Win-side может читать лог живого Revit. В v1 это
  единственный способ, каким он их видит.

**Journal берём, с двумя ограничениями.** Он кладёт наши события в одну временную шкалу с
операциями Revit — единственное место, где обе половины истории рядом. Но: **только с API-потока**
(с чужого молча пропускаем — файл эту запись уже получил) и **только `Warning` и выше**, потому что
journal уезжает в Autodesk с отчётом об ошибке. Маршрутизация чужих потоков через `ExternalEvent`
отвергнута: это та же очередь, которая на 2024 держала команду выхода 25 с, и запись, приехавшая
через 25 с, встанет в journal не на своё место — то есть сломает то самое свойство, ради которого
journal и берётся.

Следствие принимается сознательно: **события канала в journal не попадут никогда**, они все
приходят с потоков пула. Канал — наша внутренняя механика, ей место в файле.

**Пометка `*` у номера потока значит «API-поток».** Стоит ноль и адресует самую частую ошибку
проекта: вызов из канала приходит **не** на API-поток. В измеренном логе это видно прямо:
регистрация и запрос выхода без звёздочки, `OnStartup` и внешнее событие — со звёздочкой.

**Логи по каналу в v1 не гоняем.** Логировать надо раньше, чем канал существует, и в случаях,
когда его не будет вовсе; приёмник-канал породил бы рекурсию (канал логирует свои отказы) и
потребовал бы очереди. Дешёвая замена уже есть: Revit-side публикует путь своего лога обычным
ключом в снимке конфигурации, а файл открыт на чтение.

**Настройки — секция `Log`:** `Level`, `Levels:<категория>` (побеждает длиннейший совпавший
префикс), `Directory`, `File:Enabled|MaxSize|Retain|RetainDays`, `Journal:Enabled|Level`,
`Trace:Enabled`, `Console:Enabled`. Уровни и включённость приёмников перезагружаются на живую;
каталог — со следующего запуска.

> **Одно названное исключение из правила про нечитаемые значения.** В секции `Log` опечатка в
> уровне даёт предупреждение в лог и умолчание, а не отказ. Решение владельца, и причина —
> соразмерность: опечатка в имени уровня не должна мешать add-in загрузиться внутри Revit, где
> диалог никто не увидит. Везде остальное правило в силе.

**Стоимость измерена**: Revit-side приобретает **одну** сборку, `BHS.Logging.dll`, и **ноль** новых
полифиллов. Проба под `net48` — 14 сборок, из них те же 4 полифилла; всё лишнее — наше и с
префиксом `BHS.`.

### Изоляция add-in на 2026+ — измерена

`UseRevitContext=False` + `ContextName` в манифесте (метаданные item'а `RevitAddIn`; SDK
предупреждает и игнорирует их на версиях до 2026). Проверено пробой, чистое развёртывание:

| Revit | Контекст загрузки | Чья копия победила |
|---|---|---|
| 2026, обычный add-in | `Default` | Revit: `Google.Protobuf`, `Grpc.Core.Api` |
| 2026, изолированный | **`BHS.REVIT.PROBE`** | Revit: только `Grpc.Core.Api` |
| 2027, обычный add-in | `Default` | Revit: `Google.Protobuf`, `Grpc.Core.Api` |
| 2027, изолированный | **`BHS.REVIT.PROBE`** | **никто, все наши** |

**Изоляция работает и ничего не ломает** — под ней зелёные все проверки: канал, реестр, настройки,
логирование, journal, закрытие изнутри.

**Но гарантии она не даёт.** На 2026 ревитовский `Grpc.Core.Api` побеждает даже в собственном
контексте, на 2027 — нет; разница между версиями, а не между настройками, и похожа на порядок
загрузки: что Revit успел взять в `Default`, достаётся оттуда же. Механизм не установлен, и
утверждать его не следует.

> **Отсюда политика: изоляция — улучшение, а не замена правилу.** На 2024 и 2025 её нет вовсе,
> на 2026 она частична. Правило «не везти чужих сборок» остаётся единственным, что работает на всех
> четырёх версиях. Изоляцию можно включать сверху, но нельзя закладываться на неё.

> **Развёртывание только копирует, никогда не удаляет.** Найдено при этом же замере: в папках
> add-in лежали `BHS.Configuration.dll` и `GrpcDotNetNamedPipes.dll` от переименований и
> `Microsoft.Extensions.*` от дня, когда эту ссылку убрали. Revit грузил каталог, которого ни одна
> сборка давно не производила. Отдельно неприятно, что **`RVTREF005` читает вывод сборки, а не
> развёрнутую папку**, — запрещённая сборка может пережить запретившее её правило. Прогон пробы
> теперь чистит папку перед развёртыванием; для общего случая `RevitDeploy=Local` это остаётся
> открытым вопросом к SDK.

### Метрика для Revit-side

На `net48` Revit 2024 грузит все add-in в **один AppDomain** — изоляции нет. Поэтому правильная
метрика веса зависимости — **не мегабайты, а число полифиллов BCL**, вбрасываемых в общий
AppDomain. Ориентиры: named pipes — 4, grpc-dotnet — 7, StreamJsonRpc — ~14 (29 сборок).

Измерено на собранном наборе: `BHS.Transport` под `net48` — 4 сборки плюс ровно 4 полифилла
(`System.Buffers`, `System.Memory`, `System.Numerics.Vectors`, `System.Runtime.CompilerServices.Unsafe`),
то есть ориентир подтвердился. Добавление потребляющей половины доводит набор до 12 сборок —
поэтому она и отдельная.

**Метрику пришлось расширить.** Полифиллы BCL — не единственный род сборок, за которые идёт драка
в общем AppDomain; за `Microsoft.Extensions.*` и `System.Text.Json` дерутся ровно так же, и они
опаснее, потому что их возят десятки чужих плагинов. Правильная формулировка — **число сборок,
которые может привезти кто-то ещё**. Полифиллы попадают под неё как частный случай.

Отсюда и цена, которую платит Revit-side за конфигурацию с диска: **одна сборка, `BHS.Settings.dll`,
и ни одного нового полифилла** (проба под `net48` — 10 сборок, из них те же 4 полифилла). Тот же
слой через `Microsoft.Extensions.Configuration.Json` стоил бы 17 сборок и 9 полифиллов, включая
`System.Text.Json`, которого Revit не возит ни в одной версии — то есть версию не закрепляет никто.

### Framework-минимум контракта

Обмен конфигурацией — **framework-level, а не фича**, поэтому транспорт нужен с первого дня,
независимо от прикладных сервисов. Минимум: `Register`, `GetConfiguration`, `WatchConfiguration`,
`Ask`, `Shutdown` — пять методов, из них один стриминговый.

**Файл — источник истины для обеих сторон.** Обе стороны независимо читают свою слоистую
конфигурацию с диска и стартуют **без всякого канала** — это снимает зависимость от порядка
запуска целиком. По каналу передаётся не базовая конфигурация, а публикация специфичного для
экземпляра (версия Revit, пути, открытый документ) и уведомления об изменениях.

Схема из BHS «дочерний процесс спрашивает конфигурацию у родителя» отброшена: при запуске
Win-side из системы родителя нет.

#### Модельный слой: область — свойство ключа, а не слоя

Вопрос «модель важнее пользователя?» ответа не имеет, потому что задан не о том. У каждой настройки
**ровно одна область**, и она определяет, какую цепочку слоёв настройка читает:

| Область | Цепочка | Примеры |
|---|---|---|
| user-scoped | `Product → Machine → User → Process` | язык, тема, последние пути |
| project-scoped | `Product → Machine → **Model** → Process` | префиксы имён, шаблоны, правила округления |
| machine-scoped | `Product → Machine → Process` | пути к кэшам, таймауты запуска |

У project-scoped слой `User` **выпадает из цепочки, а не проигрывает ей**: пользователь не
проигрывает спор о правилах проекта — он в нём не участвует. Симметрично, модель не участвует в
споре про язык. Слой `Process` (`BHS_*` и overrides) остаётся над всем во всех трёх цепочках:
аварийный рычаг обязан уметь всё.

**Область объявляется префиксом `Model:`,** а не таблицей объявлений: таблица — это реестр, который
надо вести и который разъезжается с кодом при первой невнимательности. Признак, что разрез неверен:
ключи, нужные в обеих ролях, пойдут пачкой; тогда правильный ответ — таблица с областью на ключ,
и замена обратима (меняется один класс композиции).

**Хранилище — Extensible Storage внутри модели, а не файл рядом с ней.** Решает один факт: у
облачной и detached-модели `PathName` пуст, «рядом» для них не существует вовсе.

```
Schema BHS.ModelSettings   GUID 7b2b6a1e-2f4a-4a3d-9c1e-0f8a5d3c7e10   (навсегда)
                           VendorId BimHouseSoftware
                           ReadAccessLevel  Public     решение владельца
                           WriteAccessLevel Vendor
                           Version : string
                           Values  : map<string,string>
                           Cleared : array<string>
```

**Три поля, и никогда четвёртого.** Схему, уехавшую в чужую модель, изменить нельзя никогда —
реестр схем один на процесс Revit, переопределения нет, — а ключи внутри `map` менять можно.
Та же сделка, что у транспорта: типизируется форма, не пространство ключей.

**Третье поле нужно потому, что ES не хранит `null`.** А снятие значения — настоящий механизм:
проект убирает то, что задал вендор в `Product` или `Machine`, и потребитель видит своё умолчание.
Снятые ключи едут списком и при чтении разворачиваются обратно в `ключ → null` — ровно ту форму,
которую слияние уже понимает.

**«Настроек активного документа» в API нет намеренно.** Единственный вход — `For(Document)`, а
`Document` в этом процессе достаётся из двух мест, и оба уже за нужной дверью: `IRevitSession`
(выдаётся только коду внутри пампа, то есть на API-потоке) и параметр события или команды. Оба
отказа, которые иначе ловились бы проверками — «не тот поток» и «документа нет», — просто не
выражаются в коде.

**Читается лениво, при первом вопросе, а не на `DocumentOpened`:** большинство сессий не спросят ни
одной проектной настройки, а `DocumentOpened` на 2024 приходится на самое дорогое место старта.
Кэш ключуется самим `Document` (`Equals`/`GetHashCode` документированы), запись убирается на
**`DocumentClosing`** — у `DocumentClosedEventArgs` только `int DocumentId`, документа там уже нет
(проверено по метаданным).

> **Работа с интерфейсом не делается внутри чужой операции.** Проба переключала вкладку ленты
> прямо в `DocumentOpened` — то есть посреди открытия модели, — и на загруженной машине это
> вылезло модальным «Остановить выполнение данной операции?». Переключение уехало в памп, и время
> в логе показывает, за что: раньше оно случалось через 5 мс после открытия документа, теперь —
> через 10 с, когда Revit освободился. Памп существует ровно для такой работы.
>
> **Отдельно про бюджеты, чтобы не спутать нагрузку с дефектом.** В том же заходе модель на 2024
> открывалась **две минуты** против обычных 17 секунд — после трёх прогонов Revit подряд. Это не
> отказ: 300 с у ожидания документа не запас, а рабочий минимум, и при повторении такого замера
> поднимать надо бюджет.

> **Проверка, которая пишет в модель, обязана откатываться.** Запись делает документ изменённым, и
> Revit спрашивает про сохранение на выходе — модальное окно в прогоне, которого никто не видит.
> Проба оборачивает запись в `TransactionGroup` и откатывает его: `RollBack` отменяет уже
> закоммиченные транзакции внутри группы, поэтому продакшн-путь записи проверяется **как есть**, а
> не подменяется чем-то, что прогон делает иначе, чем продукт.

#### Слоистая конфигурация с диска — сделана и измерена

Три каталога, в каждом до трёх файлов по возрастанию частности. Позже прочитанное побеждает,
и порядок читается предложением: **что мы поставили → что говорит машина → что говорит
пользователь → что говорит окружение этого процесса**.

| Слой | Каталог | Кто пишет |
|---|---|---|
| `Product` | рядом со сборкой (для add-in — его `Lib`) | установщик; переписывается следующей установкой |
| `Machine` | `%ProgramData%\BHS` | администратор, один ответ на всю машину |
| `User` | `%AppData%\BHS` | сам пользователь |
| `Process` | переменные `BHS_*` | запускающий |

Имена внутри каталога: `appsettings.json` → `appsettings.<сторона>.json` →
`appsettings.revit<год>.json`. Сторона — `revit` или `winside`; файл по году читает только
Revit-side. Итого девять файлов плюс окружение; для Win-side — шесть плюс окружение.
Переменная `BHS_LAUNCH__SHUTDOWNTIMEOUT` становится ключом `Launch:ShutdownTimeout`: двойное
подчёркивание вместо двоеточия, которого в имени переменной быть не может.

**Каталог вендора — `BHS`, не привязанный к Revit.** Обе стороны обязаны прийти к одному файлу,
а одна из них про Revit не знает. На этой машине `%AppData%\BHS` раньше держал `App.WinSide` от
старого решения `..\BHS`; каталог вычищен, и дальше он наш.

**Формат — JSON, читатель свой.** Причина в разделе про `Microsoft.Extensions.*`: пакет
`Microsoft.Extensions.Configuration.Json` стоит 17 сборок и 9 полифиллов на `net48`, а бросать
в общий AppDomain `System.Text.Json` — напрашиваться на ту же историю, что с `System.Memory`.
Принимаются комментарии `//` и `/* */` и висячая запятая: эти файлы пишет человек. Вложенность
склеивается двоеточием, массивы индексируются по порядку, числа и `true`/`false` сохраняют
написание, а явный `null` (и пустой объект) **сохраняется как значение** — это и есть способ
для глубокого слоя снять то, что задал мелкий. Ключ, заданный дважды **в одном файле**, — ошибка;
между файлами — ровно то, ради чего слои и нужны.

**Значение, которое есть и не читается, отвергается, а не подменяется умолчанием.** Отсутствие
настройки — обычное дело, и умолчание там ответ; `"24O"` там, где ждут число, — опечатка, и тихо
поехать на умолчании значит спрятать её на месяц.

**Перезагрузка работает.** Каждый файл под наблюдением, с задержкой 250 мс (редакторы пишут файл
не один раз: пишут, обрезают, переименовывают, трогают время). Слой, чьего каталога ещё нет, не
наблюдается — `FileSystemWatcher` нельзя навести на отсутствующий каталог, а создавать пустые
папки в `%ProgramData%` на каждом старте мы не будем; такой слой подхватится на следующем запуске.
Ошибка чтения при перезагрузке **записывается, а не бросается**: бросок пришёл бы с потока таймера,
где ловить некому, и внутри Revit это чужая сессия.

Проверено вживую: на работающем `BHS.WinSide` правка `%AppData%\BHS\appsettings.json` меняет
`Launch:ShutdownTimeout` без перезапуска — `--settings` показывает новое значение.

Модель из BHS сохраняется: Revit-side объявляет публикуемые типы опций (`PublishConfiguration<T>()`),
Win-side потребляет их как обычный `IConfigurationSource` наравне с `appsettings.json`.
Что изменено против оригинала:

- **полезная нагрузка — `map<string, string>`, а не JSON-строка.** Это не аппроксимация:
  `Microsoft.Extensions.Configuration` сам является плоским хранилищем `string → string` с ключами
  через `:`, поэтому `map` — точное представление `IConfigurationProvider.Data`. Уходит двойная
  сериализация и уходит `Newtonsoft.Json` из конфигурационного пути. `MapField<,>` в ревитовской
  `Google.Protobuf` 3.23.1 присутствует (53 члена) — проверено.
  Оговорка: типизируется транспорт, но не пространство ключей — дисциплина версионирования нужна
  всё равно, просто теперь она про ключи;
- **перезагрузка вместо снимка.** В BHS конфигурация вычислялась один раз в конструкторе.
  Правильно — стриминговый `WatchConfiguration`, поверх которого свой `IConfigurationProvider`
  на каждый снимок заполняет `Data` и вызывает `OnReload()`; дальше `IOptionsMonitor<T>` и change
  tokens работают сами, как с `reloadOnChange: true` у файлового провайдера. **Сделано и
  проверено**: `PeerConfigurationSource` добавляется в `ConfigurationBuilder` наравне с
  `appsettings.json`, а проба доказывает сквозной путь — публикация в дочернем процессе доезжает
  до `IConfiguration` родителя и поднимает change token.

> **Следствие:** стриминг нужен **с первого дня**, а не когда вернётся OData. Это единственный
> аргумент за готовую RPC-библиотеку, который после отсрочки OData выглядел слабым, — и он
> восстановлен.

> **Статус.** Выбор сделан по статическому анализу метаданных и **подтверждён живым обменом**.
> `BHS.Transport.Probe` — 65 проверок, зелёных на `net48`, `net8.0-windows` и `net10.0-windows`,
> то есть на всех трёх рантаймах диапазона:
>
> - унарный вызов, `map<string,string>` в обе стороны, **серверный стриминг**;
> - все три слоя доверия: дескриптор канала, опознание процесса и учётной записи на том конце,
>   отказ рукопожатия при чужой или неназванной версии контракта;
> - **обмен между двумя процессами** — родитель поднимает дочерний, опознаёт его по PID через
>   `GetNamedPipeServerProcessId`, стримит и гасит через `Shutdown`;
> - отказ по дедлайну на отсутствующем сервере и обнаружение перечислением;
> - **сквозной поток конфигурации**: публикация в дочернем процессе доезжает до `IConfiguration`
>   родителя, поднимает change token и разбирается по секциям;
> - **реестр экземпляров**: ожидание по токену, проверка пира против его же канала, запись
>   непроверенного и пришедшего без токена, восстановление перечислением с отказом тому, кто не
>   назвал контракт, подметание, уход по смерти процесса — последнее в двухпроцессной части,
>   где процесс настоящий;
> - **настройки с диска**: формат (вложенность, массивы, комментарии, висячая запятая, экранирование,
>   отказ дублю ключа и незакавыченному тексту), слои и порядок имён для обеих сторон, снятие
>   значения явным `null`, отказ нечитаемому значению, ошибка разбора как запись вместо броска,
>   перезагрузка по изменению файла, слой окружения — и, главное, **оба источника в одном
>   builder'е**: файлы плюс то, что публикует пир.
>
> Стриминг на `net48` и был главным вопросом: обычный gRPC на .NET Framework его не умеет вовсе.
> Отдельно измерено, что опознание процесса **не тревожит сервер** — оно стоит отдельного
> подключения, потому что библиотека не отдаёт хэндл канала.
>
> **Обмен внутри процесса Revit измерен на всех четырёх версиях** — пробой `BHS.Revit.Probe` и
> прогоном `BHS.Revit.Probe.Runner`, и везде зелёный. Сервер живёт внутри процесса Revit,
> опознание процесса по каналу совпадает с запущенным PID, `GetConfiguration` отвечает изнутри,
> стриминговый `WatchConfiguration` доводит изменение до `IConfiguration` родителя и поднимает
> change token, секции разбираются, Revit закрывается изнутри `PostableCommand.ExitRevit`.
> С добавлением реестра прогон вдобавок подтверждает против живого Revit, что пир проверяется
> против собственного канала, что пустой реестр находит работающий экземпляр перечислением и не
> объявляет его своим, и что запись уходит сама, когда процесс закрылся. **Проверено на всех
> четырёх версиях.**
>
> **Число проверок зависит от режима, и это стоит называть.** Обычный прогон — **212** (53 на
> версию); с `--with-model` и `BHS_PROBE_SHOW_TAB=1`, то есть с открытой моделью и нажатой
> кнопкой, — **288**. Записанное здесь раньше «288» относилось ко второму, чего сказано не было;
> теперь прогон печатает своё число сам, и пол под ним — 45 на версию.
>
> Прогон `BHS.Revit.Probe.Runner` — **288 проверок**, зелёных на всех четырёх версиях подряд,
> полностью без человека. С добавлением настроек он вдобавок доказывает то, что снаружи Revit
> проверить нельзя: **слой `Product` разрешается в собственную папку add-in, а не в каталог
> установки Revit**. Очевидные способы её найти — entry-сборка и `AppContext.BaseDirectory` —
> оба называют каталог Revit, потому что entry-сборка здесь `Revit.exe`.
>
> С логированием он вдобавок проверяет то, что тоже проверяется только изнутри: файл пишется,
> находится снаружи по PID, заголовок называет фактически загруженные сборки, записи помечены
> потоком, и **приёмник journal подключился** — а он требует `ControlledApplication`, обязан
> присоединиться в `OnStartup`, и всё его правило (писать только с API-потока) вне процесса
> с этим потоком смысла не имеет.
>
> | Revit | Регистрация после запуска | Закрытие изнутри | Сборок в процессе |
> |---|---|---|---|
> | 2024 | 13,7–30,5 с | 38,1–**208,5** с | 303 |
> | 2025 | 12,5–24,4 с | 5,7–7,7 с | 342 |
> | 2026 | 24,6–30,3 с | 36,8–59,8 с | 625 |
> | 2027 | 16,4–22,4 с | 31,6–69,7 с | 616 |
>
> Разброс — между заходами на одной и той же машине; бюджеты стоит считать по верхней границе.
>
> **Диалог «Остановить выполнение данной операции?» — это блокировка, а не следствие.** Пока он
> висит, `OnShutdown` не выполняется и `PostCommand` бессилен; снаружи это неотличимо от медленного
> выхода или от потерянного запроса, и оба раза я поставил именно эти диагнозы, и оба раза неверно.
> Различил журнал Revit:
>
> ```
> Jrn.Data "ProgressCancelled", 1, 0
> TaskDialog "Остановить выполнение данной операции?"   Id : TaskDialog_Stop_Operation
> ```
>
> Рядом в журнале — `loadLatestVersion` и `TrustedUtility::readStreams`, то есть Revit **грузил
> модель**, и кто-то отменил прогресс. Esc никто не нажимал; единственное, что трогает интерфейс, —
> переключение вкладки ленты в пробе. Перенос его на памп не помог: **Revit сообщает о простое
> между фазами загрузки, которая ещё идёт**.
>
> Отсюда правило: **работа с интерфейсом в прогоне без человека — по явному запросу, а не по
> умолчанию.** Переключение вкладки и нажатие кнопки убраны за `BHS_PROBE_SHOW_TAB=1`. Обычный
> прогон их не делает и говорит об этом вслух — `not asked - set BHS_PROBE_SHOW_TAB=1 for both`,
> потому что пропущенная проверка, о которой молчат, читается как пройденная.
>
> И правило для диагностики, купленное двумя неверными выводами подряд: **прежде чем поднимать
> таймаут, спроси, началась ли вообще та работа, которую ты ждёшь.** Ответ есть в логе add-in
> (выполнялся ли `OnShutdown`) и в журнале Revit (что он делал в этот момент) — а не в секундомере.

> **208,5 с на 2024 были предупреждением, и второй замер пришёл.** Revit 2026, только что
> потративший 105 с на открытие модели, не успел выйти за 240 с и был убит. Документ при этом был
> чист — окна про сохранение не было, — то есть дело в самом выходе, а не в диалоге. Обе машины шли
> пятым Revit за час: именно это условие прогон создаёт себе сам.
>
> **Бюджет поднят с 240 до 360 с**, как и было условлено. Убийство посреди штатного выхода уже один
> раз выглядело отказом, которым не было; повторять это, имея два замера у потолка, значило бы
> сознательно держать ложные срабатывания.
>
> **Базовая отметка от 2026-09-03**, снятая после реестра экземпляров и подписывания: все четыре
> версии проходятся подряд, полностью без человека, при **удалённых** записях в `CodeSigning` —
> доверие несёт только подпись. Это и есть проверка того, что подписывание действительно
> заменяет реестровый путь, а не просто добавляется к нему.
>
> На 2024 это стало возможно только после форка `GrpcDotNetNamedPipes` — см. раздел про
> `System.Memory`. Под чужой учётной записью по-прежнему не проверено.
>
> Попутно измерено: вызов приходит **не на API-поток** Revit, поэтому всё, что трогает Revit API,
> обязано идти через `ExternalEvent`; add-in живёт в `DefaultDomain`, если не попросить изоляцию;
> регистрация доезжает **вдвое раньше**, чем появляется пригодное главное окно, так что готовность
> правильно ждать по каналу, а не по окнам.
>
> **Запуск с моделью измерен.** `--with-model` у прогона берёт копию модели из `testdata` (по одной
> на версию; копию, потому что открытие файла старого выпуска его обновляет и переписывает) и
> проверяет, что проба сообщила открытый документ.
>
> | Revit | Регистрация | Документ после регистрации | Закрытие | Сборок в процессе |
> |---|---|---|---|---|
> | 2024 | 15,4–17,8 с | **17,0–19,3 с** | 21,2–33,0 с | 678 |
> | 2025 | 13,0–13,8 с | **8,0 с** | 3,4–4,3 с | 445 |

> Последняя колонка — с открытой моделью, и она вдвое больше, чем без неё (303/342/625/616 выше по
> тексту): **открытие документа само по себе удваивает состав процесса**. Метрика «сколько сборок
> может привезти кто-то ещё» тем самым считается по загруженному Revit, а не по пустому.
>
> То есть двухэтапная регистрация — не теория: **документ приезжает через 8–112 с после того, как
> add-in уже зарегистрировался**, и бюджеты у этих ожиданий разные. Первый заход с бюджетом 120 с
> провалился, хотя модель открывалась нормально, — она открылась на 3 минуты 51 секунду позже
> регистрации.
>
> **Бюджет открытия поднят до 15 минут, и снова по замеру, а не по догадке.** Пятиминутного не
> хватило на 2024 при пятом за час запуске Revit: прогон отрапортовал «документ не приехал», а лог
> add-in датирует `document opened` через **696 с** после регистрации. То есть работа началась, шла
> и закончилась — короче машины оказался бюджет.
>
> Это уже третий замер одного семейства: 208,5 с на закрытие, 105 с на открытие, теперь 696 с. Все
> три — на машине, гонявшей Revit подряд, и все три сначала выглядели отказами. **Правило то же и
> стоит его повторить: прежде чем поднимать таймаут, спроси, началась ли ожидаемая работа.** Ответ
> в логе add-in и в журнале Revit, не в секундомере. Каждый раз она начиналась.
>
> **И сразу следом контроль, который стоит знать: повтор той же проверки на той же машине и том же
> коде дал 16,3 с.** Разброс **в 43 раза** на одном замере. Отсюда практический вывод про все числа
> в этих таблицах: они годятся как порядок величины и как нижняя граница, но **бюджет, настроенный
> по удачному прогону, — это ложное срабатывание, отложенное на потом**. Считать по верхней границе,
> и верхнюю границу не занижать.
>
> **И это стоило модального диалога.** Когда бюджет истёк, прогон попросил Revit закрыться —
> `ExitRevit` встал в очередь внешних событий **посреди открытия модели**, и Revit спросил
> «Остановить выполнение данной операции?». Снаружи на такой вопрос ответить нечем; ровно та же
> беда, что с диалогом неподписанного add-in, только с другой стороны. Прогон теперь **не просит
> закрыться**, если документ так и не приехал, — он убивает процесс и говорит почему.

> **Диалог вернулся, и на этот раз известно, чем кончилось.** Прогон 2026-09-07 с `--with-model`
> **и** `BHS_PROBE_SHOW_TAB=1` снова показал «Остановить выполнение данной операции?» — то есть
> сочетание «открыть модель + тронуть ленту» воспроизводит мину, а не случайно её однажды задело.
> Владелец ответил **No**, операция продолжилась, прогон дошёл до конца: **288 проверок зелёных,
> ни одного таймаута, самое долгое ожидание — 36 с на регистрацию**.
>
> Отсюда два вывода, и второй важнее.
>
> **Диалог не обязательно фатален** — прежде он выглядел блокировкой, из-за которой прогон
> проваливался; при ответе «No» Revit продолжает работу и всё проходит. Значит прежние отказы
> объясняются не самим диалогом, а тем, что **отвечать было некому**.
>
> **И потому этот режим не является автоматическим.** Зелёные 288 получены с человеком у экрана.
> Прогон, оставленный без присмотра в этом режиме, встанет на диалоге и будет неотличим от
> зависшего — ровно тот случай, который дважды диагностировали неверно. Полностью без человека
> надёжен обычный режим (**212** проверок); `--with-model` с нажатием кнопки — режим, который
> **запускают при ком-то**, и предупреждать об этом надо заранее: он занимает машину десятками
> минут и выкидывает модальное окно поверх чужой работы.

> **Бюджет закрытия складывается из двух ожиданий.** Внешнее событие с командой выхода лежит в
> очереди, пока Revit не освободится: на 2024 это 25 с после запроса, потому что проба
> регистрируется задолго до готовности. Только потом начинается сам выход. Отсюда 240 с по
> умолчанию — при меньшем бюджете прогон не «не закрывает» Revit, а убивает его посреди штатного
> выхода.

> **`PostCommand` — это заявка, а не вызов, и Revit вправе её не принять.** Правило общее, и оно
> куплено дважды. Сначала на выходе: `ExitRevit` уходил, и ничего не происходило. Потом на нажатии
> кнопки — запрос ушёл через полсекунды после того, как вкладку ленты вывели вперёд, и пропал так же
> бесследно: ни строки в логе, ни ошибки, ни исключения. Единственный признак — что ожидаемая работа
> не началась.
>
> Отсюда: всё, что построено на `PostCommand`, обязано **повторяться до подтверждённого результата**,
> а не посылаться один раз с последующим ожиданием. И то, и другое сделано именно так — прогон
> повторяет запрос внутри цикла ожидания, а не поднимает таймаут.

## Хост add-in: точка входа и композиция

Слой между «Revit позвал `OnStartup`» и «фича работает». Живёт в `BHS.Revit.Host`, контракты —
в `BHS.Revit.Abstractions`. Форма унаследована от `..\BHS` и `..\BimHouseApp`: тонкий
`IExternalApplication`, который Revit находит по манифесту, собирает состав и передаёт управление.
Не унаследовано то, **чем** он собирал.

**Издание пишет один класс и больше ничего:**

```csharp
public sealed class BhsElectricalApplication : RevitAddInApplication
{
    protected override Guid AddInId => new("...");   // тот же, что в манифесте: это ключ реестра
    protected override string Name => "BHS Electrical";
}
```

### Две формы add-in, и обе первого класса

Add-in в виде чистого `IExternalCommand` поддерживается, но это не основной случай. Основной —
**приложение с собственной лентой**, и приложений у Revit два вида:

```
RevitAddInHost                вся композиция; ни одного типа из RevitAPIUI внутри
├── RevitAddInApplication     IExternalApplication   — плюс памп, внешнее событие, лента
└── RevitDbAddInApplication   IExternalDBApplication — всё то же, кроме пампа
```

Проверено по метаданным всех четырёх версий: `IExternalDBApplication` объявлен в **`RevitAPI`**,
не в `RevitAPIUI`; оба его метода принимают `ControlledApplication`; результат —
`ExternalDBApplicationResult`, у которого **только `Succeeded` и `Failed`**, то есть нет даже
третьего ответа, какой есть у `Result`.

> **Граница между формами — не «интерфейс или нет», а есть ли мост обратно на API-поток.** Всё
> остальное работает в обеих: настройки с диска, логирование вместе с приёмником journal (ему нужен
> ровно `ControlledApplication`), реестр хостов, настройки модели, модули. Нет только
> `ExternalEvent` — он в `RevitAPIUI`, — а с ним пампа.

Поэтому база носит всю композицию и **не называет ни одного типа из `RevitAPIUI`**. Один класс,
реализующий оба интерфейса сразу, отвергнут по той же причине: само упоминание привязало бы
DB-форму к сборке, отсутствие которой и есть смысл этой формы.

**`IFeatureServices` теряет `Pump`, а `IUiFeatureServices : IFeatureServices` его добавляет.**
Три отвергнутых варианта, и каждый хуже по-своему:

| Вариант | Почему нет |
|---|---|
| `Pump` как nullable | `services.Pump!` появится при первом же предупреждении компилятора, а дальше `NullReferenceException`, не называющий причины. И платит за это каждая UI-фича, чтобы DB-форма могла существовать |
| памп в DB-хосте, выполняющий делегат на вызывающем потоке | **самый опасный.** Памп существует ровно для вызывающих не с API-потока — измерено, вызов из канала всегда приходит с потока пула. Это не отказ, а порча, всплывающая в другом месте и позже |
| памп в DB-хосте, который бросает | Несовпадение формы видно только запуском внутри Revit. При отдельном интерфейсе фича пишет `IUiFeatureServices` в собственной сигнатуре, и большинство ошибок ловит компилятор |

Разрез окупился в тот же час: компилятор нашёл **два** места в пробе, где `.Pump` брался у общей
поверхности. Ни одно не было бы найдено иначе.

`IFeatureModule.Start(IFeatureServices)` не меняется — модуль, которому нужен API-поток, пишет
`services.Ui()` и получает **предложение**, а не `InvalidCastException`. `IFeatureCommand` наоборот
принимает `IUiFeatureServices` сразу: команду достигают нажатием, значит у её хоста интерфейс есть
по определению.

**`IRevitContext` берёт `ControlledApplication`** — то, что есть у обеих форм; UI-форма передаёт
`application.ControlledApplication`, который она и так достаёт первой строкой.

> **`IsSessionReady` переименован в `IsInitialized`, и это не косметика — это исправление, купленное
> замером.** Пара поднималась из `ControlledApplication.ApplicationInitialized`, а называлась «есть
> ли сессия». Предполагалось, что в DB-форме она вечно `false`, потому что сессии там нет никогда;
> проверять это никто не собирался — «очевидно».
>
> Измерено: **`ApplicationInitialized` приходит и в `DBApplication`-add-in** (подтверждено на 2024
> и 2025). То есть событие общее для обеих форм, имя обещало интерфейс, а механизм не обещал ничего
> подобного. Отсюда две правки сразу: имя называет то, что произошло, а **подписывается база**, а не
> UI-форма. За UI-формой осталось единственное, что действительно её: взять `UIApplication`.
>
> Порядок здесь важнее вывода. Проверка была заведена **нотой, а не утверждением** — именно потому,
> что ответа не знал никто, а «всегда зелёная проверка» хуже отсутствующей. Утверждением она стала
> после ответа, и вместе с ответом сменилось имя члена. Переименуй я сначала, замер подтверждал бы
> моё же предположение.

> **Сборки не расщепляются, и довод за расщепление назван недостаточным явно.** Пакет
> `Nice3point.Revit.Api.RevitAPIUI` — reference-only, в вывод не попадает, поэтому по метрике
> «сколько сборок может привезти кто-то ещё» ссылка стоит ноль. Остаётся единственный довод — не
> тронуть UI-тип там, где `RevitAPIUI` физически нет; но `RevitAPIUI.dll` лежит в каталоге установки
> **всех четырёх** версий, а Design Automation и `RevitCoreConsole` работают на том же каталоге.
> Пока не появится хост, в путях поиска которого его нет, это гипотеза о среде, которой у нас нет.
> И опасна там была бы не ссылка, а вызов: падало бы `ExternalEvent.Create`, а от этого расщепление
> сборок не защищает — защищает то, что в DB-хосте его никто не зовёт.

### Манифест перечисляет add-in'ы, а не описывает один

Издание, у которого есть и лента, и часть, не нуждающаяся в окне, объявляет **две** записи в одном
`.addin`-файле — формат Revit это и предполагает. SDK этого не умел: `GenerateRevitAddIn` принимал
`ITaskItem` (скаляр), и второй `RevitAddIn` в проекте давал ошибку преобразования списка. Теперь
принимает массив и группирует по выходному файлу.

Каждой записи — **свой `AddInId`**: по нему Revit ведёт доверие и изоляцию, по нему же ключуется
`HostRegistry`. Дубликат сделал бы один из хостов недостижимым так, что это выглядело бы как «не
запустился». SDK отвергает дубль ошибкой сборки.

Попутно вскрылись две вещи, которых по коду видно не было, и обе стоили бы отладки:

- **`ManifestSettings` — свойство файла, а не add-in'а.** Он сосед `<AddIn>` под `<RevitAddIns>`,
  значит две записи в одном файле делят изоляцию. Для двух половин одного издания это правильно и
  есть; генерация расщеплена на «элемент add-in'а» и «настройки файла», а расхождение между
  записями — ошибка сборки, а не молча выигравшая первая.
- **`%(RevitAddIn.AddInName)` внутри `PropertyGroup` батчит весь таргет публикации**, а тот
  начинается с `RemoveDir` корня публикации. Два манифеста — второй проход снёс бы результат
  первого. Папка публикации теперь берётся из `$(RevitPackageName)`: она свойство **пакета**, а не
  add-in'а — один проект строит одну сборку и публикует одну папку, сколько бы записей внутри ни
  объявил. Попутно исчезло расхождение с деплоем, который `RevitPackageName` использовал всегда, —
  невидимое ровно до тех пор, пока отображаемое имя совпадало с именем сборки. Заодно отображаемое
  имя перестало называть каталог: в нём может быть что угодно.

### DB-форма измерена, а не объявлена

Проба везёт **обе половины одним манифестом и одной сборкой**: `ProbeApplication` — `Application`,
`ProbeDbApplication` — `DBApplication`. Обычный интерактивный Revit грузит второй манифест так же
охотно, как первый, поэтому DB-форма проверяется **тем же прогоном**, без Design Automation и без
отдельного захода.

Что доказано на всех четырёх версиях:

- DB-add-in поднимает тот же хост, ключуется собственным `AddInId`, и в реестре **два разных
  объекта**, а не один, ответивший дважды (проверяется поиском по обоим ключам и сравнением ссылок,
  а не счётчиком — счётчик прошёл бы и при двойной регистрации одного хоста);
- один и тот же реестр отдаёт UI-хосту услуги **с** пампом, а DB-хосту — **без**;
- обе формы вызваны Revit'ом **на одном и том же API-потоке**;
- настройки с диска читаются там же, модуль стартует, и хост **сузил ему настройки до собственной
  секции** — то есть `For(moduleId)` не задел, а рабочий путь;
- просьба об API-потоке отвергается **предложением**, содержащим и «no user interface», и
  «DBApplication»;
- `OnShutdown` DB-формы выполняется и останавливает свой модуль — видно только в файле лога, потому
  что канала к этому моменту уже нет.

**Чего проба намеренно не делает: второго сервера канала.** Два сервера в одном процессе подрались
бы за одно имя. Это ограничение пробы, а не формы: транспорт к UI отношения не имеет, и настоящее
DB-издание свой канал держать может.

**Настройки модели из DB-формы не проверяются, и причина названа.** Extensible Storage от UI не
зависит, а второй вход за `Document` — параметр события — работает и там; но единственный триггер,
доступный DB-половине пробы, это `DocumentOpened`, то есть запись **посреди загрузки модели** —
ровно то место, которое уже один раз дало «Остановить выполнение данной операции?». Повторять
доказанное ценой известной мины незачем.

### Издание: четыре файла, и ни одного пятого

Издание — это add-in, который Revit грузит. Первое сделано, `source/BHS.FullEdition`, и состоит
ровно из:

| Файл | Что в нём |
|---|---|
| `FullEditionApplication.cs` | два члена: `AddInId` и `Name` |
| `CollectCablingEntryPoint.cs` | пустой наследник `CommandEntryPoint<T>` с `[Transaction]` |
| `NeedsDocument.cs` | класс доступности |
| `.csproj` | манифест add-in и объявление ленты |

**Всё, что издание пишет дважды, принадлежит базе.** Композицию несёт хост, работу — фича;
издание, которое выросло, — признак, что что-то лежит не там.

**Стоимость измерена: десять сборок на `net48`, все наши, все с префиксом `BHS.`, и ни одного
полифилла BCL.** По метрике «сколько сборок может привезти кто-то ещё» издание стоит **ноль**.
Канала в нём нет, поэтому `Grpc.Core.Api` и `Google.Protobuf` в AppDomain Revit не едут вовсе —
в отличие от пробы, которая их везёт по своей природе.

### Наши собственные сборки сталкиваются друг с другом — измерено первым же нажатием

Первое нажатие первой команды дало:

```
MissingMethodException: Method not found:
  'Double BHS.Settings.SettingsValues.Real(BHS.Settings.ISettings, System.String, Double)'
```

Метод был на месте — в копии, лежавшей в папке издания. Но проба была развёрнута двадцатью
минутами раньше, до его появления, и **её** `BHS.Settings.dll` заняла простое имя в общем AppDomain
первой. Издание связалось с чужой копией нашей же сборки.

**Это тот самый механизм, вокруг которого построен весь этот файл, — но впервые не с чужой
сборкой, а со своей.** Два add-in везут одни и те же сборки фреймворка под одними и теми же
простыми именами, и загружается ровно одна копия каждой.

> **Решение владельца, и оно закрывает вопрос о версионировании целиком: в продакшене издание
> всегда одно.** Переход на другое издание деинсталлирует прежнее; конфигурация мигрирует, где
> это возможно. Значит два наших add-in рядом — состояние **разработки**, а в поле оно означает
> неполную деинсталляцию, то есть само по себе дефект.
>
> Отсюда: **`AssemblyVersion` остаётся `major.minor`**, и вопрос «морозить ли по мажору ради
> изданий разных выпусков» снят — таких пар не бывает. А проверка при старте меняет адресата:
> она защищает не заказчика от несовместимых изданий, а нас от собственной несинхронной выкладки,
> и заодно ловит остатки прежнего издания после неудачного удаления. Отсюда же и уровень `ERR`
> остаётся оправданным: сработав в поле, она говорит о настоящем дефекте установки.
>
> **Миграция конфигурации при этом уже устроена, а не ждёт работы.** Слои `Machine` и `User`
> лежат в `%ProgramData%\BHS` и `%AppData%\BHS` — каталог **вендорский, не издания**, — поэтому
> переживают удаление сами собой. Настройки модели ключуются GUID схемы Extensible Storage, тоже
> не изданием. Заменяется ровно слой `Product`, который лежит рядом со сборкой и является тем,
> что мы поставляем: он и обязан приходить с новой установкой.
>
> Единственное, что действительно привязано к изданию, — `AddInId`: по нему Revit ведёт доверие,
> и новое издание попросит его заново. Подписанная сборка снимает и это, потому что доверие тогда
> на издателе.

**Случаев два, и они кончаются по-разному. Оба измерены нарочно поставленным расхождением.**

| | одинаковая версия, разное содержимое | разные версии |
|---|---|---|
| когда бывает | **разработка**: одно развёртывание обновили, другое нет | **неполная деинсталляция**: папка или манифест прежнего издания пережили переход |
| Revit 2024, `net48` | побеждает загрузившийся первым → `MissingMethodException` при первом же вызове того, чего в чужой копии нет | оба add-in **стартуют** (`API_SUCCESS`), второй работает против чужого фреймворка |
| Revit 2026, .NET | то же самое | **add-in не стартует вовсе** — `API_ERROR`: загрузчик резолвит по простому имени, и запрос более высокой версии не удовлетворяется ничем |

Правая нижняя клетка — тот же отказ, что описан выше для `Microsoft.Extensions.Configuration.Abstractions`
на Revit 2026, только теперь с нашими сборками по обе стороны.

**Ответ — проверка при старте, `FrameworkAssemblyCheck`.** Хост сравнивает `FileVersion` каждой
загруженной сборки с префиксом `BHS.` со своей копией на диске: разные версии — `ERR` с обоими
путями и обеими версиями, одинаковые — `INF`, называющая чужой путь. Проверена красной: на Revit
2024 с нарочным расхождением она назвала четыре сборки поимённо.

**Чего она не ловит, и это надо знать: ровно тот случай, который её и породил.** Обе копии были
`0.1.0.0` и различались только содержимым. Версия их не различает, и байты тоже не годятся —
измерено, две сборки неизменённого исходника дают неодинаковые файлы, так что проверка на хеше
кричала бы на каждом обычном развёртывании и через неделю перестала бы читаться. Поэтому случай
одинаковых версий даёт `INF`, называющую чужую папку и то, что она означает, — это и есть подсказка
человеку, у которого пропал метод.

**И на оси .NET проверка не выполняется вовсе, когда версии разошлись**: хост, в котором она живёт,
не запускается. Громкость там обеспечивает сам Revit — `API_ERROR` в журнале.

> **Попутно найдено и починено, с тем же корнем.** Слой `Product` слоистых настроек резолвился
> относительно `BHS.Settings.dll`, то есть относительно копии, выигравшей простое имя. Пока add-in
> был один, комментарий «продуктовый слой разрешается в собственную папку» был верен; со вторым
> издание молча читало бы `appsettings.json` **из чужой папки**. Ни исключения, ни симптома. Теперь
> каталог передаётся явно и берётся от сборки самого издания (`GetType().Assembly`), потому что все
> прочие способы называют не то: `AppContext.BaseDirectory` и entry-сборка дают каталог установки
> Revit, а всё, что резолвится от сборки фреймворка, — папку победителя.

> Изоляция здесь не помощник: на 2024 и 2025 её нет вовсе. В примерах Revit 2027 есть
> `<PublicAssemblies>` и `<DependsOnContext>` — механизм, которым два изолированных контекста делят
> сборку намеренно; **не измерено**, и до тех пор проверка при старте нужна в любом случае.

### Что нашлось только исполнением: коннекторы и резервные цепи

Два дефекта и один шум, ни один из которых не давал ни анализ метаданных, ни компиляция под четыре
фреймворка.

**`Connector.Origin` существует только у физических коннекторов.** `ConnectorType` — набор флагов:
`End = 1`, `Curve = 2`, **`Logical = 4`**, `Surface = 16`, `Physical = 19` (то есть
`End | Curve | Surface`). Значения совпадают на 2024, 2026 и 2027. Логический коннектор — это то,
как Revit описывает связь, **у которой нет места**: щит питает цепь, они соединены в электрической
системе, и ни одна точка на щите этим соединением не является. Чтение `Origin` у такого бросает.

Проверяется флаг, а не ловится исключение: ловля заодно проглотила бы тот день, когда Revit бросит
по другой причине, а дыра в сети после этого выглядит как чужая ошибка моделирования.

**Отсюда поправка к самому себе.** Здесь было записано, что брать точку вставки щита — ошибка
предшественника, а правильный ответ `BaseEquipmentConnector`. На живой модели этот коннектор часто
логический, и точка вставки оказывается всем, что щит предлагает. Лестница теперь такая:

```
коннектор цепи, если у него есть место
  → любой физический электрический коннектор элемента
  → центр габаритного контейнера          решение владельца
  → точка вставки
```

**Центр габарита перед точкой вставки, а не вместо неё.** Точка вставки — это где семейство
разместили, она может лежать в углу или вне тела; центр протяжённости всегда внутри предмета. Это
догадка и помечена догадкой: габарит выровнен по осям модели и покрывает элемент целиком, так что у
шинопровода или длинного короба центр может оказаться далеко от любой клеммы. Та же ступень добавлена
носителям — фитинг без коннекторов и без положения раньше выпадал молча.

**`CircuitType` различает `Circuit`, `Spare` и `Space`.** Первый прогон по настоящей модели доложил
семь «цепей без достижимых устройств» — почти наверняка семь обычных резервных мест в щите.
Считаются отдельно, показываются в основной части ответа, а не в разделе «что не так», и пишутся в
лог как `Info`.

> **Отчёт, который кричит на нормальное, перестают читать — и тогда он не может рассказать и о
> ненормальном.** То же правило, что у `RVTREF006`, применённое к пользователю вместо разработчика.

### Что заменено против предшественников, и почему

| В `..\BHS` / `..\BimHouseApp` | Здесь | Причина |
|---|---|---|
| Generic Host (`HostBuilder`) | нет | тянет `Microsoft.Extensions.*` — под полным запретом в Revit-side, `RVTREF005`. Разбор в разделе про конфликт сборок |
| DI-контейнер | конструкторы вручную | состав хоста — десяток объектов, известных на этапе компиляции; контейнер здесь покупает только сборку, которую нельзя везти |
| статик, держащий построенный хост | `HostRegistry`, ключ — `AddInId` | на 2024 все add-in в одном AppDomain, и два наших издания делят одну `BHS.Revit.Host.dll`. Статик «я тут один» — ровно то, на чём погорело предыдущее поколение. Реестр аддитивен и идемпотентен, как `LogRouter.Default` |
| ожидание старта хоста в `OnStartup` | ничего не блокирует | `OnStartup` каждого add-in сериализован с чужими, а холодный Revit и без нас стоит до 70 с. Предшественник тратил там 30 с на ожидание собственного хоста и ещё 4 на заставку |

**В `OnStartup` не блокирует ничто.** Ни ожидания канала, ни `Task.Run(...).Wait(n)`, ни обхода
каталогов, ни `AppDomain.AssemblyResolve`. Настройки читаются с диска (это файловые операции, они
дёшевы и от порядка запуска не зависят), лог поднимается, реестр заполняется — и всё.

**Исключение поймано, а не проброшено.** Исключение, ушедшее из `OnStartup`, — это модальное окно
на машине, перед которой никого нет. Несостоявшийся старт — строка в логе и отсутствующая кнопка,
но `Result.Succeeded` всё равно.

### Памп: единственный мост на API-поток

Вызов из канала приходит **не на API-поток** — измерено, и это самая частая ошибка проекта. Поэтому
всё, что трогает Revit API, идёт через `IRevitApiPump` (`Post`, `PostAsync<T>`) поверх одного
`ExternalEvent`, созданного в `OnStartup` — единственном месте, где для этого есть законный
контекст.

`IRevitSession` (с `UIApplication` внутри) **выдаётся только коду, уже исполняемому внутри пампа**.
Не хранится нигде: сессия, отданная наружу, — это сессия, использованная не с того потока.
`IRevitContext` намеренно `UIApplication` не содержит — на `UIControlledApplication` нет члена,
который бы его вернул, ни на одной из четырёх версий (проверено по метаданным).

### Модальное окно: что внутри него работает — измерено на всех четырёх версиях

Утверждение «`ExternalEvent`, поднятый из модального окна, не сработает никогда, потому что Revit не
доходит до `Idling`, пока окно открыто» стояло в файле проекта `BHS.MEP.Cabling.Routing` как
обоснование его формы — и **ни разу не проверялось**. Проверено пробой: окно настоящее, поднято
пампом на API-потоке, то есть стоит ровно там, где стоит модальная команда, вызвавшая `ShowDialog`.

| | 2024 | 2025 | 2026 | 2027 |
|---|---|---|---|---|
| памп работает, пока окно открыто | **нет** | нет | нет | нет |
| работа из очереди выполняется при закрытии | да, в ту же сотую долю секунды | да | да | да |
| Revit API отвечает на чтение изнутри окна | **да** | да | да | да |
| …и после того, как возобновился `await` | **да** | да | да | да |
| `await` возобновляется, на API-потоке | **да**, 0,3–0,5 с | да | да | да |
| контекст внутри окна | `DispatcherSynchronizationContext` | то же | то же | то же |
| контекст снаружи окна | `WindowsFormsSynchronizationContext` | то же | то же | то же |

**Отсюда форма команды, и она лучше той, что предполагалась.** Сбор — синхронно, прямо в диалоге:
чтения пампа не требуют, команда уже стоит в законном контексте API. Расчёт — на фоновом потоке.
Применение — **в том же продолжении, не закрывая окна**. Альтернатива, отдать применение пампу,
означала бы, что окно результатов исчезает раньше, чем сделана работа, которую оно описывает:
памп не выполняется, пока диалог не закрыт.

**Работа, положенная в памп при открытом окне, выполняется ровно в момент закрытия**, а не со
следующего простоя: памп разбирает всю очередь одним проходом `Execute`, и ожидание длится не до
`Idling`, а до раскрутки стека.

**Контекст снаружи окна — WinForms, и это неожиданность, стоящая записи.** На API-потоке внутри
внешнего события действует `WindowsFormsSynchronizationContext`; диспетчерский появляется только
внутри диалога. Значит `await`, взятый в команде **до** показа окна, возобновляется другим
механизмом, чем взятый внутри, — знать это надо до того, как на их одинаковости что-то построено.

> **Не измерено, и это названо, чтобы не сошло за решённое: транзакция.** Всё перечисленное —
> чтения. Применение маршрута это запись, а воротами модификации служит `Transaction.Start`, а не
> сам вызов; успешное чтение за неё не отвечает. Замер уедет вместе с фазой применения — настоящей
> записью, откатываемой группой, той самой формы, что уже применена в проверке схемы: так
> проверяется продакшн-путь, а не его репетиция.

#### Фаза расчёта сделана, и форма оказалась ровно предсказанной

Команда `Route cables` в `BHS.FullEdition`: читает синхронно на API-потоке, ищет на фоновом с живой
полосой, докладывает. **В модель не пишет ничего** — применение уедет со своим замером транзакции.

- **`RouteRun`** — что говорит о себе один прогон: счётчики по причинам, отказы в порядке, в котором
  их пробовали, и сравнение длин. Живёт рядом с поиском, а не во вью-модели: вью-модель, решающая
  «что пошло не так», была бы вторым местом, где это решается, и через месяц два места разошлись бы.
- **Длину, которую Revit сообщает сам, несёт `RouteResult`, а не сумма рядом.** Первая версия
  сравнивала наши сорок с ревитовскими пятьюдесятью пятью — разница, которая целиком есть недостающие
  пятнадцать, и первый увидевший сообщил бы о ней как о дефекте поиска. Едущая вместе пара из разных
  множеств взяться не может. Проверка на это **показана красной** до того, как ей поверили.
- **Читать нельзя отменить, и полоса говорит об этом неопределённостью.** Один проход по коллекторам
  Revit, места, где можно остановиться, в нём нет. Кнопка «Стоп», ничего не делающая ровно ту
  половину ожидания, которая на большой модели длиннее, хуже отсутствующей.
- **Окно не отпускает себя, пока поиск идёт.** Кнопка «Закрыть» выключена, но крестик и Alt+F4 не
  спрашивают: первая просьба отменяет, а закрывается окно, когда поиск действительно встал. Иначе
  команда вернулась бы, оставив поиск работать против документа, — форма падения, которое приезжает
  минутами позже и называет другое место.

#### Первый полный прогон по настоящей модели, и что он нашёл

**54 цепи из 55, и пятьдесят пятая — не отказ инструмента.** `id 574892` оказался потребителем
**смежного раздела** (ОВиК), к которому проектировщик забыл проложить несущие элементы — причём **в
обоих разделах**. То есть `NoCarrierNear` сработал верно, и нашёл то, ради чего такой инструмент и
существует: пропуск на стыке дисциплин, который человеческая проверка не заметила.

Это первое свидетельство ценности, а не работоспособности, и стоит различать. Работоспособность
показали 54 маршрута; ценность — одна строка, назвавшая элемент, которого не хватает.

**Заодно окупилась правка адреса, сделанная в тот же день.** Строка отказа несла имя типа, номер
цепи и `[574892]` — идентификатор, который принимает ревитовский «Выбрать по ID». Владельцу хватило
его, чтобы опознать элемент в модели за один взгляд. До правки на этом месте стояло имя типа,
одинаковое у сотен розеток, и та же находка потребовала бы поиска руками.

> **Следствие для будущего предупреждения о коробках:** устройство смежного раздела без несущих
> элементов — находка, которую надо показывать заметно, а не прятать среди прочего. Оно отличается
> от «коробки нет» тем, что это ошибка модели, а не выбор способа подключения.

#### Спуск к устройству: два типа подключения, и в коде сегодня один

**Записано со слов владельца, а не измерено, и различать это обязательно.** Всё в этом файле,
помеченное как измеренное, получено запуском; здесь — предметное знание, которое из API не
достаётся никаким замером.

Устройство подключается к магистрали **двумя способами**:

| | что происходит | сколько раз считается спуск |
|---|---|---|
| **разрез на терминале** | кабель двойной: приходит вниз к устройству, и от него уходит новый | **дважды** на каждом промежуточном |
| **разрез на ответвительной коробке** | кабель одинарный: магистраль режется в коробке, к устройству идёт отвод | **один раз**, плюс отвод от коробки |

**Сегодня реализован только первый, и он попал в код допущением.** `Router.Route` складывает плечи,
каждое плечо платит подход на входе и на выходе, поэтому спуск к промежуточному устройству
считается дважды. Для разреза на терминале это верно; для разреза на коробке — завышение примерно
вдвое на всех промежуточных.

**Цена ошибки названа числом:** на первой настоящей модели спуски составили 472 485 мм из 1 235 289,
то есть **38 % итога**. Выбор типа двигает заголовочное число примерно на пятую часть.

> **Как это допущение сюда попало — и почему это отдельный урок.** Оно не просто не обсуждалось: оно
> было **закреплено комментарием как обоснование** — «кабель не летает, он идёт поперёк и вниз». То
> есть утверждение об инженерной практике заняло место, отведённое измерению, и выглядело оттуда так
> же авторитетно, как соседние строки, купленные запуском Revit. Спрошено было уже после того, как
> число стояло на экране.
>
> **Правило, выведенное владельцем и записанное здесь: допущения об устройстве модели обсуждаются
> до того, как на них построен код.** Различать надо не «уверен/не уверен», а род вопроса: что
> достаётся из API — измеряется; что относится к тому, как на самом деле прокладывают, — спрашивается.
> Отказ такого рода не падает и не краснеет: он выдаёт правдоподобное число, из которого кто-то
> сделает кабельный журнал.

**Ответвительной коробки в модели может не быть**, даже там, где разводка именно такая. Поэтому
владелец просит не молчаливую догадку, а **предупреждение или предложение**. Отсюда форма, которую
предстоит сделать: настройка типа, поиск коробок там, где они смоделированы, и названное
предупреждение там, где тип говорит «коробка должна быть», а её нет.

**Ответы владельца, 2026-09-09.**

- **Тип — свойство цепи, наследуемое с панели.** Не проекта и не вида устройства: панель
  электроснабжения делает все свои цепи через коробки, а цепи на панели RS485 идут через терминал.
  То есть значение читается у цепи, при отсутствии — у её панели, при отсутствии — из настроек.
- **Коробка бывает разных категорий, но чаще это фитинг несущего элемента.** Следствие сильное и
  приятное: `OST_CableTrayFitting` и `OST_ConduitFitting` мы **уже собираем**, значит коробка чаще
  всего уже является узлом сети, и маршрут через неё уже проходит. Не хватает не сбора, а
  **опознания** — какой из фитингов коробка. Это `CarrierCatalogue` ещё раз: список, который ведёт
  пользователь, а не константа в коде.
- **Где ставить коробку, которой нет, — это задача оптимизации трассы, и её надо исследовать.**
  Владелец относит её к помощи проектировщику: инструмент не подставляет число молча, а предлагает
  расстановку. Значит это отдельная работа, а не ветка в `if`.
- **Предупреждение — на цепь**, и адресатов у него два: уведомление на модальном диалоге и механизм
  `FailureDefinition`.

**Два адресата, потому что механизмы работают в разных местах — проверено, а не предположено.**
`Document.PostFailure` вызывается **внутри транзакции**: так в примере Autodesk `ErrorHandling`
(транзакция, `PostFailure`, коммит) и так в коде владельца — транзакция открыта строкой 100
`CalcCableLengthRouteModel`, предупреждения кладутся строками 215–224. Фаза расчёта ничего не пишет
и транзакции не имеет, значит в этот механизм попасть не может вовсе. Отсюда разрез:

| Фаза | Чем говорит | Почему так |
|---|---|---|
| расчёт | строка на модальном диалоге | транзакции нет, `PostFailure` недоступен |
| применение | `FailureMessage` в открытой транзакции | Revit показывает их сам, и они остаются в списке предупреждений модели |

**И здесь же нашёлся первый потребитель `FailureDefinition`** — той самой регистрации, которая
стоит шагом 1 в порядке работ и была отложена до потребителя. Заодно снимается сомнение «механизм
с нулём потребителей»: он есть, и он этот.

**Что теперь блокирует работу — не вопрос к модели, а порядок.** Тип живёт на цепи, то есть в
параметре; параметр наш, то есть общий (shared); а схема параметров в этом файле числится
предстоящей работой и не сделана. Значит фаза применения и режим коробки упираются в неё, а не
друг в друга.

**Длины форматирует Revit, а не мы, — и это первый настоящий ответ на отложенный вопрос о единицах.**
`UnitFormatUtils.Format(units, SpecTypeId.Length, value, false)` — четырёхаргументная форма, она есть
на всех четырёх (проверено по примерам Autodesk для 2024 и 2027, а не по памяти: этот API менял форму
в 2021). Наше число стоит на экране рядом с ревитовским, а точность, разделители и подавление нулей
выбрал пользователь и держит `Units` документа. Число, расходящееся с ревитовским на одном экране,
хуже отсутствующего — ему верят, пока не проверят.

Форматирование добирается до экрана делегатом, потому что вью-модель на чистой оси и типа `Document`
не видит. Захватывается **`Units`, а не документ**: это не утверждение, что форматирование
безпоточное — вызов остаётся ревитовским и делается только там, где он законен, то есть на UI-потоке
внутри модального окна, который и есть API-поток.

### Схема параметров: что измерено, и развилка, которую решать владельцу

Узкое место сразу для двух работ — тип подключения живёт на цепи, то есть в параметре, и фаза
применения пишет длину и маршрут туда же. Разбор сделан по предшественнику и по метаданным; ни
строки кода ещё нет, потому что развилка ниже меняет форму механизма.

**Измерено: API одинаков на всех четырёх.** `ExternalDefinitionCreationOptions(string, ForgeTypeId)`,
`Application.Create.NewInstanceBinding(CategorySet)`, `Document.ParameterBindings.Insert`,
`Application.SharedParametersFilename`, `OpenSharedParameterFile()` — примеры Autodesk для 2024 и
2027 совпадают дословно. Расхождений нет, `#if` не нужен.

> **И это упрощение против предшественника.** `CableLengthRouteSharedParameters` в `..\BHS` несёт
> `#if RVT2019||…||RVT2023` для `BuiltInParameterGroup` против `GroupTypeId` — и обрывается на
> `#error Unknown Revit version`, потому что 2027 в нём не предусмотрен. Наш диапазон начинается с
> 2024, где `GroupTypeId` уже есть везде: двадцать одна директива условной компиляции исчезает,
> не будучи написанной.

**У предшественника уже есть 21 общий параметр с зафиксированными GUID** —
`BhCtCableLength`, `BhCtCableMass`, `BhCtCircuitRefs`, `BhCtSkipRouting` и другие, — привязанных к
`OST_ElectricalCircuit` и к четырём категориям носителей, с группами `GroupTypeId.ElectricalEngineering`,
`.ElectricalCirculating`, `.Data`, `.General`.

**И файл общих параметров у него пользовательский.** `SharedParametersTools` только **открывает**
текущий (`OpenSharedParameterFile()`) и ищет в нём определения по GUID; `SharedParametersFilename`
не подменяется никогда. То есть параметры принадлежат стандарту заказчика, а инструмент проверяет,
что они там есть, и привязывает их к категориям.

#### Развилка решена владельцем: свои GUID, свой файл

- **GUID новые.** Не переиспользуем предшественниковы: чистый лист.
- **Файл свой, с временной подменой.** И это не отступление от правила «не трогать глобальное
  состояние», а признание, что третьего пути нет: `OpenSharedParameterFile()` открывает **текущий**
  файл, так что создать своё определение можно только выставив `SharedParametersFilename`.
- **Образец у владельца уже есть и он правильный.** `SharedParameterScheme` в `..\BHS` запоминает
  прежний путь, ставит свой, и восстанавливает **в `finally`** — то есть при любом исключении путь
  возвращается. Повторяем эту форму.

> **Одно улучшение против образца, и оно про единственный отказ, который `finally` не покрывает.**
> `finally` не выполняется, когда процесс умирает: Revit убит, упал, снят по таймауту прогоном. Тогда
> у пользователя остаётся наш путь вместо его. Лечится дёшево: **записать прежний путь в настройки до
> подмены** и на следующем старте, увидев там свой, вернуть чужой. Окно опасности из «навсегда»
> превращается в «до следующего запуска».

#### Развилка, и обе стороны имеют цену

| | пользовательский файл, как у предшественника | свой файл с временной подменой |
|---|---|---|
| настройка у заказчика | нужна: файл поставить, Revit на него навести | не нужна |
| глобальное состояние Revit | **не трогаем** | `SharedParametersFilename` подменяется и восстанавливается |
| если мы упали посередине | нечему падать | путь к чужому файлу потерян |
| параметры в стандарте заказчика | да, они его | наши, рядом с его |

Третьего пути нет: `OpenSharedParameterFile()` открывает **текущий** файл, а чтобы открыть свой,
надо выставить `SharedParametersFilename`. Подмена — единственный способ создать определение самим.

Позиция этого файла склоняется к первому столбцу: он согласуется с отказом от
`RegisterFailuresProcessor` и `OverrideResult` — не забирать у процесса того, что принадлежит всем.
Но это решение владельца, а не вывод из метаданных.

**Вопросы, на которые ответа нет:**

- **GUID — переиспользовать предшественниковы или завести свои?** Переиспользование значит, что
  модели, обработанные прежним инструментом, совместимы сразу и мигрировать нечего. Свои значат
  чистый лист и два параллельных набора в одной модели.
- **Файл — чей?** Столбец из таблицы выше.
**Где живёт тип подключения — вопрос был задан невнятно, вот он заново.** Речь именно о вашем
различении **один кабель или два**: разрез на терминале (двойной) против разреза на ответвительной
коробке (одинарный). Я искал, нет ли у предшественника готового места под это, и его нет:
`BhCtConduitInstallationType` читается **с типа** трубы или фитинга, то есть это способ монтажа
носителя, а не способ подключения устройства; `BhCtCableInstallationTypeLength` на цепи — разбивка
длины по способу монтажа. Ось соседняя, вопрос другой.

Значит параметр наш, новый, **на цепи** — решение владельца, — и форма его следует из ответа про
наследование: один общий параметр, привязанный и к `OST_ElectricalCircuit`, и к категории панелей;
читается у цепи, при пустом значении — у её панели, при пустом и там — из настроек.

**И к нему нужен алгоритм автоматического определения, с возможностью пользователя вмешаться.**
Основание для алгоритма у Revit есть своё: `ElectricalSystem.SystemType` — тип системы цепи, и он
ровно про то различие, которое владелец назвал примером («панель электроснабжения против RS485»).
`ElectricalSystemType.PowerCircuit` встречается в примерах Autodesk и для 2024, и для 2027;
остальные значения перечисления вычитать из метаданных при реализации, а не по памяти.

> **Правка пользователя не должна переживаться расчётом — это главное требование, а не деталь.**
> Инструмент, затирающий выбор человека при следующем прогоне, перестают запускать. Форма, которая
> сохраняет правку **по построению**, а не по дисциплине: **заполнять только пустое**. Тогда
> затереть чужое значение физически нечем.
>
> Цена — пересчёт становится невидим: пользователь не понимает, почему тип не изменился. Лечится
> двумя вещами, обе дешёвые: прогон говорит, **сколько заполнил и сколько оставил как есть**, и
> существует явное действие «определить заново», которое очищает и заполняет. Альтернатива —
> второй параметр «кто задал значение» — дороже и всё равно не умеет отличить правку человека от
> нашей записи.

### Виртуальные узлы: замечание владельца вскрыло уже существующий дефект

Владелец: «в Revit возможно соединение несущих элементов без фитинга, и возможно под это нам нужны
виртуальные узлы графа». Замечание верное, и при проверке оказалось, что дефект того же корня
**уже есть в коде**, независимо от фитингов.

**Связность у нас по концам — намеренно.** `Touches` сравнивает терминалы носителей, а не тела:
«лоток, проходящий метром выше другого, не стык, как бы близко он ни шёл». Это правило спасает от
ложных стыков и стоит его сохранить.

**Но подход устройства к магистрали спрашивает то же самое, а не должен.** `Router.Reachable`
меряет расстояние от устройства **до терминалов** носителя:

```csharp
foreach (var at in node.Terminals)
    distance = Math.Min(distance, Approach(terminal.At, at, options));
```

Розетка под серединой двадцатиметрового лотка отстоит от **ближайшего конца** на десять метров —
при `MaxApproach` в три метра этот лоток для неё не существует. А если и попадёт в бюджет, длина
спуска посчитается до конца лотка, а не до точки над устройством.

> **Насколько это испортило измеренный результат — неизвестно, и это надо сказать прямо.** 54 цепи
> из 55 прошли, значит на этой модели сегменты короткие и ближайший конец обычно близко. Дефект
> systematic, его величина — нет; мерить придётся на модели.

**И здесь же ответ на «где ставить коробку, которой нет».** Точка, в которой кабель покидает
магистраль, — это проекция устройства на носитель, то есть ровно тот виртуальный узел. Три вопроса
оказались одним:

| вопрос | чего требует |
|---|---|
| соединение носителей без фитинга | узел в точке стыка, которой не соответствует элемент |
| подход устройства к середине прогона | узел в точке проекции устройства на носитель |
| место отсутствующей ответвительной коробки | тот же узел, названный по-другому |

**Коробка не режет носитель — и это переводит виртуальный узел из «возможно понадобится» в
основание.** Решение владельца: коробка ставится в желаемые координаты, не разрывая несущий
элемент; ставить ли настоящую — решает проектировщик, и он может сказать расчёту «без
дополнительных коробок». Значит расчёт элементов не размещает, а **называет координату**, и эта
координата и есть виртуальный узел. Настоящая коробка, если поставлена, побеждает вычисленную точку.

**Цена, которую надо назвать до того, как это будет написано: частичный проход носителя.** Сегодня
вход в носитель стоит его **длины целиком** — так сделано намеренно, и проба это стережёт: без
этого маршрут, вошедший и вышедший в одном лотке, не платил бы за него вовсе, и двадцатиметровый
лоток стоил бы столько же, сколько двадцатичетырёхметровая труба. Врезка в середину означает, что
пройдена часть, и seeding Дейкстры придётся считать от точки, а не от узла. Это настоящая работа, а
не правка одной строки, и переписывать она будет тот же участок, который проба уже накрыла.

**«Без дополнительных коробок» — свойство проекта, и дом у него уже есть.** Решение владельца:
не предлагать новых, считать по существующим; управляется через интерфейс. Значит это **не**
параметр на цепи, а настройка модельного слоя — та самая цепочка `Product → Machine → Model →
Process` с префиксом `Model:`, которая сделана и измерена. Заводить под неё параметр было бы вторым
механизмом для того, для чего уже есть первый.

Смысл для длины прямой: в режиме коробки отвод считается **от ближайшей существующей коробки**, как
бы далеко она ни была; расчёт не придумывает точку, потому что его об этом попросили не делать.
Устройство, у которого коробки в досягаемости нет вовсе, — предупреждение на цепь.

**Что надо измерить, а не предположить:**

- где на самом деле стоят коннекторы при соединении без фитинга — совпадают ли концы двух сегментов
  (тогда близость их уже соединяет и виртуальный узел не нужен) или расходятся;
- бывает ли в Revit врезка **в середину** прогона без фитинга — у лотка коннекторы только на концах,
  так что это может быть невыразимо, и тогда случай отпадает;
- насколько велика разница между «до ближайшего конца» и «до проекции» на настоящей модели —
  считается тем же прогоном, если посчитать обе величины и показать разницу; это дешевле, чем
  писать частичный проход и потом выяснять, что он ничего не изменил.

Первые два требуют кейса в модели; владелец такие создаёт. **Третье сделано:** `ApproachStudy`
считает обе величины на каждом прогоне и показывает разницу на экране.

**Замер устроен грубой силой намеренно, и это само по себе часть ответа.** Пространственный индекс
подшивает носитель под его **терминалы**, поэтому двадцатиметровый лоток, середина которого над
устройством, лежит в ячейках далеко и индексом найден не будет — то есть замер через индекс мерил бы
индекс, а не расстояние. Отсюда следствие для настоящей правки: носители придётся подшивать **по
длине**, а не только по концам. Для нескольких сотен носителей полный перебор честен и дёшев, и
формой будущего решения он не является.

Строка появляется только при расхождении: совпадение — это ноль новых достижимых терминалов и
меньше десятой доли фута разницы на всю модель, то есть «сегменты коротки, и их концы там же, где
кабель уходит». Всё, что больше, — довод за работу.

Проверка на сам замер: лоток от 0 до 20, розетка под серединой в футе под ним. По концам это
одиннадцать футов по осям и вне досягаемости; вдоль лотка — один фут. **Показана красной** правдоподобно
неверным ответом (ближайший терминал для всего): четыре проверки из семи падают.

#### Результат замера на настоящей модели, и что он решает

| | сумма спусков | охват |
|---|---|---|
| до концов носителей — как считается сегодня | **100 338 мм** | 184 из 185 |
| до ближайшей точки вдоль носителя | **65 287 мм** | 184 из 185 |

**Достижимость не меняется вовсе.** Ни один терминал не переходит из «носителя нет» в «носитель
есть»; сто восемьдесят пятый — потребитель ОВиК, к которому носителей нет ни при каком измерении.
Значит врезка в середину прогона на этой модели **ничего не спасает**, и половина ожидаемой выгоды
не подтвердилась.

**Зато спуски завышены на 35 %**, а самый длинный сокращается на 1086 мм.

> **Два числа со спусками нельзя перемножать, и это стоит сказать прямо.** В заголовке экрана
> 472 485 мм, в замере 100 338 — величины разные. Замер берёт **лучший подход на каждый терминал по
> одному разу**; маршрут платит подход на входе и выходе **каждого плеча** и к тому носителю, который
> реально выбран, а не к ближайшему. 35 % — это доля от нижней границы; насколько упадёт заголовочное
> число, скажет только переписанный маршрутизатор.

**И замер поднял вопрос, которого в нём не было, — а ответ владельца превратил его в цену.**
«Ближайшая точка вдоль носителя» предполагает, что кабель покидает носитель где угодно. Для лотка
так; **труба — закрытый канал**, и кабель выходит на фитинге или на конце. Владелец: «да, кабель не
может выйти из трубы, но для этого и будет рекомендация по коробке — или должна быть выбрана
ближайшая, или предупреждение».

Замерено третьей величиной, и раскол вышел резким:

| | сумма | разница |
|---|---|---|
| до концов носителей — сегодня | 100 338 мм | — |
| врезка вдоль **лотка**, труба только на стыках | 89 109 мм | **−11 229** |
| врезка вдоль чего угодно | 65 287 мм | ещё **−23 822** |

**Две трети «выигрыша» принадлежали трубам**, то есть тому, чего физически не бывает. Законная
выгода от проекции — **11 %**, а не 35.

**Оставшиеся 24 % — не «нельзя», а «можно, если поставить коробку».** Это и есть цена рекомендации
по коробкам, выраженная в тех же миллиметрах, что и всё остальное на экране, — довод, у которого
есть число, вместо довода из принципа. Экран говорит именно так: сколько бесплатно, сколько ждёт
коробок.

> **Замер был неверен, и проба это показала.** Каждая величина суммировалась **по своему** множеству
> достижимых терминалов, а разность двух сумм по разным множествам — не экономия: в пробе терминал,
> недостижимый по концам и достижимый вдоль лотка, дал **отрицательную** экономию. Теперь все три
> суммы берутся по терминалам, которые видят **все** измерения, и это число (`Comparable`) стоит
> рядом; кто сколько достаёт по отдельности — счётчики, они выше. **Показано красным** возвратом к
> прежнему учёту: две проверки падают.
>
> Урок общий и уже знакомый этому файлу: **сравнение двух величин обязано брать их на одном
> множестве**, иначе оно сравнивает состав множеств, а выглядит как сравнение величин.

### Часть решения — наши собственные семейства

**Решение владельца, и оно меняет ответ на вопрос про опознание коробок.** Начиная отсюда мы везём
**специально разработанные семейства**; требования к ним вырабатываются совместно, реализует их
владелец. Спецификации лежат в `docs/families/`, по файлу на семейство.

- **Авторская версия — Revit 2024.** Старший Revit загружает семейство младшего, обратное неверно;
  нижняя граница диапазона поддержки и есть версия авторства. Редкие исключения возможны и должны
  называться в спецификации явно.
- **Опознаётся семейство нашим общим параметром типа, а не именем.** Имя переименуют, и код
  замолчит — «не нашли» и «нет такого» с этой стороны неотличимы.
- **Отсюда связь схемы параметров с семействами:** автор добавляет параметры в семейство **из того
  же файла, который мы поставляем**, иначе GUID не совпадут при внешне правильном имени.
- **Загрузка семейства — модификация**, значит фаза применения. Каталог резолвится **от сборки
  издания**, как и слой `Product`, и по той же измеренной причине.

Так снимается вопрос «по чему узнавать коробку»: не по категории и не по эвристике, а по нашему
параметру на нашем семействе, которое к тому же остаётся фитингом несущего элемента — то есть
попадает в сеть само собой и стыкуется коннекторами, все из которых мы теперь читаем.

### Модули объявляются, а не сканируются

`Modules` — список, который пишет издание, а не каталог, который хост обходит. Сканирование значит
загрузку, а на 2024 загруженная сборка держит своё простое имя в общем AppDomain до конца сессии —
включая фичи, которых никто не касался. Кнопки приезжают из манифестов, а их сборки грузятся при
нажатии; это и измерено в разделе про ленту.

## Лента: измеренное ограничение на класс доступности

`IExternalCommandAvailability` **обязан лежать в той же сборке, что и команда.** Справка Revit API
говорит «should share the same assembly», и разница между советом и требованием стоила бы половины
объёма генератора ленты — поэтому её измерили, а не вычитали второй раз.

Кнопка, у которой `AvailabilityClassName` называет тип в соседней сборке, даёт **модальное окно
пользователю**:

```
System.TypeLoadException при создании экземпляра 'BHS.Revit.Common.ForeignAvailability'
Could not load type 'BHS.Revit.Common.ForeignAvailability'
  from assembly 'BHS.Revit.Probe, Version=1.0.0.0, ...'
```

Механизм виден в самом сообщении: Revit берёт `AssemblyName` **с кнопки** и разрешает имя класса
внутри неё. Тип из другой сборки не находится никогда, и отказ **не тихий** — не серая кнопка, а
диалог. Значит фреймворк не может поставлять предикаты доступности сам; генератор обязан класть
класс доступности в сборку издания, рядом с диспетчером команды.

### Ленивая кнопка через дженерик: работает на 2026, отвергается на 2024

Предшественник `..\BHS` закрывал границу «Revit создаёт тип по имени класса» **без генератора** —
дженерик-точкой входа:

```csharp
var entry = typeof(ExternalCommandEntryPoint<BomKeyCommand>);
new PushButtonData(name, text, entry.Assembly.Location, entry.FullName)
{
    AvailabilityClassName = typeof(ExternalCommandAvailabilityEntryPoint<...>).FullName,
};
```

Класс на команду материализует система типов. Побочно решается и ограничение выше: у
сконструированного генерика `Assembly` — это сборка, где объявлено определение, поэтому команда и
класс доступности оказываются в сборке хоста **автоматически**.

Цена там была — **отказ от ленивости**: `typeof(EntryPoint<Foo>)` при построении ленты загружает
сборку `Foo`. Но имя — всего лишь строка, и её можно собрать из манифеста, ничего не загружая.
Проверено пробой:

| Revit | Строка принята | Сборка feature'а при построенной ленте | Команда выполнилась |
|---|---|---|---|
| 2026 | **да** | **не загружена** | **да**, и только тогда сборка загрузилась |
| 2024 | **нет** | не загружена | нет — модальное окно |

На 2024 Revit сообщает «в сборке надстройки не найден класс» и показывает диалог; в журнале видно,
что строка дошла до него дословно. Пробовались обе формы — короткая `[[Тип, Сборка]]` и полностью
квалифицированная с версией и токеном; **отвергнуты обе**.

**Выход нашёлся в предыдущем поколении, и он лучше обоих вариантов.** В `..\BHS` манифест
приложения называет **простое** имя, а дженерик спрятан в базовый тип:

```csharp
public class ApplicationEntryPoint : ExternalUiAppEntryPoint<Application, ApplicationConfigurator> { }
```

То же годится и для команд:

```csharp
// в сборке хоста - вся логика, написанная один раз
public class CommandEntryPoint<TCommand> : IExternalCommand where TCommand : ... { ... }

// в сборке издания - то, что кладёт генератор: одна строка на команду
public sealed class FooCommandEntryPoint : CommandEntryPoint<FooCommand> { }
```

- имя **простое**, значит Revit разрешает его на всех четырёх версиях;
- класс лежит **в сборке издания**, значит ограничение по `AvailabilityClassName` выполнено;
- логика написана один раз в дженерик-базе, а не размножена генератором;
- загрузка типов в CLR ленива, поэтому базовый тип — а с ним сборка feature'а — разрешается лишь
  когда Revit создаёт экземпляр, то есть при нажатии.

Генератор остаётся, но выпускает **пустые наследники**, а не тела диспетчеров.

> **Вывод: пока Revit 2024 в поддержке, дженерик-имя в манифесте и на кнопке недоступно.** Заодно
> объясняется, почему у `..\BHS` это работало шесть лет: он звал `typeof(...)` первым, то есть тип
> уже существовал в загруженной сборке — Revit его лишь находил, а не конструировал. Что именно не
> умеет 2024 — конструировать генерик по имени или находить тип в незагруженной сборке — дальше не
> разделялось: на решение это не влияет.

### Схема измерена целиком, на всех четырёх версиях

Проба возит подставную фичу **отдельной сборкой** (`BHS.Revit.Probe.Feature`) именно затем, чтобы
у вопроса «загружена или нет» был ответ; прогон нажимает кнопку изнутри Revit и спрашивает, что
вышло.

| Revit | Простое имя принято | Сборка фичи при построенной ленте | Команда выполнилась | `ActiveAddInId` в команде |
|---|---|---|---|---|
| 2024 | **да** | **не загружена** | да | наш `AddInId` |
| 2025 | да | не загружена | да | наш `AddInId` |
| 2026 | да | не загружена | да | наш `AddInId` |
| 2027 | да | не загружена | да | наш `AddInId` |

Три вывода, и каждый до этого был предположением:

- **ленивость — свойство CLR, и она действительно работает.** Сборка фичи не загружена, пока лента
  стоит, и загружается ровно при нажатии. На 2024 это и есть цена вопроса: там все add-in в одном
  AppDomain, и загруженная сборка держит своё простое имя до конца сессии — включая фичи, которых
  никто не касался;
- **реестр хостов находится из команды**, созданной Revit'ом по строке, и находится **по
  `AddInId`**: `ExternalCommandData.Application.ActiveAddInId` внутри команды называет тот add-in,
  чья кнопка нажата. Это было документировано и ни разу не измерено, а от этого зависит вся
  композиция — команда не может получить услуги иначе, потому что конструирует её Revit;
- **`[Transaction]` читается с созданного типа**, то есть с наследника, а не с команды фичи —
  ту Revit не видит вовсе. Проверено отказом: без атрибута на наследнике Revit показывает модальное
  окно «нет атрибута Transaction». Режим транзакции — свойство каждой команды, едет в манифесте,
  и **умолчания у него нет**: команда, чей режим никто не назвал, — это кнопка, падающая при
  нажатии.

  > **Поправка к самому себе, и она про порядок утверждения и замера.** Здесь стояло «поставить
  > атрибут на базу выглядело бы аккуратно и не дало бы ничего». Это не было измерено. Замер по
  > метаданным всех четырёх версий говорит обратное: `TransactionAttribute` объявлен как
  > `[AttributeUsage(AttributeTargets.Class)]` **без единого именованного аргумента**, значит
  > `Inherited` остаётся своим умолчанием `true` — атрибут наследуем в принципе. Спрашивает ли Revit
  > его с `inherit: true`, **не измерено**: единственный замер здесь был про цепочку, где атрибута не
  > было нигде, и про наследование он не говорит ничего.
  >
  > Правило от этого не меняется, но опирается теперь на своё основание, а не на чужое: режим —
  > свойство команды, поэтому объявляется там, где объявлена команда. Унаследованный режим — это
  > режим, которого никто не выбирал. `RVTRIB003` требует атрибут непосредственно **сознательно
  > строже CLR**, и это записано в самой проверке.

> **`typeof` на кнопке отменяет всю ленивость, и компилятор об этом молчит.** Первый заход писал
> имя класса как `typeof(PingCommandEntryPoint).FullName` — ради читаемости. Этого достаточно:
> тип загружается, тянет за собой базовый `CommandEntryPoint<PingCommand>`, а тот — сборку фичи,
> **при построении ленты**. В логе это видно дословно: `feature assembly loaded: True` до единого
> нажатия.
>
> Запретить это в коде нечем — `typeof` здесь совершенно законен, и заметить подмену можно только
> замером. **Это самый сильный из имеющихся доводов за манифест**: дело не в том, что генерировать
> строки удобнее, а в том, что в этом месте `typeof` писать нельзя вообще, и единственный надёжный
> способ его не написать — не иметь такой возможности.

### Лента строится из манифеста

Издание объявляет кнопки в файле проекта, SDK пишет рядом со сборкой `<сборка>.features.json`, хост
читает его на старте и отдаёт Revit **имена классов текстом**:

```xml
<RevitRibbonButton Include="BHS.Probe.Ping">
    <Panel>BHS Probe</Panel>
    <Text>Ping</Text>
    <ClassName>BHS.Revit.Probe.PingCommandEntryPoint</ClassName>
    <AvailabilityClassName>BHS.Revit.Probe.LocalAvailability</AvailabilityClassName>
    <ToolTip>...</ToolTip>
    <Order>2</Order>
</RevitRibbonButton>
```

**Довод за манифест — не удобство генерации, а невозможность написать `typeof`.** Он молча
отменяет ленивость (см. выше), законен с точки зрения компилятора, и заметить его можно только
замером. В пути «манифест → строка → `PushButtonData`» его негде написать.

**Манифест читается тем же читателем, что и слоистые настройки** (`JsonSettings` из `BHS.Settings`:
плоская карта `ключ → строка`, массивы по порядковому номеру). Ноль новых сборок в AppDomain Revit —
`System.Text.Json` Revit не везёт ни в одной версии, значит его не закрепляет никто.

Обязательные метаданные — `Panel`, `Text`, `ClassName`; необязательные — `Tab` (пусто = вкладка
Add-Ins), `ToolTip`, `LongDescription`, `AvailabilityClassName`, `Order`. Задача SDK проверяет то,
что видно по самому item'у: `RVTRIB010` — не хватает обязательного, `RVTRIB011` — две кнопки с одним
именем.

#### Иконки-заглушки: вендорский знак, пока фича не нарисовала свой

Кнопка без изображения — не нейтральная кнопка: Revit рисует ей пустую рамку, и панель из таких
читается как сломанная, а не как незаконченная. Поэтому хост ставит на каждую кнопку знак из логотипа
вендора, а издание, нарисовавшее своё, его перекрывает.

**Два файла, вдвое больше пикселей и вдвое больший объявленный dpi.** У `ButtonData` ровно `Image`
и `LargeImage` — проверено по метаданным 2024 и 2027, причём оба на общей базе, то есть есть у всех
видов кнопок. Значит два слота, и выбирать между вариантами Revit не станет.

#### Что Revit хочет от иконок при 150% и 200% — измерено

**Лента рисует иконку натуральным размером: `Stretch=None`.** Измерено подстановкой файлов на живую
кнопку и чтением визуального дерева ленты с UI-потока:

| Источник | Нарисовано |
|---|---|
| 16px @ 96 dpi | 16 × 16 |
| 32px @ 96 dpi | 32 × 32 |
| 48px @ 96 dpi | 48 × 48 |
| 64px @ 96 dpi | 64 × 64 |

То есть при 96 dpi **больше пикселей даёт больше кнопку, а не резче картинку**. Отсюда и
общеизвестный совет «строго 16 и 32» — он верен ровно для файлов при 96 dpi, и только для них.

**Та же формула даёт выход.** Натуральный размер в WPF — это `пиксели × 96/DpiX`, значит
64 пикселя при 192 dpi занимают **32 единицы**: кнопка та же, пикселей вдвое больше. Проверено:

```
32px@192dpi -> 16.0x16.0     наша малая
64px@192dpi -> 32.0x32.0     наша большая
32px@96dpi  -> 32.0x32.0     контроль: чужая иконка рядом
```

Поэтому едут **32px@192dpi** и **64px@192dpi**. Один файл на слот закрывает все масштабы: при 100%
он даунсэмплится, при 200% ложится пиксель в пиксель, при 150% пересэмплируется из вдвое большего
материала, чем мог бы дать 32-пиксельный.

> **Менять масштаб экрана не понадобилось, и это не увёртка.** Натуральный размер от DPI дисплея не
> зависит вовсе — он свойство файла; число физических пикселей под ним Windows выдаёт сама по
> масштабу. Обе половины арифметики прочитаны из живого Revit: нарисованный размер из визуального
> дерева, коэффициент масштаба из `CompositionTarget.TransformToDevice`. Смена масштаба добавила бы
> только взгляд глазами на резкость.

> **Первый заход этого замера дал противоположный ответ, и виноват был порядок.** Раскладка читалась
> до того, как её попросили: непромеренный бокс равен нулю, фильтр «ширина больше нуля» его отбросил,
> и 32-пиксельная иконка вышла «не нарисована», а 64-пиксельная — «64», потому что её читали уже
> после `UpdateLayout()`. Асимметрия была в моих действиях, а не в ленте. То же правило, что трижды
> сработало на классе доступности: **условие, наступающее асинхронно, надо дождаться, а не прочитать
> один раз** — а здесь ещё и вызвать явно.
>
> Заодно убрано сопоставление по ссылке: лента вправе обернуть или сконвертировать то, что ей дали,
> и сравнение ссылок, которое тихо не совпало, читается как ответ «не нарисовано».

Попутно: `ComponentManager.UseOriginalImageSize` = `False`. То есть кнопка **не** подгоняется под
картинку этим свойством — растягивание отключено в шаблоне ленты, и путать эти две вещи не стоит.

**Вектор не проверялся.** `Image` типизирован как `ImageSource`, то есть `DrawingImage` туда
формально ложится; будет ли лента с ним вести себя так же — отдельный вопрос. Руководство Autodesk
(см. ниже) для SVG вариантов по DPI не требует вовсе, так что вопрос стоит задать, когда появятся
настоящие иконки.

#### Руководство Autodesk по иконкам, и что из него следует

`E:\Development\Revit\Revit 2027.2 SDK\Autodesk Icon Design Guidelines.pdf`, семь страниц.
Существенное:

- размеры десктопных иконок — **32×32 и 16×16** (24×24 только для веба);
- **светлая и тёмная темы, обе**;
- формат — **PNG** для десктопа, SVG для веба;
- **Multi-DPI: пять PNG на каждый размер и тему** — 100, 150, 200, 300, 400 %, «и продукт покажет
  нужный файл при нужном DPI». Для SVG варианты не нужны;
- палитра задана поимённо (Grey/Cyan/Red/Blue/Orange/Purple, по светлому и тёмному варианту),
  композиция — main body + accent + badge/arrow, библиотека готовых бейджей лежит по ссылке
  `IconDesignGuidelinesfor3rdparty.zip`.

**Пять вариантов на размер и тему — это двадцать файлов на иконку, и выбирает из них сам продукт.**
Через публичный API add-in этого механизма нет: у `ButtonData` ровно два слота. То есть измеренный
выше приём — объявить DPI в самом файле — не обход руководства, а тот же выбор, сделанный на нашей
стороне: продукт выбирает файл, мы выбираем метаданные файла.

**Тема — требование, которое я сначала не увидел вовсе.** `UIThemeManager.CurrentTheme` (значения
`Light`/`Dark`) и событие `UIApplication.ThemeChanged` есть на **всех четырёх** версиях — проверено
по метаданным. Оба варианта иконки едут, выбор идёт по теме, а живые кнопки перекрашиваются при
переключении: `Autodesk.Revit.UI.RibbonButton` несёт `Image`/`LargeImage`, так что ленту
перестраивать не нужно. Выбирать один раз на старте было бы неверно — тему переключают среди дня.

Проверено на живом Revit, причём обе ветки исполнились сами собой: на этой машине 2024 и 2026
работают в **тёмной** теме, 2025 и 2027 — в светлой.

> **Руководство поймало дефект, который замер пропустил.** Тёмный вариант иконки вышел байт в байт
> равным светлому, и причина оказалась не в подмене цвета: **`RenderTargetBitmap` трактует координаты
> визуала как DIP и масштабирует их на `dpi/96`**. Логотип рисовался в 64 единицы, а битмап
> запрашивался 64 пикселя при 192 dpi — то есть на выходе была **верхняя левая четверть, увеличенная
> вдвое**. Тёмно-синие полосы логотипа как раз в правом нижнем углу, потому и исчезли.
>
> Проверка внутри Revit при этом была зелёной, и справедливо: она мерила **габарит**, а не
> содержимое. `64px@192dpi -> 32 units` доказывает, что кнопка не выросла, и ровно ничего не говорит
> о том, что на кнопке нарисовано. Верная формула — `units = size × 96/dpi`.
>
> Отсюда правило: **проверка размера — не проверка картинки.** Если результат работы визуальный, на
> него надо посмотреть, а не только измерить.

**Вшиты ресурсами в `BHS.Revit.Host`, а не положены файлами.** Файл рядом со сборкой пришлось бы
искать по пути, проводить через публикацию и деплой, и он пережил бы то, что его породило —
развёртывание копирует и никогда не удаляет. То, что обязано быть всегда, лучше держать внутри
сборки, которой оно нужно. `ImageSource` замораживается: лента строится на API-потоке, а рисуется на
UI-потоке.

Растеризованы из `Resources/PlaceholderIcon.svg` (тот же логотип, что у пакета SDK). Растеризатора на
машине нет ни одного, но пути в SVG — обычный синтаксис, который разбирает `Geometry.Parse`, так что
хватило коротенькой утилиты на WPF: пути и цвета из `style`, общие границы, вписать с отступом,
`RenderTargetBitmap` → PNG.

> **Цена — `UseWPF`, и она передаётся потребителям.** `ImageSource` живёт в `PresentationCore`,
> значит хост объявляет `UseWPF`, а вместе с ним обязано и каждое издание, которое на него ссылается.
> На оси .NET это сразу вылезло как `NETSDK1136`.
>
> Вскрылось, что базовый SDK делает эту проверку **дважды**, а заглушена была одна:
> `_CheckForInvalidWindowsDesktopTargetingConfiguration` ловит проект, попросивший WPF сам, а
> `_CheckForTransitiveWindowsDesktopDependencies` — тот, который лишь сослался на такой проект.
> Причина у обеих одна (платформа `revit`, а не `Windows`), заглушены теперь обе.
>
> **В выводе это не стоит ничего.** `PresentationCore` и соседи лежат в GAC на `net48` и в shared
> framework на оси .NET, а интерфейс самого Revit на них и построен. Измерено: набор сборок в `Lib`
> не изменился, полифиллов на `net48` по-прежнему ровно четыре.

#### Проверки против сборки живут в RefCheck, а не в MSBuild

Два отказа, которые компилятор поймать не может, — это ровно те два модальных диалога, которые
проект уже видел вживую. Проверить их можно только чтением метаданных собранной сборки, и вот здесь
напрашивающееся решение неверно:

> **Задача MSBuild была почти написана и отвергнута.** `System.Reflection.Metadata` на оси
> `net48` — а MSBuild под Visual Studio и Rider именно там — привозит с собой шесть сборок, включая
> `System.Memory`, `System.Buffers` и `Unsafe`, **внутрь процесса сборки**. Это тот же класс
> столкновения, который в этом репозитории стоил форка библиотеки, только этажом ниже. RefCheck —
> обычное .NET-приложение, запускаемое `Exec` в отдельном процессе, где всё это в коробке.

| Код | Что ловит | Как это выглядело бы у пользователя |
|---|---|---|
| `RVTRIB001` | класса нет в сборке | «в сборке надстройки не найден класс» |
| `RVTRIB002` | класс не `IExternalCommand` | отказ при нажатии |
| `RVTRIB003` | нет `[Transaction]` на созданном типе | «Нет атрибута Transaction», при нажатии — возможно через месяцы |
| `RVTRIB004` | класс доступности в другой сборке | `TypeLoadException` модальным окном |
| `RVTRIB005` | класс доступности не `IExternalCommandAvailability` | отказ |

Измерено на всех четырёх версиях: лента строится из манифеста, обе кнопки на месте, и **сборка фичи
не загружена, пока лента стоит**. Проверено подделкой манифеста: каждая из трёх воспроизводимых
находок выдаётся, а чистый манифест проходит — то есть обход цепочки базовых типов **через соседнюю сборку** до `IExternalCommand`
работает, а не просто молчит.

> **RefCheck не был подключён к сборке ни разу.** `build/RefCheck/RefCheck.targets` написан полностью
> и корректно, раздел выше описывает `RVTREF005` как проверку, валящую сборку, — а импорта не
> существовало нигде в дереве. То есть инструмент работал, правило было записано, и всё, что этот
> репозиторий от него знает, получено вручную набранной командой.
>
> Теперь импортируется из `Directory.Build.targets` в корне, под условием `'$(RevitVersion)' != ''`;
> под `build/` стоит пустой щит-двойник к `Directory.Build.props`. Первый же прогон выдал два
> `RVTREF004` про сборки вне watchlist. **Проверка, которую никто не импортирует, — это проверка,
> которую никто не выполняет.**

**Revit спрашивает доступность, только пока вкладка показана** — по два вызова на каждой из
четырёх версий, когда вкладку выводят вперёд, и ноль, когда нет. Первые два захода этого замера
вернули ноль и не доказали ничего: в прогоне без человека вкладку никто не открывает.
Переключение вкладок — не операция Revit API, а свойство WPF-ленты под ним, доступное через
`AdWindows` (`Autodesk.Windows.ComponentManager.Ribbon.ActiveTab`): ни транзакции, ни внешнего
события не нужно, но нужен UI-поток, и `DocumentOpened` на нём.

> **Лента — объект WPF, и спрашивать её можно только с UI-потока.** Проверка «создалась ли наша
> собственная вкладка» была написана как обращение к `AdWindows` из обработчика канала — и падала
> каждый раз: `RibbonControl.get_Tabs()` бросает `InvalidOperationException` («вызывающий поток не
> может получить доступ к данному объекту»), потому что вызов из канала приходит **не на API-поток**.
> Это записано в этом файле в трёх местах, и я всё равно так написал.
>
> Лента при этом была в порядке — в том же логе строкой выше стоит `activated tab 'BHS' holding
> 'Probe feature'`, записанная с пампа. То есть проверка сообщала о себе, а не о ленте.
>
> Лечится не try/catch'ем, а местом: ответ **записывается там, где мы уже на UI-потоке**, и канал
> отдаёт записанное. Отсюда общее правило для таких проверок: **если вопрос про интерфейс, его
> задаёт памп, а канал только докладывает ответ.**
>
> И второй урок, помельче: неудача, логируемая на каждом опросе, дала **полторы сотни строк `ERR`**
> за прогон. Опрашивающая проверка не должна писать в лог на каждой итерации — иначе журнал перестают
> читать ровно тогда, когда он нужен.

> **Три захода на один вопрос, и все три ошибки — в порядке, а не в существе.** Сначала счётчик
> читался, когда Revit ещё не спрашивал; потом проверка стояла до открытия документа; потом
> читалась однократно за полсекунды до самого вызова. Отсюда правило для таких замеров: **условие,
> наступающее асинхронно, надо ждать, а не опрашивать один раз** — и контроль обязателен, иначе
> «не вызвали» неотличимо от «не спросили».

## Объекты, которые настраивает приложение, а использует команда

Целый класс Revit API устроен так: зарегистрировать можно только в `OnStartup`, а нужен он потом,
в команде, которую Revit создаёт по строке имени класса. Разобрано по метаданным **всех четырёх**
версий и по примерам Autodesk (`<каталог SDK>\Samples`); все восемь регистраций в примерах
вызываются из `OnStartup` — проверено по контексту вызова, а не по справке.

| Регистрация | Сборка | Чем спросить «уже есть?» | Обратный ход |
|---|---|---|---|
| `FailureDefinition.CreateFailureDefinition` | RevitAPI | `GetFailureDefinitionRegistry().FindFailureDefinition` | **нет, навсегда** |
| `UpdaterRegistry.RegisterUpdater` | RevitAPI | `IsUpdaterRegistered` | `UnregisterUpdater` |
| `ExternalService.AddServer` | RevitAPI | `IsRegisteredServerId` | `RemoveServer` |
| `PerformanceAdviser.AddRule` | RevitAPI | **нельзя** | `DeleteRule` |
| `UIControlledApplication.RegisterDockablePane` | RevitAPIUI | `DockablePane.PaneIsRegistered` | нет |
| `UIControlledApplication.RegisterContextMenu` | RevitAPIUI | **нельзя** | нет |
| `CreateAddInCommandBinding` | RevitAPIUI | `RevitCommandId.HasBinding` | `RemoveAddInCommandBinding` |
| `ControlledApplication.RegisterFailuresProcessor` | RevitAPI | нельзя | нет — **и потому вычеркнут** |

`RegisterContextMenu` **отсутствует на 2024**; остальные семь есть на всех четырёх.

**Разрез тот же, что у хоста.** Пять из восьми объявлены в `RevitAPI`, то есть доступны обеим
формам add-in; три — в `RevitAPIUI`. Это ровно граница `RevitAddInHost` / `RevitAddInApplication`,
уже проведённая для пампа и для потока фаз.

**Но форма передаётся параметром, а не хранится свойством.** Три UI-регистрации требуют
`UIControlledApplication`, живой только внутри `OnStartup`, а `IFeatureServices` долгоживущ и
достижим из команды через `HostRegistry`. Регистратор на нём — это регистратор, которого позовут,
когда объект уже мёртв. Та же причина, по которой `IRevitSession` выдаётся только внутри пампа.

### Три правила, каждое обобщает свой случай

**Где объявлять — решает Revit, а не вкус.** Не «код или манифест», а: **принимает фабрику →
манифест, требует саму вещь → код**. `RegisterUpdater` требует экземпляр `IUpdater`,
`FailureDefinition.AddResolutionType` требует `Type` — их манифест не спасёт, сборка фичи
загрузится в `OnStartup` всё равно. `RegisterDockablePane` принимает `IFrameworkElementCreator`
(есть на всех четырёх) — значит хост подставляет **свой** провайдер, собранный из строк манифеста,
и разрешает класс содержимого лениво. Ленивость возвращается, и вместе с ней — невозможность
написать `typeof`, которая однажды её молча отменила.

**И вторая половина правила, без которой первая обманывает: ленивость окупается тем больше, чем
вероятнее, что вещь не понадобится вовсе.** Панель часто не открывают ни разу, кнопку часто не
нажимают — а апдейтер срабатывает на первом же подходящем изменении модели, то есть отложенная
загрузка его сборки экономит секунды и ничего больше. Обе половины вместе объясняют панель, кнопку
и апдейтер одним измерением, а не тремя вкусами.

**Что не берём вовсе.** Три случая оказались одним семейством:

| | Почему необратимо |
|---|---|
| `RegisterFailuresProcessor` | `static`, один слот на процесс: забирает обработку отказов у **всех** вендоров |
| `CreateAddInCommandBinding` | `Executed` **заменяет** штатную команду; `Cancel` нет ни у одного из трёх типов аргументов, повторная привязка бросает |
| `DialogBoxShowing.OverrideResult` | уже отклонён выше по тексту |

> **Регистрация, действующая на весь процесс и не имеющая обратного хода, не берётся без явного
> решения владельца.** Первая из трёх едва не попала в план первым шагом — под именем «обработка
> отказов», то есть как удобство, а не как захват чужого поведения.

Замена для своих нужд есть и она в области фичи: `FailureHandlingOptions.SetFailuresPreprocessor`
действует на одну транзакцию, а `ControlledApplication.FailuresProcessing` — аддитивное событие.

**Идемпотентность: сначала спросить Revit.** Его состояние переживает наш `Stop`, видит чужих
вендоров и не врёт; свой статик видит только нас. Спросить можно у **шести из восьми**, значит
собственный учёт нужен только `RegisterContextMenu` и `PerformanceAdviser.AddRule` — а обе
отложены. **Отсюда: реестр регистраций сейчас не заводится.** Механизм с нулём потребителей — это
`Revit.Base` из `..\BimHouseApp` в новой форме.

### Владение уже по `AddInId`, и это механизм Revit, а не наше соглашение

Здесь стояло опасение, что снять апдейтер на `Stop` значит испортить работу второму изданию: на
Revit 2024 все add-in в одном AppDomain. Опасение снято метаданными: `UpdaterId` конструируется как
**`(AddInId, Guid)`**, а `AddInId` у изданий разные по определению — это ключ манифеста и ключ
`HostRegistry`. Два наших издания физически не могут зарегистрировать один апдейтер.

Вывод от этого переворачивается: снимать **обязательно**. Оставленный апдейтер держит живым
экземпляр `IUpdater`, то есть сборку фичи, и Revit продолжит его звать в сессии, где нашего хоста
уже нет. Порядок разматывания тот же, что у модулей: обратный, каждый шаг под своим `try`.

Единственный настоящий спор — `AddInCommandBinding`: ключ `RevitCommandId` глобален, и столкновение
там межвендорское. Ещё один довод отложить.

### Порядок работ

1. `IRegistrationScope` / `IUiRegistrationScope` + `IRegisteringFeature`, и **одна** регистрация —
   `FailureDefinition`. Единственная необратимая, значит единственная, чью ошибку нельзя починить.
2. `DockablePane` — манифестом, плюс запекание строк объявления по культурам в SDK.
3. `IUpdater` — кодом, по первому потребителю.
4. `RegisterContextMenu` — вместе с реестром и первым версионным разрезом; `#if REVIT2025_OR_GREATER`
   живёт **внутри хоста**, метод объявлен на всех четырёх TFM, на 2024 возвращает отказ. Иначе
   каждая фича заведёт свой `#if` и будет молча вести себя по-разному между версиями.

> **Панель поднята на шаг вверх против первого плана, и по четырём доводам.** Она подешевела:
> `FrameworkElementCreator` снял то, что делало её дорогой. Она **делит с `FailureDefinition` одну
> задачу** — тексты отказа это интерфейс, их читает человек в предупреждении Revit, и объявляются
> они в `OnStartup`, то есть попадают ровно в «строки объявления»; механизм для них нужен один, и
> делать его дважды не придётся. `IUpdater` **невидим**: он меняет модель за спиной пользователя, и
> всё, чем он может о себе сообщить, — это отказ и панель, так что «сначала то, чем говорят» дешевле
> обратного. И главное: панель — **первый настоящий потребитель UI-набора**. Сегодня `WPF-UI` 4.0.3
> объявлен в CPM и не используется ни одним проектом; измерен на живом Revit 2024 был **полный**
> набор, потом его урезали, и урезанный внутри Revit не жил ни разу. Панель делает проверяемыми
> четыре сегодняшние гипотезы: грузится ли `Wpf.Ui` 4.0.0.0 из нашей папки, остаются ли полифиллы на
> `net48` теми же четырьмя, верно ли ещё «мы первые, кто везёт `Wpf.Ui` на этой машине», и работает
> ли схема с темой при живом переключении.
>
> Что панель тянет: `WPF-UI` 4.0.3 (значит имя `Wpf.Ui` в watchlist RefCheck) и `Lepo.i18n.Wpf`.
> `Microsoft.Xaml.Behaviors.Wpf` первой панели не нужен. `UseWPF` на хосте уже включён ради
> `PlaceholderIcon`, палитра и слой темы — наш код: ноль новых сборок сверх названных.
>
> **И решение про прогон, которое стоит принять сразу.** Панель с `VisibleByDefault = false`
> показывается нажатием, а нажатие — это `BHS_PROBE_SHOW_TAB=1`, дорогой режим с человеком у экрана.
> Значит проверки надо разложить осознанно: в **обычный** режим — что панель зарегистрирована
> (`PaneIsRegistered`), что `PaneExists` отвечает, и что **сборка фичи не загружена**, потому что
> creator не звали; это прямой аналог измерения ленивости ленты и самое ценное из набора. В
> **расширенный** — что панель показана, creator вызван, словари темы на корне, и переключение темы
> Revit её перекрасило. Пол проверок поднять вместе с этим.

**Что надо померить в шаге 1, а не предсказать:** отвечает ли `FindFailureDefinition` на
определение, зарегистрированное в том же процессе **чужим** add-in — от этого зависит, действительно
ли опрос заменяет свой учёт. И бросает ли `CreateFailureDefinition` на повторе.

**Проверок в сборке здесь не нужно, и это признак, что механизм выбран верно.** У ленты Revit
конструирует по строке, поэтому отказ виден только запуском — отсюда `RVTRIB001`–`RVTRIB005`. Здесь
всё типизировано и ловится компилятором. Нужда вернётся вместе с манифестным путём панели.

**Документные триггеры знать заранее:** `AddTrigger(UpdaterId, Document, ...)` ставятся на
`DocumentOpened`, это не одноразовая работа `OnStartup`. Потребителя нет — не заводим, но первая
документная фича иначе полезет к событиям сама.

### Что framework обязан дать панели, чтобы фича писала только содержимое

Панель — это `FrameworkElement`, отданный Revit **один раз** и живущий всю сессию. Он переживает
открытие и закрытие документов, смену вида и смену темы; Revit больше никогда не спросит его заново.
Отсюда всё остальное.

**Фича пишет `UserControl` и вью-модель, и ничего больше.** Хост даёт оболочку, которая берёт на себя
четыре вещи — каждая иначе будет написана в каждой фиче заново и по-разному:

- **Состояние «документа нет».** Панель создаётся раньше, чем документ существует, и остаётся после
  его закрытия. Это не сообщение об ошибке, а обычный экран: одна фраза о том, что нужно открыть
  модель. Пишет его framework, единообразно.
- **Состояние ожидания.** Панель безмодальна, значит каждое обращение к API идёт через памп, значит
  каждое действие асинхронно по природе. Оболочка даёт индикатор и строку текста, и **текст
  обязателен**: «Чтение кабельных трасс», а не «Загрузка». Словарь для таких строк уже есть — тот же,
  которым `RevitDiagnostics` возит captions самого Revit.
- **Текущий документ.** Оболочка подписана на `DocumentOpened` / `DocumentClosing` / `ViewActivated`,
  сводит их к одному свойству и отдаёт вью-модели. Фича не подписывается ни на что.
- **Содержимое не пересоздаётся при смене документа.** Пересоздание теряет прокрутку, выделение и
  фокус — то есть ровно то, ради чего панель и держат открытой. Меняются данные, а не дерево.

**Умолчания раскладки, и каждое с причиной:**

| Свойство | Значение | Почему |
|---|---|---|
| `VisibleByDefault` | `false` | панель, появившаяся сама в раскладке, которую пользователь выстроил, — плохой гость; показывается по кнопке |
| `EditorInteraction` | `Dismiss` | панель, пережившая вход в редактор семейства или режим эскиза, будет предлагать действия, которые там незаконны; `KeepAlive` — только когда фича правда работает в редакторах и сказала об этом |
| `InitialState` | `DockPosition.Right`, `MinimumWidth` ≈ 320 | ширина палитры свойств; `MinimumHeight` маленький |
| `TabBehind` | **не ставить по умолчанию** | это прячет то, за что мы встали, обычно палитру свойств; оставить выбором издания в манифесте |

**GUID панели постоянен навсегда.** Revit хранит раскладку доков по нему, и смена GUID теряет
расстановку, которую выстроил пользователь. Та же дисциплина, что у GUID схемы Extensible Storage,
и по той же причине: идентификатор, уехавший наружу, назад не берётся.

### Контекстное меню — только второй вход, никогда единственный

`CommandMenuItem(String text, String className, String assemblyPath)` — те же три строки, что у
`PushButtonData`, плюс `SetAvailabilityClassName` и `SetToolTip`; рядом `SeparatorItem()` и
`SubMenuItem(String, ContextMenu)`. Манифестная дисциплина ленты переносится дословно, `typeof`
писать негде, а `BuildContextMenu` зовётся при открытии меню — сборка фичи при старте не грузится.
Мелкий бонус: тексты строятся каждый раз, значит следуют за сменой языка, в отличие от заголовка
панели.

**Контекстное меню — сокращение пути для того, кто уже знает, что делает.** Оно ничего не объявляет
и ничему не учит: пункт видно только после того, как его вызвали. Функцию находят на ленте, а
короткую дорогу к ней обнаруживают потом.

> **Правило: пункт контекстного меню обязан быть вторым входом в команду, у которой есть кнопка на
> ленте, и никогда единственным.** Тогда пользователь Revit 2024, где `RegisterContextMenu` нет,
> теряет два клика, а не функцию, и документация, написанная про ленту, верна для всех четырёх
> версий. Без правила он читает «правой кнопкой → Пересчитать», жмёт правой кнопкой, пункта нет — и
> делает вывод «плагин установился криво», а не «в этой версии механизма нет».

Проверяется статически, из семейства `RVTRIB`: `ClassName` пункта обязан встречаться среди
`ClassName` кнопок того же манифеста.

**Не измерено, и это единственная нота, оставшаяся открытой во всём разборе.** Первый аргумент
`RegisterContextMenu` — это строка, и пример 2027 кладёт туда имя собственного класса приложения, а не категорию Revit. Где
после этого появляется пункт, по метаданным не видно. Если привязка к типу выделенного элемента —
механизм уместный; если пункт появляется всегда — это шум в чужом меню, которое и без нас длинное.

### Перехват встроенных команд: `Executed` запрещён по умолчанию

Запрещать механизм целиком не надо, но самая сильная его часть по умолчанию выключена.

- **`Executed` — только за явной настройкой, выключаемой, никогда не включённой из коробки, и
  перехват обязан быть виден в интерфейсе.** Пользователь нажимает знакомую кнопку и получает не то;
  хуже всего, что отказ не выглядит отказом — интерфейс не изменился, изменилось поведение, и
  причину человек будет искать в Revit. Без видимого признака «у меня Revit сломался» неотличимо от
  «у меня установлен ваш плагин».
- **`CanExecute` — можно, но с объяснением.** Серая команда не говорит, почему она серая; это
  называет и сам пример Autodesk. Фича, гасящая встроенную команду, объясняет это в видимом месте, а
  хост логирует каждое `CanExecute = false` с причиной — иначе обращение «не работает Стена»
  разбирать не по чему.
- **`BeforeExecuted` — санкционированный путь:** наблюдать, подготовить, записать и дать Revit
  сделать свою работу. Отменить он всё равно не умеет, и это к лучшему.
- **Спрашивать до того, как брать.** `CanHaveBinding == false` → отказ строкой в лог, не исключение
  из `OnStartup`. `HasBinding == true` → отказ: кто-то успел первым, и на 2024 он живёт в нашем
  AppDomain. **За привязку не спорить никогда** — победа означает, что чужой плагин молча перестал
  работать.
- **Снимать в `OnShutdown`** — единственная обратимая из трёх, значит единственная, за которую мы
  отвечаем до конца.
- **`LookupPostableCommandId(PostableCommand)` вместо `LookupCommandId(string)`** везде, где хватает
  перечисления: его проверяет компилятор. Сырые строковые id версионны и мерятся на каждой версии.
- **В манифест — по причине, особенной именно для привязок: они невидимы.** Панель видно, кнопку
  видно, взятую команду не видно нигде; декларация — единственное место, где список читается целиком.

И стоп-сигнал, стоящий выше механики: перехват встроенной команды выходит за «место на нашей вкладке
ленты» — он трогает то, чем пользуются помимо нас. Первую такую привязку заводить под конкретную
задачу и с явным согласием владельца, а не потому, что механизм есть.

### Изображений нет ни у панели, ни у меню

Проверено: у `DockablePane` только `GetTitle`/`SetTitle`/`Show`/`Hide`/`IsShown`/`Id`; у
`DockablePaneProviderData` — `FrameworkElement`, `FrameworkElementCreator`, `InitialState`,
`ContextualHelp`, `EditorInteraction`, `VisibleByDefault`; у `MenuItem`, `CommandMenuItem`,
`SeparatorItem`, `SubMenuItem` — текст, подсказка, класс доступности. Ни одного члена с изображением.

**Значит приём «32px и 64px при 192 dpi» относится только к кнопкам ленты** — он существует потому,
что лента рисует `Stretch=None`. Ни панели, ни меню он не нужен.

Идентичность панели несёт заголовок и вкладка, поэтому заголовок **называет предмет, а не вендора**
(«Кабельные трассы», не «BHS Панель») и коротко: он живёт в полосе вкладок рядом с «Обозреватель
проекта» и «Свойства». Всё, что мы хотим нарисовать, рисуется **внутри** панели, где разметка наша,
и там правильный ответ — **вектор** (`DrawingImage`, `Path`): корректен при 150 % без арифметики с
dpi. Отложенный вопрос про вектор этим закрыт наполовину: внутри панели откладывать нечего, на ленте
он остаётся, потому что неизвестно, как `DrawingImage` поведёт себя при `Stretch=None`.

### `ApplicationThemeManager` внутри Revit звать нельзя — измерено по IL

Правило того же рода, что «не везти чужих сборок», только про ключи ресурсов. И записано вместе с
измерением, потому что `Apply(FrameworkElement)` называется ровно как то, что нам нужно.

Декодированы вызовы в `wpf-ui` 4.0.3, ветка `net472`:

```
ApplicationThemeManager::Apply(ApplicationTheme, ...)
    ResourceDictionaryManager::UpdateDictionary
    UiApplication::get_Current -> get_MainWindow -> WindowBackgroundManager::UpdateBackground

ResourceDictionaryManager::UpdateDictionary
    UiApplication::get_Current -> get_Resources -> MergedDictionaries -> set_Item

UiApplication::get_Resources
    Application::get_Resources          <- когда Application.Current есть, то есть внутри Revit

ApplicationThemeManager::Apply(FrameworkElement)
    UiApplication::get_Current, get_Resources, ResourceDictionary::GetEnumerator,
    DictionaryEntry::get_Key/get_Value, ResourceDictionary::set_Item
```

Первый **мутирует словарь ресурсов Revit и красит главное окно Revit** — это не побочный эффект, а
назначение метода. Второй **копирует** ресурсы приложения в элемент, а источник копии внутри Revit —
опять ресурсы Revit: он либо не даст ничего, либо перетащит в нашу панель чужие ключи.

**Рабочий путь — свой, на три строки:** `ThemesDictionary { Theme = ... }` и `ControlsDictionary`
в `MergedDictionaries` **нашего** корня. Ни `Apply`, ни `ApplySystemTheme`, ни подписки на
`ApplicationThemeManager.Changed` в Revit-side не появляется.

Источник истины о теме — Revit, и он же единственный, кто о ней сообщает:

| | Revit | WPF-UI |
|---|---|---|
| значение | `UIThemeManager.CurrentTheme` | `GetAppTheme()` — **не спрашивать** |
| уведомление | `UIControlledApplication.ThemeChanged` | `Changed` — **не подписываться** |
| применение | — | `ThemesDictionary.Theme` на нашем корне |

Оба ревитовских члена есть на всех четырёх версиях. Хост ведёт список живых корней и меняет тему у
каждого; это работа с WPF, значит UI-поток, значит памп.

> **Попутно исправляется утверждение в коде.** `RevitAddInApplication.OnInitialized` откладывает
> подписку до `ApplicationInitialized` с комментарием, что событие живёт на `UIApplication`.
> `UIControlledApplication.ThemeChanged` есть на всех четырёх — подписаться можно прямо в
> `OnStartup`, и тогда исчезает окно, в котором смена темы теряется.

### Язык берётся у Revit, а не у Windows

`ControlledApplication.Language` есть на всех четырёх и лежит в **`RevitAPI`** — то есть доступен и
DB-форме. `LanguageType` даёт `English_USA`, `English_GB`, `Russian` — ложится на наш
`SatelliteResourceLanguages` один в один, — плюс `Unknown`, который обрабатывается явно и отвечает
нейтральным `en`.

Язык интерфейса Revit выбирается при установке и запуске и с языком Windows не связан: русская
Windows с английским Revit — обычный случай, поэтому `CurrentUICulture` здесь неверный источник.

**И следствие для строк объявления.** `DockablePane.SetTitle` есть **только на 2027**, значит на
2024–2026 заголовок фиксируется в `OnStartup` навсегда. Само по себе это почти бесплатно — Revit не
меняет язык интерфейса на живую, — но ломается ровно одним способом: если **мы** заведём свою
настройку языка, меняемую на живую. Не надо; язык следует за Revit, а переопределение, если
понадобится, применяется только при старте и говорит об этом в себе.

Отсюда разрез в слое строк, повторяющий ленивую границу:

- **строки объявления** — заголовок панели, `Text` и `ToolTip` кнопки — нужны **до** загрузки фичи.
  `new ResourceManager(baseName, assembly)` в `OnStartup` загрузит сборку фичи ровно там, где
  `FrameworkElementCreator` от этого избавил: тот же класс отказа, что `typeof` на кнопке — код
  законен, компилятор молчит, видно только замером;
- **строки содержимого** — внутри панели и команды, обычный `Lepo.i18n` без оговорок.

**Долг, вскрытый попутно:** `Text` и `ToolTip` в манифесте ленты сегодня литералы в csproj, а
правило проекта требует строки интерфейса в ресурсах. У кнопки цена ошибки ниже, чем у заголовка
панели, но нарушение то же, и чинить их стоит одним механизмом.

**Механизм — SDK запекает `.resx` в манифест по культурам.** Источник один — `.resx` рядом с фичей,
то есть правило «строки в ресурсах» соблюдено буквально; отрисовки две — сателлитные сборки для
строк содержимого и json для строк объявления. Выход: `<сборка>.features.json` (нейтральный) плюс
`<сборка>.features.<культура>.json`; хост накладывает файл культуры на нейтральный тем же
`JsonSettings` и тем же слоением, что и настройки. **Ноль новых сборок в AppDomain Revit, ноль
загрузок фичи.** Json — производное, с шапкой «generated, do not edit».

**Культурных файлов два, а не три:**

```
English_GB -> en-GB      наложение
Russian    -> ru-RU      наложение
всё прочее -> нейтральный, файла не ищем
```

`English_USA` и `Unknown` попадают в одну ветку **намеренно**: «язык, для которого у нас нет
наложения» — одно состояние, а не два. Нейтральный у нас `en` и несёт американский английский, так
что файл для `English_USA` был бы пустым или дословной копией — и то и другое хуже отсутствия, потому
что пустой файл читается как брошенная на полпути локализация и притягивает наполнение копиями. **Файл
заводится вместе с первым настоящим переопределением.**

**`RVTRIB012` проверяет в одну сторону:** каждый ключ файла культуры обязан существовать в
нейтральном; обратное **не** требуется. Файл культуры — наложение, `en-GB` отличается от нейтрального
горсткой слов, и требование одинаковых множеств сделало бы правильный разреженный файл ошибкой
сборки — а чинили бы её копированием нейтральных строк, то есть строками, которые выглядят
переведёнными и никогда не переводились. Это хуже отсутствующего перевода, который виден сразу и на
своём месте. Проверяемая сторона ловит опечатку в ключе и — что важнее — **сироту** после
переименования ключа в нейтральном `.resx`: сирота молчит вечно, файл валиден, ключ просто никогда не
спрашивают. Счётчик непереведённого — строка в лог, не отказ. И проходя, проверка обязана оставлять
след **тем же способом**, что `RVTRIB010`/`RVTRIB011`: в этом репозитории RefCheck сначала месяцами
не импортировался, а потом печатал строку с важностью, невидимой в логе раннера.

**Что попадает в `en-GB`** — ключ идёт туда, только когда термин действительно другой, и решает это
не стилевое руководство, а то, как ту же вещь называет **сам британский Revit**: мы говорим словами
хоста. Практическое следствие — файл может долго оставаться очень коротким, и это его нормальное
состояние, а не признак недоделанной локализации.

**Запасной вариант, если запекание не поспеет к первой панели:** английский литерал **в нейтральной
позиции** — той, которая потом станет ключом. Тогда гашение долга это перенос строки в `.resx` и
замена значения на ключ, механическая правка в одну строку диффа. Промежуточный вариант «резолвить
ключи против ресурсов сборки издания» отклонён: он работает, и **поэтому** опасен — делает «строки
фичи живут у издания» путём наименьшего сопротивления для каждой следующей фичи. Тот же урок, что
записан про escape hatch у `RVTREF005`.

> **`SatelliteResourceLanguages` к нашему набору языков отношения не имеет — это два механизма под
> одним именем.** Проверено по целевым файлам .NET SDK 10.0.400: `_FilterSatelliteResourcesForPublish`
> фильтрует **уже разрешённые** ассеты с `AssetType == 'resources'`, а не создаёт их. Сателлит
> рождается от `.resx` с суффиксом культуры. То есть список отвечает на «что из чужого мы везём» — его
> настоящая работа обрезать переводы `WPF-UI` и `Lepo.i18n`, которых там десятки культур, — а на «на
> каких языках пишем мы» отвечает то, какие `.resx` мы заводим. Наборы совпадать не обязаны, и
> `en-US` в списке лишним не является.
>
> Мы заводим `.resx` только для **`en-GB`** и **`ru-RU`**; нейтральный `en` несёт американский
> английский. Запекание json следует **нашему** набору, а не этому списку, иначе появится
> `features.en-US.json` и мы вернёмся туда, откуда ушли.

## Доверие Revit к add-in: измеренный механизм

Разобрано экспериментом на Revit 2027, потому что запись в реестр доверия оказалась ненадёжной,
а поведение — не тем, что о нём думали. У Revit **три** диалога безопасности, не один; строки
лежат в `RevitUI.dll`, тексты — в `UIFrameworkRes.dll`:

| Состояние сборки | Диалог | Что делает «Всегда загружать» |
|---|---|---|
| подписи нет | `TaskDialog_Security_Unsigned_File_Loading` | пишет DWORD `1` в `HKCU\...\Autodesk Revit <год>\CodeSigning`, имя значения — `AddInId` |
| подпись есть, цепочка не проверяется | `TaskDialog_Security_Invalid_Signature` | — (кнопка по умолчанию «Не загружать») |
| подпись валидна, папка не доверена | `TaskDialog_Security_Signed_File_Not_In_Trusted_Folder` | кладёт **сертификат издателя** в `Cert:\CurrentUser\TrustedPublisher` |

Третья строка — ответ на вопрос «почему „Всегда загружать“ не помогает». Она **не про файл и не
про `AddInId`, а про издателя**, и это качественно другой уровень: доверив сертификат один раз,
вы снимаете диалог для **всех** своих сборок, всех `AddInId` и всех версий Revit сразу. Реестровая
запись из первой строки, наоборот, живёт по одной на add-in на версию Revit.

Проверено, что `Cert:\CurrentUser\TrustedPublisher` на этой машине и есть накопленный за годы
список вендоров Revit-плагинов — AGA CAD, Arch-Intelligence, ModPlus, RTV Tools, BIMobject, DKC,
Bim2B, Enscape, Autodesk. То есть это штатный путь, а не обходной.

### Самоподписанный сертификат для разработки — работает

Измерено на Revit 2027, в такой последовательности:

1. подписали пробу самоподписанным сертификатом, **не** положив его в доверенные → Revit выдал
   `TaskDialog_Security_Invalid_Signature`. Значит **цепочка проверяется**, наличия подписи мало;
2. положили сертификат в `Cert:\CurrentUser\Root` → подпись стала `Valid`, Revit выдал уже третий
   диалог, про папку, и по «Всегда загружать» сам добавил сертификат в `TrustedPublisher`;
3. **пересобрали** сборку (другие байты), подписали заново, запись в `CodeSigning` при этом
   отсутствовала → **ни одного диалога**, полностью без участия человека.

Третий шаг и есть доказательство: доверие пережило пересборку, потому что оно на издателе.

```powershell
# один раз на машину. Без явных -KeyAlgorithm/-Provider падает с CRYPT_E_UNKNOWN_ALGO
$cert = New-SelfSignedCertificate -Type CodeSigningCert `
    -Subject "CN=BimHouse Software (development), O=BimHouse Software, C=RU" `
    -CertStoreLocation "Cert:\CurrentUser\My" `
    -KeyAlgorithm RSA -KeyLength 3072 -HashAlgorithm SHA256 `
    -Provider "Microsoft Software Key Storage Provider" `
    -KeyExportPolicy Exportable -KeyUsage DigitalSignature -NotAfter (Get-Date).AddYears(3)

# корень — чтобы цепочка проверялась; издатель — чтобы Revit не спрашивал про папку.
# Второе Revit сделает и сам по «Всегда загружать», но тогда это стоит одного клика.
foreach ($name in 'Root','TrustedPublisher') {
    $store = [System.Security.Cryptography.X509Certificates.X509Store]::new($name, 'CurrentUser')
    $store.Open('ReadWrite'); $store.Add($cert); $store.Close()
}

# на каждую сборку
Set-AuthenticodeSignature -FilePath <путь к dll> -Certificate $cert -HashAlgorithm SHA256
```

Границы применимости, чтобы потом не выяснять заново:

- сертификат **машинный и пользовательский**: доверие получает только эта учётка на этой машине.
  Заказчику подписанное им ничего не даёт — для поставки нужен настоящий сертификат от CA;
- закрытый ключ лежит в профиле и помечен экспортируемым. Это **ключ, которым можно подписать
  что угодно от нашего имени**, и учётка ему верит. Для машины разработчика приемлемо, для общей
  или сборочной — нет;
- снимается симметрично: удалить сертификат из `My`, `Root` и `TrustedPublisher`;
- подписывать нужно сборку, названную в манифесте (`<Assembly>`), а не весь `Lib`.

### Как это заведено в сборку

SDK умеет подписывать сам, свойством **`RevitSignWith`** (см. раздел 10 в
`build/BHS.Revit.Sdk/readme.md`). По умолчанию оно пустое — **продакшн собирается без подписи**,
и ни одна из этих задач не выполняется.

Отпечаток — свойство машины, а не репозитория, поэтому берётся из переменной окружения
`BHS_REVIT_SIGN_WITH`; в git его класть нельзя. Задав её один раз, вы получаете подписанными
и обычную сборку, и `--deploy` у прогона пробы — прогон просто наследует окружение.

```powershell
# постоянно, на пользователя — так и надо: переменная сессии умирает вместе с окном
[Environment]::SetEnvironmentVariable('BHS_REVIT_SIGN_WITH', '<отпечаток>', 'User')

$env:BHS_REVIT_SIGN_WITH = '<отпечаток>'                                          # только на сессию
dotnet build <проект> -c Release -f net8.0-revit2026 -p:RevitSignWith=<отпечаток>  # или разово
```

> **Задавайте её постоянно, а не на сессию.** Первый раз переменную поставили через `$env:` — то
> есть на одно окно, — и через день сборка молча вышла неподписанной, а Revit снова начал
> спрашивать. Ошибки при этом нет никакой: пустая `RevitSignWith` означает «продакшн», и задача
> подписи просто не выполняется. Отпечаток здесь не приводится — этот же раздел двумя абзацами
> выше запрещает класть его в git, и запрет держался ровно до того абзаца. Спросить его у машины:
>
> ```powershell
> Get-ChildItem Cert:\CurrentUser\My -CodeSigningCert | Format-List Subject, Thumbprint
> ```
>
> Проверить, что подпись доехала до развёрнутого add-in:
>
> ```powershell
> Get-AuthenticodeSignature "$env:APPDATA\Autodesk\Revit\Addins\2026\BimHouseSoftware\BHS.Revit.Probe\Lib\BHS.Revit.Probe.dll"
> ```
>
> Заметьте и раскладку: сборки лежат в подкаталоге **`Lib`**, а не в папке add-in. Всё, что должно
> лежать рядом со сборкой — файл настроек в первую очередь, — принадлежит `Lib`. Положенное уровнем
> выше существует, не читается и стоит одного прогона.

Три решения внутри, каждое куплено отказом:

- **подписывается только сборка из манифеста.** Revit спрашивает лишь про неё — измерено на 2027:
  всё остальное в `Lib` осталось без подписи, диалога нет;
- **подписывается промежуточная сборка в `obj`, а не результат в `bin`.** Подписать `bin` кажется
  правильным и не работает: `CopyFilesToOutputDirectory` на следующей сборке восстанавливает файл
  из `obj` вместе с его временем, так что инкрементальная проверка по выходному файлу даже не
  замечает пропажи подписи. Найдено сборкой, где развёрнутый add-in оказался неподписанным, а
  задача рапортовала «up-to-date»;
- **`PSModulePath` сбрасывается перед вызовом `powershell.exe`.** Он наследуется, и сборка,
  запущенная из терминала PowerShell 7 (в том числе рядеровского), подсовывает Windows PowerShell
  модули семёрки. Тот не может загрузить свой `Microsoft.PowerShell.Security`, и вместе с ним
  исчезают `Set-AuthenticodeSignature` и диск `Cert:`. Ошибка при этом не называет ни причины,
  ни лекарства.

Проверено сквозным прогоном: подпись доезжает `obj` → `bin` → publish → `%AppData%`, повторная
сборка не переподписывает, а Revit 2027 с пустым `CodeSigning` грузит add-in **без единого
диалога**.

## Путь поставки: проверка на каждое изменение

Заведено по своду правил, выведенному из соседнего проекта: **путь поставки строится раньше
первой функции**. Основание там измеренное, и у нас оно то же самое — репозиторий прожил
**51 коммит и все измерения этого файла без единой автоматической проверки**. Возражение
«у нас 288 проверок в Revit и 65 в транспортной пробе, это больше, чем у многих с CI» неверно
ровно тем, о чём свод и предупреждает: они гонялись **руками и на одной машине**, потому что
я вспоминал набрать команду. У такого обрыва нет симптома.

### Две ступени, и разрез вынужденный

Не выбран, а продиктован предметом: **Revit на арендованный раннер не поставить**. Поэтому
`.github/workflows/build.yml` везёт всё, что верно **без** Revit:

| Шаг | Что доказывает |
|---|---|
| сборка `build/BHS.Revit.Sdk` | двухэтапность соблюдена: пакет попадает в `artifacts/feed` до restore остального |
| сборка решения на всех четырёх Revit-TFM | компилируется то, что мы пишем, а не то, что собралось у меня в кэше |
| **RefCheck** — сам, из `Directory.Build.targets` | `RVTREF005` и родня выполняются, а не только описаны |
| транспортная проба ×3 рантайма | канал, доверие, реестр, настройки, стриминг на `net48` |

Вторая ступень — **прогон `BHS.Revit.Probe.Runner` по четырём версиям** — остаётся местной,
потому что Revit на раннере не поставить. Но её результат больше не живёт в терминале: прогон
выпускает запись, запись едет в репозиторий, и CI проверяет **её** — см. подраздел ниже. Это
записано здесь, а не оставлено подразумеваемым: ступень, о которой молчат, читается как пройденная.

> **Побочная выгода, которой не планировалось: CI гоняет пробу на пересозданном окружении.**
> На раннере нет ни `%ProgramData%\BHS`, ни `%AppData%\BHS`, ни накопленных за месяцы
> `TrustedPublisher` и `CodeSigning`. Свод отдельным правилом требует проверять на чистом
> состоянии, а не на накопленном, — и здесь это получается само.

### Вторая ступень: CI проверяет запись о прогоне, а не прогон

> **CI не запускает Revit. Никогда не запускал и не будет.** Ему нужна интерактивная сессия,
> лицензия и гигабайт Autodesk на диске; на арендованном раннере этого нет. **Ни одна из 288
> проверок, доказывающих, что add-in работает, в CI не выполняется** — они выполняются здесь,
> руками, через `BHS.Revit.Probe.Runner`.
>
> Job называется `sweep-evidence`, а не `sweep`, и это не педантизм: через полгода зелёная галочка
> будет выглядеть как «Revit проверен на CI», а это не так.

Прогон выпускает **машиночитаемую запись** — `--report evidence/sweep-report.json`, — и она едет
в репозиторий вместе с кодом. CI проверяет запись пятью вопросами, и каждый отвечает на способ,
которым запись могла бы оказаться бесполезной:

| Вопрос | Что закрывает |
|---|---|
| файл есть, разбирается, схема знакомая | запись, которой нет, — не запись |
| снят на **чистом дереве** | прогон поверх незакоммиченных правок проверял то, что есть на одной машине и больше нигде |
| Revit-side каталоги **хешируются в то же, что при записи** | **главный**: без него позавчерашняя запись проходит вечно |
| присутствуют все четыре версии, ни одного отказа | «2026 прошла, про остальные забыли» |
| ни одна проверка не **исчезла** против базовой записи | пропавшая проверка ничего не печатает и ничего не роняет |


> **Третий вопрос спрашивает про содержимое, а не про предка, и это исправление, купленное
> первым же слиянием.** Сначала проверка спрашивала, является ли коммит записи предком HEAD.
> Мы сливаем **squash**, а squash пишет **новый** коммит: в тот час, когда первая запись попала
> в `master`, названный ею коммит из истории исчез, и совершенно свежая запись была забракована.
> Rebase и cherry-pick сделали бы то же.
>
> Запись везёт git tree-хеш каждого Revit-side каталога, и сравниваются они. Ни squash, ни rebase,
> ни cherry-pick не меняют того, что написано в файлах, — значит не трогают и проверку. Коммит
> по-прежнему **обязателен** — запись без него отвергается как «record of nothing», и он же стоит
> в итоговой строке, — но **свежесть** на нём больше не держится. Разница важна для того, кто
> будет писать другого производителя записей: поле нельзя опустить.
>
> Проверено всеми тремя случаями: текущая запись проходит; одна строка, добавленная в
> `PlaceholderIcon.cs`, делает запись устаревшей **и называет файл**; точная модель squash —
> то же содержимое, новый коммит, `merge-base --is-ancestor` отвечает `NO` — **проходит**.

**Брошенная версия из пятого вопроса исключается**, как и из пола проверок. Измерено: прогон, где
Revit 2026 и 2027 встали на модальном диалоге, выдал десятки строк «проверка больше не выполняется»
— каждая правдива и все не о том: эти проверки не исчезли, их не задавали, а прогон уже отказал
двумя вопросами раньше. Поле `Abandoned` в записи заведено ровно за этим.

> **И заодно измерена цена самого прогона для машины.** Три полных прогона с моделью за час — это
> двенадцать запусков Revit, и на втором и третьем **три версии из четырёх** встали на
> `TaskDialog_Stop_Operation`: Revit объявляет отменённым прогресс загрузки, которая идёт нормально
> (`ProgressCancelled` в журнале через 0,3 с после успешного `TrustedUtility::readStreams`), а
> отвечать некому. `BHS_PROBE_SHOW_TAB` при этом не задан — ленту никто не трогал.
>
> После паузы тот же код на той же машине прошёл **без единого диалога**, 272 из 272. То есть
> «машина, гонявшая Revit подряд» — не оговорка, а воспроизводимое условие, и **прогоны нельзя
> ставить подряд**. Отличить одно от другого помогло то, что Revit 2025 в обоих отказах давал ровно
> те же 68 проверок и ноль отказов, что и в зелёной записи: сломайся код — сломался бы и он.

**Пятый пункт** — про исчезнувшую проверку — сильнее пола по числу, который живёт внутри прогона: пол замечает только массовую
пропажу, а сравнение множеств называет исчезнувшую **по имени**. Сравнение идёт только между
записями **одного режима** — обычный прогон это 212 проверок, а с моделью и нажатием кнопки 288, и
сравнение поперёк режимов объявило бы семьдесят проверок пропавшими. Проверка, которая кричит зря,
хуже отсутствующей: её учатся пропускать.

**Порядок работы, и он не случаен:** сначала коммит кода, потом прогон, потом коммит записи.
Требование «чистое дерево» его и навязывает — запись всегда о коммите, который существует, а не о
состоянии чьей-то рабочей копии.

**Режимов три, а не два, и запись обязана называть свой.** Числа приведены по последним замерам и
двигаются вверх по мере добавления проверок — поэтому пол считается по версии, а не по итогу:

| Режим | Проверок | Кто может запускать |
|---|---|---|
| обычный | 224 | без человека |
| `--with-model` | **272** | без человека, но занимает машину на полчаса |
| `--with-model` + `BHS_PROBE_SHOW_TAB=1` | 288 | **только при ком-то** — выкидывает модальный диалог |

**Канонический — обычный:** он безопасен без присмотра и не открывает моделей. Средний снимается,
когда правка трогает работу с документом, старший — когда трогает ленту.

> **Мера доказательности у записи не одна.** Прогон 2026-09-07 показал это в лоб: коммит, вводивший
> сторожа за ожиданием документа, был записан обычным прогоном — а обычный прогон пропускает
> `CheckDocumentAsync` целиком, то есть **единственный путь, где сторож живёт**. Запись была честной,
> полной и зелёной, и про изменение не говорила ничего. Отсюда правило: запись снимается в режиме,
> исполняющем изменённый код, а не в самом дешёвом из доступных.
>
> **Цена смены режима названа прямо: на этом PR пятый вопрос CI не задаётся.** Сравнение
> «не пропала ли проверка» идёт только между записями одного режима, иначе переход на более дешёвый
> объявил бы семьдесят проверок исчезнувшими. Значит каждое переключение режима стоит одного
> пропущенного сравнения — и если режим начнёт скакать от PR к PR, вопрос перестанет задаваться
> вовсе. Это известная слабость, а не недосмотр; лечится она выбором одного режима как канонического
> и отступлением от него по названной причине, что здесь и сделано.

**Требуется не всегда.** Отслеживаются `source/Revit/**`, `source/Shared/**`, `source/WinSide/**`
и `build/BHS.Revit.Sdk/**`; `source/WinSide` в списке потому, что `BHS.Revit.Launch` решает, дойдёт
ли дело до регистрации вообще, — то есть правит исход проверок не меньше, чем сам add-in; правка документации или самого CI свежего прогона не требует. Иначе
исправление опечатки стоило бы двадцати минут Revit — а правило с такой ценой отключают.

> **Обещание про `source/Features` пришло исполнять, и исполнить его нельзя — посылка оказалась
> неверной.** Здесь стояло: как только издание повезёт `BHS.MEP.Cabling.Revit` внутрь Revit, каталог
> обязан войти в список, иначе правка кода, исполняющегося в процессе Revit, перестанет требовать
> свежей записи. Издание сделано, феатура едет, срок наступил.
>
> Посылка была в том, что запись говорит о фиче хоть что-нибудь. **Она не говорит ничего:** прогон
> водит `BHS.Revit.Probe`, а не издание, и ни одна из 348 проверок не меняется от правки в
> `source/Features` или `source/BHS.FullEdition` — там нет ни одной. Требовать за такую правку
> получаса Revit значило бы платить за запись, которая заведомо не про неё; это ровно то правило с
> непомерной ценой, которое через месяц отключают целиком, вместе с той частью, что работала.
>
> Поэтому список остаётся как есть, а вместо него записывается то, что было спрятано за обещанием:
> **у кода издания и фичи автоматической проверки внутри Revit нет вообще никакой.** Ни прогон, ни
> CI его не касаются; он проверяется человеком, который поставил издание и нажал кнопку. Три дефекта
> `BHS.MEP.Cabling.Revit` найдены именно так — глазами, по скриншотам, в три захода.
>
> Настоящих выходов два, и оба названы, чтобы дыра не считалась закрытой. Либо прогон учится водить
> издание — тогда каталоги в список входят и обещание исполняется по-настоящему. Либо появляется
> проверка, которой Revit UI не нужен, — см. отложенное решение про `Nice3point.TUnit.Revit` в
> разделе «Чего мы сознательно не делаем». Второе дешевле и закрывает ровно тот слой, о котором речь.

**Сырой лог в репозиторий не едет, и это измерено.** Полный прогон — 3404 строки и 288 КБ, из
которых **3003 строки чужие**: Dynamo, MCP-сервер Revit 2027, стеки исключений чужих плагинов,
порты и PID, меняющиеся от запуска к запуску. Как файл под контролем версий это 288 КБ шума на
прогон и диффы, в которых ничего не разобрать. Запись везёт те четыреста строк, которые наши, —
данными, а не текстом.

**Чего это честно не даёт.** Это самоотчёт. CI не может отличить добросовестный прогон от
небрежного и не проверяет, что Revit действительно работает, — он проверяет, что **чьё-то
свидетельство существует и относится к этому коду**. Механически закрыты «записи нет», «запись
устарела», «запись неполна», «в записи отказ» и «из записи пропала проверка». Всё остальное —
на нас.

Побочная выгода, ради которой стоило бы и одной её: таблицы времён в этом файле велись руками и
трижды вводили в заблуждение — 208 с, 696 с и 16 с у одного и того же ожидания. Теперь каждая нота
прогона едет в запись, и разброс виден как разброс, а не как замер.

### Имена задач — договор с правилом ветки

`sdk-version`, `build` и `sweep-evidence` перечислены в защите `master` **по именам**. Переименование задачи значит,
что обязательная проверка не придёт никогда, а слияние заблокировано навсегда сообщением, которое
на имя не указывает ничем. Менять — только вместе с правилом, и **сначала правило**.

### Проверка подъёма версии SDK

`build/scripts/Check-SdkVersion.ps1`, две половины, и обе про отказы, за которые уже заплачено:

- **согласованность** — версия в `BHS.Revit.Sdk.csproj` и в шапке каждого из пяти проектов,
  которые её называют. Расхождение даёт `Could not resolve SDK`, то есть сообщение, указывающее
  на шапку, а не на правку, которая всё сломала. Git не нужен, годится как местная пред-проверка;
- **подъём** — если под `Sdk/`, `tasks/` или в самом csproj что-то менялось относительно базы
  PR, а `<Version>` осталась прежней, сборка падает. Это тот самый отказ **без симптома**: пакет
  везёт сборку задач MSBuild, распакованная копия в кэше не перезаписывается, и сборка продолжает
  исполнять код, которого в дереве уже нет. Две версии SDK сожжены именно так.

`readme.md` и `images/` намеренно **не** отслеживаются: они едут в пакет и ничего не решают, а
подъём версии стоит правки в пяти шапках плюс перезагрузки проектов в IDE — слишком дорого за
опечатку в прозе.

Отдельная строка внутри проверки падает, если **не нашлось ни одного проекта**, называющего SDK.
Проверка, которой нечего проверять, — не пройденная проверка, а вечнозелёная.

### Каждая проверка обязана хоть раз покраснеть

Свод отводит этому отдельное правило, и у нас на него свой счёт: иконки прошли **все** проверки
внутри Revit, содержа четверть логотипа в двукратном увеличении. Проверка мерила габарит и была
права; проверенным это только выглядело.

Поэтому обе половины `Check-SdkVersion` и сама проба были **сломаны намеренно** и показаны
красными до того, как им поверили. Попутно измерено то, что иначе осталось бы незамеченным:

> **Код возврата у `dotnet run | tail` — это код возврата `tail`.** Первый заход мерил именно его
> и показывал ноль на любом исходе. В `build.yml` шага с конвейером нет ни одного, и это не
> случайность оформления.

### Защита ветки, и чем за неё заплачено

`master` закрыт **ruleset**'ом: только через pull request, обязательны **три** проверки по именам
(`build`, `sdk-version`, `sweep-evidence`), запрещены force-push и удаление ветки. Одобрений требуется ноль — ревью
здесь делает не второй человек, которого нет, а явно вызванное автоматическое; свод считает это
законной заменой, но **не** отсутствие ревью вовсе.

Проверено отказом, а не созданием: пустой коммит прямо в `master` отклонён с
`Changes must be made through a pull request` и `3 of 3 required status checks are expected`.
Правило, которое не пробовали нарушить, — это правило, о котором неизвестно, включено ли оно.

> **Число в этой цитате менялось, и это не косметика.** Сначала было `2 of 2`; когда
> `sweep-evidence` стала обязательной, я обновил список проверок **в другом разделе** и не тронул
> этот — то есть в файле два места говорили разное, в двух экранах друг от друга, и авторитетным
> выглядело устаревшее. Ровно то правило свода, которое велит после починки первым делом искать
> второй такой же вход.

> **Репозиторий сделан публичным, и это цена защиты, а не смена позиции по открытости.** На
> приватном репозитории при плане Free защита ветки недоступна ни в классическом виде, ни как
> ruleset — обе формы отвечают `403: Upgrade to GitHub Pro or make this repository public`.
> Выбор был между четырьмя долларами в месяц, открытым кодом и правилом, держащимся на памяти.
>
> Перед публикацией проверено: форк `GrpcDotNetNamedPipes` везёт LICENSE и заголовки Apache 2.0,
> путей вида `C:\Users\...` в отслеживаемых файлах нет, секретов не найдено. **Кроме одного:**
> раздел про подписывание запрещал класть отпечаток сертификата в git и печатал его двумя абзацами
> ниже. Убран; в истории остаётся — отпечаток это SHA-1 публичного сертификата и без закрытого
> ключа не подписывает ничего, а переписывать историю ради публичного идентификатора дороже, чем
> он стоит.
>
> Что публикация действительно открывает: раскладку этой машины, состав установленных чужих
> плагинов и все измерения из этого файла. Ничего из этого не секрет, но и не было предназначено
> для чужих глаз, поэтому названо здесь прямо.

### Что теперь не может отказать молча

Правило свода — **отказ обязан выглядеть отказом**, и главный вопрос к любому месту, где что-то
может не получиться: виден ли будет отказ или его покажут пустым списком, нулём и прочерком. Четыре
места ответили «покажут», и все четыре исправлены.

- **Предупреждения — ошибки.** `TreatWarningsAsErrors=true` на обеих сторонах щита. Свод предлагает
  здесь храповик, но храповик нужен при долге, а долга нет: всё решение собирается с нулём
  предупреждений на четырёх Revit-TFM. Планка, поставленная на нуле сегодня, не стоит ничего;
  поставленная через год — стоит и разбора, и машинерии. Окупилась в тот же час: поймала
  `SYSLIB0057` в только что написанном коде.
- **Развёртывание чистит свою папку.** Раньше копировало и не удаляло, и в папках add-in лежали
  `BHS.Configuration.dll` и `GrpcDotNetNamedPipes.dll` от переименований, `Microsoft.Extensions.*`
  от дня, когда ссылку убрали, — Revit грузил каталог, которого ни одна сборка не производила
  неделями. Чистится **только наш** подкаталог `VendorId\PackageName`: каталог `Addins` общий для
  всех вендоров машины. Показательно, что прогон пробы чистил папку сам — то есть нужда была
  известна, а закрыл её только тот, кого она укусила.
- **Деплой называет состояние подписи.** Пустая `RevitSignWith` значит «продакшн», и задача подписи
  молча не выполняется — верно для выпуска и неверно для развёртывания: неподписанный add-in даёт
  модальное окно **до** `OnStartup` любого add-in, а снаружи это неотличимо от медленного Revit.
  Один раз уже стоило дня, когда отпечаток задали на одно окно терминала.
- **Иконка-заглушка объясняет, почему её нет.** `PlaceholderIcon` отвечал `null` на любое
  исключение, и кнопка выходила пустой — неотличимо от кнопки, которой просто не нарисовали иконку,
  то есть ровно от состояния, ради видимости которого класс и существует. Причина теперь
  сохраняется, а лента говорит её один раз на построение, не на кнопку.

### Проверка, переставшая выполняться, теперь видна

Отдельный род отказа, и самый неприятный: **условие, которое не вычисляют, ничего не печатает,
ничего не роняет и выглядит как пройденное**. Так RefCheck месяцами не импортировался, пока этот
файл описывал его как валящий сборку; так иконки прошли все проверки, содержа четверть логотипа.

Обе пробы теперь считают выполненные проверки и **отказываются считать прогон успешным, если их
стало меньше пола**: 60 у транспортной пробы (измерено 65) и 45 на версию у прогона в Revit
(измерено 53 в самом бедном режиме). Это пол, а не точная цифра — добавлять проверки надо без
правки этого числа, а вот потерять их незаметно теперь нельзя.

> Проверено красным на обеих: подняв пол выше измеренного, получаешь
> `only 65 checks ran, fewer than the 100 this probe is known to have`.

### Сторож по молчанию вместо бюджета

Ожидание документа больше не число. Раньше стояло **900 секунд**, и каждое повышение этого числа
покупалось отказом, который отказом не был: две минуты не хватило Revit 2026, открывавшему модель за
3 мин 51 с; пяти минут не хватило 2024, чей лог датирует документ через 11 мин 36 с после
регистрации. Урок каждый раз был один — **спроси, началась ли работа, а не сколько она идёт**, — и
поток фаз отвечает на это непрерывно.

Порог — **60 секунд тишины** против измеренных десяти. Потолок в пятнадцать минут остался
**последним средством**, чтобы прогон без человека всё-таки заканчивался.

**Четыре исхода, а не два.** Ожидание, знающее только «дождались» и «истекло», обязано считать
модальный диалог зависанием — именно так этот проект дважды поставил неверный диагноз.

| Исход | Что значит | Кто отвечает |
|---|---|---|
| `Arrived` | дождались | — |
| `Blocked` | Revit ждёт ответа на диалог, и его идентификатор назван | человек |
| `WentQuiet` | Revit молчит дольше положенного, названа фаза | разбираться |
| `Unreachable` | Revit перестал отвечать вовсе | процесс ушёл или заперт |
| `Ceiling` | пятнадцать минут прошли | машина медленнее всего, что мы мерили |

> **Тишина в `Blocked` не считается вовсе, и это исправление, купленное отказом.** Сторож
> **различал** диалог и зависание — и обращался с ними одинаково: сообщал «Revit ждёт, чтобы
> кто-нибудь ответил», и через шестьдесят секунд сдавался. Измерено на Revit 2024: владелец отвечал
> на диалог, а процесс был уже убит. Механизм работал и рассказывал не ту историю — ровно тот род
> отказа, который этот файл ловит в других местах.
>
> Молчание в `Blocked` не свидетельствует ни о чём: Revit не работает, а **спрашивает**, и ответ на
> это — человек, а не больший бюджет. Поэтому в этой фазе часы тишины останавливаются, а потолок
> остаётся: прогон без человека приходит к тому же отказу, только позже и названным верно, а прогон
> с человеком теперь доходит до конца. Ожидание вдобавок говорит вслух, чего именно ждёт, — иначе
> сидящий у экрана видит тишину и не знает, что нужен он.

**Молчание не выводится из пустоты.** Если поток не сказал ни слова — диагностика выключена или
стрим не поднялся, — сторож не считает тишину признаком чего-либо и откатывается на потолок,
сообщая об этом. Проверено на бумаге по всем пяти веткам.

> **И сломавшийся стрим — тот же случай, а не противоположный.** Первая версия спрашивала только
> «слышали ли мы хоть что-нибудь», и этого достаточно, чтобы сторож начал врать: читатель
> записывает свой отказ и выходит, отметка «последний раз слышали» замирает навсегда, и упавший на
> тридцатой секунде канал через минуту даёт «молчит» про Revit, который спокойно открывает модель.
> Дальше — убийство работающего Revit и отчёт «документ не приехал», то есть **ровно тот ложный
> диагноз, ради которого сторож и заводился**, только приехавший через сам инструмент. Признак
> «слушаем» теперь требует и полученных событий, и целого стрима.
>
> **Отсчёт тишины начинается не раньше самого ожидания.** `SinceLastHeard` мерит от последнего
> события вообще, а до ожидания документа успевают отработать проверки восстановления,
> конфигурации, контекста, настроек и лога — каждая со своими дедлайнами. Ожидание, открывшееся уже
> без терпения к работе, за которой оно ещё не наблюдало, срабатывает на первой же итерации.
> Берётся меньшее из двух: «сколько не слышали» и «сколько наблюдаем».
>
> **`Blocked` определяется фазой, а не идентификатором диалога.** `DialogBoxShowing` вправе не
> назвать `DialogId`, и чтение одного лишь идентификатора понижало такие диалоги до «замолчал» —
> хотя отвечает на них в обоих случаях человек.
>
> **Пол проверок считается по версиям, а не одной суммой.** Глобальный счётчик против пола,
> падающего на 45 за каждую брошенную версию, позволял им сократиться: брошенная оставляет свои
> тридцать с лишним проверок в сумме и снимает с планки сорок пять. При двух брошенных из четырёх
> завершившаяся версия могла потерять почти всё после регистрации и остаться зелёной — то есть
> охраняемое исчезновение проходило мимо охраны. Каждая версия отвечает за себя; отдельной строкой
> ловится версия, не доложившая вовсе, — записи у неё нет, и в цикл она не попадает.

**Закрытие оставлено на бюджете, и это осознанно.** Уход Revit **выглядит** как молчание: стрим
обрывается, потому что процесс заканчивается, и сторож принял бы собственный успех за зависание.
Пока нет признака, отличающего «канал закрылся, потому что Revit ушёл» от «канал замолчал, потому
что Revit встал», закрытие ждёт по-старому.

#### Что нашлось, когда модель сломали нарочно

Проверить `Blocked` иначе было нельзя, поэтому тестовая модель 2027 была обрезана вдвое — с
резервной копией и восстановлением. Нашлись три вещи, и ни одна не была видна на зелёных прогонах:

- **Сторож ронял весь прогон.** `done()` обращается к Revit по каналу, и мёртвый Revit отвечает
  исключением, а не значением. Оно выходило неперехваченным — то есть механизм, заведённый на
  случай «Revit перестал себя вести», ломался ровно тогда, когда Revit переставал себя вести.
  Теперь это исход `Unreachable`, и он требует **восьми** отказов подряд: один — это занятый канал,
  и сказать «ушёл» про занятый Revit было бы той же ошибкой с другой стороны.
- **Путь отказа шёл дальше и падал.** При неудавшемся документе прогон продолжал задавать вопросы
  каналу мёртвого Revit и умирал внутри проверки настроек модели — отчёт хуже, чем «документ не
  приехал». Теперь выход сразу, и **поток фаз докладывается первым**: прогон, который пошёл не так,
  был единственным, где его не показывали.
- **Не всякий диалог виден.** «contains an incorrect schema» Revit поднял на своём потоке 3 во время
  загрузки файла, и `DialogBoxShowing` не сработал — сторож сказал «молчит в фазе Starting». А
  «неизвестная ошибка» тем же механизмом поймана: `TaskDialog_Revit_File_Unknown_Error`. Значит
  `Blocked` — **лучший** ответ, когда он доступен, а «молчит» — тот, который доступен всегда. И оба
  заканчиваются за минуту вместо пятнадцати.

> **Пол проверок не применяется к прерванному релизу.** Он ловит проверку, которая незаметно
> перестала выполняться; релиз, который сам сдался, уже отказал громко, и второй отказ поверх него
> ничего не добавляет. Измерено на том же сломанном прогоне: три отказа там, где содержательных два.

### Что нашла первая же проверка

Три находки за три прогона, и все три — про расхождение между этой машиной и чистой. Ни одна не
видна отсюда, потому что здесь всё нужное накоплено месяцами.

- **Чистый клон не собирался вовсе.** `NuGet.config` называет `artifacts/feed` источником пакетов,
  а `.gitignore` его исключал; NuGet отказывает в restore, когда локального источника нет — `NU1301`,
  на самом первом восстановлении. Ломался в том числе тот самый первый шаг из раздела «Команды»,
  который здесь предписан как лекарство. Теперь каталог в git, содержимое — по-прежнему нет.
- **Выходной каталог имел два написания, и оба существовали здесь.** Сборка решения кладёт в
  `bin\Release\<tfm>\`, а `dotnet run` по проекту искал в `bin\x64\Release\<tfm>\`. Разные по
  содержимому копии лежали рядом, и **каждый местный прогон транспортной пробы исполнял ту, что
  оказалась новее** — не обязательно ту, которую только что собрали. Все записанные здесь замеры
  транспорта сняты в этих условиях. Лечится `AppendPlatformToOutputPath=false`: x64 — единственная
  платформа, какая у Revit бывает, и в пути она не различала ничего.
- **RefCheck работал, но доказать это по логу было нельзя.** Он печатает по строке на проект, а
  печатал её с важностью `normal`, которой в логе арендованного раннера (`minimal`) не видно.
  Пройденная проверка, не оставляющая следа, неотличима от переставшей выполняться — а этот
  инструмент **уже** однажды месяцами не выполнялся, пока файл описывал его как валящий сборку.
  Важность поднята до `high`: двадцать строк за прогон (пять Revit-side проектов на четыре версии)
  — цена того, чтобы это было видно.

> Вторая находка — самая дорогая, и она из того же семейства, что иконки: **измерение было верным
> и относилось не к тому объекту**. Там проверка мерила габарит вместо картинки, здесь — запускала
> одну сборку вместо другой. Оба раза зелёное было честным и отвечало не на заданный вопрос.

### Версии сборок: две половины смотрят в разные стороны

Единый источник — `VersionPrefix` в корневом `Directory.Build.props`; `build/` не покрыт, у SDK
своя версия, потому что она контракт с проектами, которые её называют в шапке.

- **`FileVersion` едет** за `VersionPrefix`. Это то, что человек читает с развёрнутого файла,
  чтобы ответить «это та сборка, которую я отлаживаю» — вопрос, на котором репозиторий горел
  дважды (устаревшая копия SDK; молча неподписанная сборка);
- **`AssemblyVersion` заморожена по мажору и минору** — `Directory.Build.targets` берёт
  `major.minor.0.0`. На Revit 2024 все add-in в одном AppDomain, и два наших издания обязаны
  сойтись на **одной** `BHS.Logging.dll` и **одной** `BHS.Revit.Host.dll`: `LogRouter.Default` и
  `HostRegistry` сделаны аддитивными именно между изданиями, а при разных идентичностях каждое
  издание получит свой `Default`, и аддитивность будет значить ровно ничего.

Это та же заморозка, которую этот файл считает опасной у `Wpf.Ui`, и опасность настоящая: любая
сборка с тем же мажором и минором получает ту же идентичность. Безопасно здесь **только** потому,
что все наши простые имена несут префикс `BHS.`, и чужой вендор на них не приземлится. Префикс
окупается второй раз.

> **Здесь дважды стояло неверное.** Было написано «заморожена по мажору» и «в выводе стоит
> `file=0.1.0.0 asm=0.0.0.0`». Измерено на развёрнутых файлах: `asm=0.1.0.0`, то есть заморожены
> **мажор и минор**, а не один мажор. Ошибка происходит из более раннего замера, когда заморозка
> действительно давала нули: базовый SDK выводит `FileVersion` из `AssemblyVersion`, обе вышли
> `0.0.0.0`, `FileVersion` задали явно — а строчка про `asm` осталась от того дня и пережила
> исправление механики.
>
> **Следствие, которое от этой ошибки скрывалось: аддитивность держится только внутри одного
> `major.minor`.** Подъём минорной версии расщепляет идентичность, и дальше см. раздел про
> столкновение наших собственных сборок — на двух осях оно кончается по-разному, и на одной из них
> add-in не запускается вовсе.
>
> **Вопрос был поставлен владельцу и закрыт: остаётся `major.minor`.** В продакшене издание всегда
> одно, переход деинсталлирует прежнее, — значит пары изданий разных выпусков не существует, и
> морозить идентичность ради неё не за чем. Разбор и следствия — в разделе про столкновение
> собственных сборок.
>
> **И заметьте, чего эта заморозка не даёт нигде: изоляции.** На 2024 издание с
> `AssemblyVersion 0.2.0.0`, везущее собственную копию, всё равно загрузило чужую `0.1.0.0` —
> `RevitAssemblyResolver` сопоставляет по **простому имени**, а версию игнорирует. Разные версии
> не дают второму add-in свою копию ни на одной оси; они лишь превращают возможный отказ при
> вызове в гарантированный отказ при загрузке на 2025+.

## Чего мы сознательно не делаем

Свод правил заводит этот список отдельным пунктом, и основание там резкое: пустой трекер — не
порядок, а **отсутствие отбора**. В том проекте из 393 задач осталась открытой одна, медиана жизни
задачи — полтора часа, то есть всё, что приходило в голову, делалось в тот же день, и объём системы
определялся скоростью рук, а не ценностью.

Здесь такой же счёт: **51 коммит, и ни одного отклонённого предложения** — потому что предложения
нигде и не записывались. Отказы у нас были, и хорошие; они просто лежали по местам, каждый рядом со
своим разделом. Собранные вместе, они и есть то, что свод называет тренировкой мышцы «не делать».

**Отказано, и решение стоит держать закрытым:**

| Не делаем | Вместо этого | Где разобрано |
|---|---|---|
| Windows-служба для Win-side | пользовательское фоновое приложение | Revit требует интерактивной сессии, значит единственное преимущество службы не существует |
| WinUI 3 в Revit-side | WPF + `WPF-UI` | Windows App SDK требует .NET 6+, Revit 2024 — это `net48` |
| Generic Host, DI-контейнер | конструкторы вручную | тянут `Microsoft.Extensions.*`, запрещённые в Revit-side |
| `Newtonsoft.Json`, `System.Text.Json` | свой читатель в `BHS.Settings` | конфликт с копией Revit; `RVTREF005` |
| `Serilog`, `NLog`, `log4net`, `Microsoft.Extensions.Logging` | свой `BHS.Logging` | каждая уже загружена в процессе Revit, в несовместимых версиях сразу |
| `CommunityToolkit.Mvvm`, `WPF-UI.Tray`, `WPF-UI.DependencyInjection`, `SharpVectors` | урезанный UI-набор | висячие ссылки, лишние полифиллы, трей, которого в Revit не бывает |
| пиннинг версий `Grpc.*` | проверка в сборке | понижать нечего, а `NU1605` с подавлением скроет настоящее понижение |
| задача MSBuild, читающая метаданные | RefCheck отдельным процессом | `System.Reflection.Metadata` на `net48` привозит пять полифиллов **внутрь сборки** |
| сканирование каталога ради модулей | список в издании | загруженная сборка держит простое имя до конца сессии |
| логи по каналу | путь к файлу в снимке конфигурации | логировать надо раньше, чем канал существует |
| дженерик-имя типа в манифесте и на кнопке | пустой наследник из генератора | Revit 2024 не принимает, измерено |
| расщепление сборок ради `RevitAPIUI` | одна сборка | `RevitAPIUI.dll` лежит в каталоге всех четырёх версий; довод оказался гипотезой о среде, которой у нас нет |
| храповик на замечания линтера | планка сразу на нуле | храповик нужен при долге, а долга нет: ноль предупреждений на всём решении |
| `RegisterFailuresProcessor` | `SetFailuresPreprocessor` на транзакции | `static`, один слот на процесс: забирает обработку отказов у всех вендоров |
| `CreateAddInCommandBinding` | ничего | `Executed` заменяет штатную команду, `Cancel` нет нигде, повторная привязка бросает |
| `ApplicationThemeManager` в Revit-side | `ThemesDictionary` на своём корне | мутирует ресурсы и главное окно самого Revit — измерено по IL |
| `CurrentUICulture` как источник языка | `ControlledApplication.Language` | язык Revit выбирается при установке и с языком Windows не связан |
| реестр регистраций сейчас | опрос самого Revit | опрашиваемы шесть из восьми; у механизма было бы ноль потребителей |
| машинный перевод на языки, которые мы не ведём | нейтральный английский | он **выглядит** переведённым, а сказать «это не переведено» умеет только непереведённое |

**Отложено, а не отклонено** — и разница в том, что у отложенного есть условие возврата:

- **вектор (`DrawingImage`) на кнопке ленты** — вернуться, когда появятся настоящие иконки:
  руководство Autodesk для SVG вариантов по DPI не требует вовсе. **Внутри панели откладывать
  нечего** — там разметка наша, `Stretch=None` не действует, и вектор берётся сразу;
- **поля иконок в манифесте ленты** — вместе с первой фичей, которая нарисует свою;
- **свой MCP-модуль** — сначала выяснить, что умеет сервер, который Revit 2027 везёт сам;
- **snapping пина `WPF-UI`** — когда Revit 2024 выйдет из поддержки;
- **вторая ступень CI на self-hosted раннере** — когда прогон в Revit станет мешать чаще, чем
  стоит его настройка;
- **`ExternalService` / `IExternalServer` и `PerformanceAdviser`** — когда появится первый
  потребитель; разбор и способ добавления уже записаны;
- **строки объявления из ресурсов** (`Text` и `ToolTip` ленты, заголовок панели) — вместе с первой
  панелью: у неё цена ошибки выше, а механизм нужен один на оба.

- **`Nice3point.TUnit.Revit`** — вернуться, когда сядет фаза применения и читатели
  `BHS.MEP.Cabling.Revit` перестанут меняться каждый день. Разобрано по вскрытым пакетам, а не по
  readme: на nuget.org, MIT, версии 2021–2027, раскладка `lib/` — `net48` для 2024 и до
  `net10.0-windows7.0` для 2027, то есть **точно наш диапазон**.

  **Revit он не запускает — он вносит движок базы Revit в свой процесс.** `Injector.
  InjectApplication()` из пакета `Nice3point.Revit.Injector`, которого на nuget.org нет (404,
  приватный фид GitHub Packages) и который вплавлен в сборку ILRepack'ом, плюс `PolyHook2.NET` —
  `PolyHook_2.dll`, `Zydis`, `asmjit`, то есть полный набор для переписывания машинного кода в
  рантайме. Работают `Application.NewProjectDocument`, `Transaction`, `FilteredElementCollector`.

  **Закрывает ровно один слой — тот, у которого сегодня ноль проверок:** `BHS.MEP.Cabling.Revit` и
  Revit-side читатели, настройки модели на Extensible Storage, абстракция единиц. Три дефекта,
  найденные глазами по скриншотам за один день, писались бы тестами на засеянном документе за
  минуты.

  **Не закрывает больше половины сборника:** даёт `Application`, а не `UIApplication`, — значит мимо
  проходят лента, памп, модальное окно, journal, канал, доверие и связывание сборок в AppDomain
  Revit. Прогон не заменяется и не сокращается. И лицензированный Revit на машине по-прежнему
  обязателен, так что разрез CI не меняется.

  **Два вопроса до принятия:** решение владельца о средстве, которое патчит машинный код
  лицензированного приложения, чтобы поднять его движок без оболочки, — это острее уже записанной
  оговорки про автоматизацию Revit; и разовая проверка, что оно вообще поднимается на всех четырёх,
  где вероятнее всего откажет `net48` на 2024. На `net48` пакет тянет `System.Memory` 4.6.3
  (`4.0.5.0`), поэтому `BHS.Transport` под ним проверять нельзя — у него своя проба.

- **`UnitsNet`** — вернуться, если понадобится широта величин, которой у Revit нет, и **только
  Win-side**. Измерено: 5.75.1 весит 3,27 МБ и, что редкость, не тянет **ни одной** зависимости на
  `netstandard2.0` — то есть ноль полифиллов; лицензия MIT-0; на этой машине его не возит ни один
  Revit и ни один плагин, значит мы стали бы первыми — как с `Wpf.Ui`, а это риск, а не
  безопасность.

  **Основанием отказа размер не является.** Внутри Revit форматирование обязано быть ревитовским:
  наше число стоит на экране рядом с ревитовским — в свойствах, в спецификации, — а точность,
  разделитель разрядов, десятичный знак и подавление нулей задал пользователь и хранит
  `Units.GetFormatOptions(spec)`. `UnitsNet` о них не знает и узнать не может; плюс у Revit есть
  футы с дробными дюймами и спецификации, которых у него нет вовсе. Число, не совпадающее с
  ревитовским на одном экране, хуже отсутствия библиотеки.

  Форк тоже не обоснован: `GrpcDotNetNamedPipes` форкнут по **измеренному отказу** внутри Revit
  2024, а здесь отказа нет — форк стоил бы тех же мегабайт и покупал бы одно переименование.

  Вместо этого — своя абстракция на два вопроса, «во что перевести» и «как показать», с
  провайдерами: **Revit** (авторитетный, `UnitUtils` + `UnitFormatUtils` + `Units` документа),
  **простой** (Playground, тесты, Win-side) и, если понадобится, `UnitsNet` третьим — там, где
  метрика «сборки, которые может привезти кто-то ещё» не действует. Ядру расчёта единицы не нужны
  вовсе: оно считает в сырых внутренних футах, а «2,4 м» разбирает UI.

> **Правило ведения простое: сюда пишется то, что предлагалось и не взято, с причиной.** Список без
> причин — это перечень, о котором через месяц спорят заново; список с причинами — тот, который
> закрывает спор.

## Диагностический канал: что Revit делает прямо сейчас

Наш код грузится в `OnStartup` — измерено, регистрация приходит через 13–28 с, вдвое раньше
пригодного главного окна. Значит изнутри видна вся загрузка, а снаружи не видно ничего: раннер
ждал по фиксированным бюджетам, и один и тот же замер давал **696 с и 16,3 с**. Бюджет, настроенный
по удачному прогону, — ложное срабатывание, отложенное на потом.

Канал уже был; не хватало не двери, а потока состояния через неё. Добавлен стриминговый
`WatchDiagnostics` — пятый метод контракта и второй стриминговый.

### Что Revit готов рассказать — проверено по метаданным всех четырёх версий

Расхождений между 2024 и 2027 **ноль**, что для этого проекта редкость.

| Член | Что даёт |
|---|---|
| `ControlledApplication.ProgressChanged` | `Stage`, `Caption`, `Position`, `LowerRange`, `UpperRange` |
| `ProgressStage` | `Started`, `RangeChanged`, `PositionChanged`, `CaptionChanged`, `Unchanged`, `Finished` |
| `UIControlledApplication.DialogBoxShowing` | `DialogId`, `Cancellable`, **`OverrideResult`** |
| `Idling` + `IdlingEventArgs.SetRaiseWithoutDelay` | момент, когда Revit освободился |
| `DocumentOpening/Opened/Closing`, `FailuresProcessing` | границы фаз |

### Разрез повторяет разрез хоста

`ProgressChanged` и документные события объявлены в **`RevitAPI`**, то есть доступны обеим формам
add-in; `DialogBoxShowing` — в `RevitAPIUI`. Поэтому машина фаз живёт в `RevitDiagnostics`
(`BHS.Revit.Host`, ни одного типа из `RevitAPIUI`), а диалоги докладывает UI-форма, вызывая
`Observe`. DB-издание получает фазы, не притворяясь, что у него есть интерфейс.

**Хост не ссылается на транспорт.** Событие несёт `RevitDiagnostic` — обычный тип из
`BHS.Revit.Abstractions`; перевод в protobuf делает тот, кто держит канал. Издание без канала не
везёт `Grpc` и `Google.Protobuf` в AppDomain Revit ради машины фаз.

### Измерено на живом Revit, четыре версии, с открытием модели

Два прогона, а не один — потому что единственная цифра, снятая с одного запуска, в этом файле уже
трижды выглядела измерением и им не была.

| Revit | Событий | Потеряно | Самое долгое молчание | Второй прогон | Молчание | Где |
|---|---|---|---|---|---|---|
| 2024 | 90 | 0 | 8,5 с | 96 | **11,5 с** | `Starting` |
| 2025 | 64 | 0 | 3,6 с | 66 | 3,9 с | `Working` |
| 2026 | 140 | 0 | 9,8 с | 147 | 8,3 с | `Starting` |
| 2027 | 143 | 0 | 9,6 с | 147 | 8,2 с | `Idle` |

**Это и есть число, ради которого всё делалось.** Без диалога Revit молчит около десяти секунд —
верхняя из восьми замеренных величин 11,5 с, — даже когда открывает модель. Прежний бюджет ожидания
документа был **900 секунд**; сторож с порогом в минуту обнаруживает настоящее зависание в
пятнадцать раз быстрее и точнее, оставляя пятикратный запас над худшим измеренным молчанием.

> Заметьте, что «десять секунд» пришлось поправить на первом же повторе: 11,5 с против прежних 9,8.
> Порог в минуту от этого не двигается — он и выбирался с запасом именно на такой случай, — но
> цифра, названная максимумом по четырём замерам, максимумом не была.

Captions приезжают словами самого Revit: «Открытие существующего проекта», «Загрузка ….rvt»,
«Обновление связей», «Фиксация транзакций», «Формирование графики для План этажа: Уровень 1». Они
**локализованы** — строить на их тексте нельзя, это язык интерфейса. Строить можно на `DialogId`,
который стабилен.

> **Молчание молчанию рознь, и это не теория.** Прогон, во время которого владелец отвечал на
> «Остановить выполнение данной операции?», дал самое долгое молчание **119,6 с — во время
> `Blocked`**. Тишина в `Working` значит «Revit работает»; тишина в `Blocked` значит «диалог ждёт
> человека». Сторож обязан различать: второе не зависание, а неотвеченный вопрос. Поэтому
> записывается не только длительность молчания, но и фаза, в которой оно случилось.

> **Диалог теперь виден изнутри.** `Blocked` появился в потоке ровно тогда, когда на экране висело
> модальное окно, — то самое состояние, которое дважды диагностировали неверно, потому что снаружи
> оно неотличимо от медленного Revit.

### Три правила, за которые нельзя выходить

- **Ничто не блокирует API-поток.** Обработчики выполняются внутри собственной отчётности Revit —
  самого горячего колбэка процесса при загрузке модели. Публикация берёт замок, кладёт в кольцевой
  буфер и возвращается; читатель, который не поспевает, теряет события, а не тормозит Revit.
  Потери **считаются и докладываются**: потребитель следит за тишиной, значит обязан отличать
  прореженное от остановившегося.
- **Прореживание у источника.** Позиция передаётся не чаще раза в 250 мс; смена смысла — `Started`,
  `Finished`, `CaptionChanged`, новый caption — не прореживается никогда. Измерено: 64–143 события
  на прогон с моделью при нуле потерь, то есть буфера в 256 хватает с запасом.
- **Диалоги докладываются и никогда не отвечаются.** `OverrideResult` перехватывает **все** диалоги
  процесса, включая чужих вендоров, и ответить «да» на чужое «сохранить изменения?» — это испортить
  чужую модель. Если автоответ когда-нибудь понадобится, он лежит за явным списком `DialogId`,
  который задаёт наблюдатель, и только в прогоне, никогда в продукте.

### Выключено по умолчанию

`Diagnostics:Enabled`, и по умолчанию `false`. Включено только в настройках, которые прогон пишет
пробе. Причина названа прямо: **то, что мы строим для отладки, уезжает к заказчику в той же
сборке**. Вход, открываемый конфигурацией, — это вход, который однажды откроет не тот, кто его
делал. Плюс цена: подписка на `ProgressChanged` — колбэк на API-потоке при каждой загрузке модели
в процессе, и продукт не должен платить её за то, чтобы за ним никто не наблюдал.

> **Ошибка, стоившая двух прогонов и записанная как правило.** Первая версия наблюдателя в раннере
> подписывалась, слушала двадцать секунд и докладывала — и намерила **одно** событие, меньше, чем
> тот же прогон без модели. Со стримом всё было в порядке: документ приезжает минутой позже, когда
> слушателя уже нет. **Фазу нельзя увидеть выборкой** — у неё есть начало и конец, и наблюдатель
> обязан жить столько же, сколько то, за чем он наблюдает.

## Известные проблемы окружения

- **Устаревшая распакованная копия SDK.** Симптомы — `Could not resolve SDK`,
  `UnauthorizedAccessException` при восстановлении, поведение, которого нет в текущих исходниках
  SDK. Причина в разделе «Статус репозитория»: сборку задач держит открытой любой процесс,
  оценивший Revit-проект. Лечится поднятием версии SDK; если версию поднять нельзя — закрыть
  Rider и снести `%USERPROFILE%\.nuget\packages\bhs.revit.sdk\<версия>`. Помогает также
  `MSBUILDDISABLENODEREUSE=1`.
- **После поднятия версии SDK Rider нужно перезагрузить проекты.** Версия стоит в шапке каждого
  Revit-проекта, и модель проекта в IDE строится на той, что была на момент загрузки решения.
  «Reload All Projects» дешевле, чем разбираться, почему IDE и командная строка расходятся.
- **Гонка при параллельной сборке на холодном кэше** — несколько проектов распаковывают SDK
  одновременно и получают `UnauthorizedAccessException`. Наблюдалась однократно,
  систематичность не проверена. Обходится предварительной сборкой `build/BHS.Revit.Sdk`.
- **Отладка MSBuild включена машинно**: `MSBUILDDEBUGENGINE=1` и `MSBUILDDEBUGPATH=C:\Temp\msbuild.logs`.
  Замедляет restore примерно восьмикратно и копит логи сотнями мегабайт. К проектам отношения
  не имеет, но при странном поведении сборки проверяйте это первым.

> **Исторически:** «`dotnet restore` молча падает на любом пакете вне кэша» оказалось
> неверным диагнозом. Обычные проекты восстанавливались нормально; не работал `Restore`
> **в SDK** — его диспетчер читал свойство, которое нигде не присваивалось, и рапортовал успех,
> не сделав ничего. Диспетчера больше нет: восстановлением занимается базовый SDK, и каждый
> проект обходится ровно один раз.

Три наблюдения по составу, снятых при первом заходе:

- **`AddinsIsolation` (только 2027) описывает элементы манифеста, которых наш SDK не умеет.** Кроме
  `UseRevitContext` и `ContextName` там есть `<PublicAssemblies>` и

  публикует сборку, другой её потребляет. Это ровно тот механизм, который понадобится двум нашим

  ту самую аддитивность `LogRouter.Default` и `HostRegistry`, которую замороженная
  `AssemblyVersion` в общем AppDomain обеспечивает, а в разных контекстах уже нет. **Не измерено.**
- **Изоляция между 2026 и 2027 из диковинки стала позицией по умолчанию.** Все **208** манифестов
  примеров 2027 несут `<UseRevitContext>False</UseRevitContext>`; в 2026 таких **1 из 204**
  (`CoordinationModel`), в 2025 и 2024 — ни одного. `ContextName` встречается дважды и только там,

  изоляцию. Нашей политики это не отменяет (на 2024 и 2025 изоляции нет вовсе), но направление
  Autodesk называет прямо.
- **`UIThemeManager` и `ThemeChanged` не встречаются ни в одном примере.** Выбор иконки по теме
  опереть не на что, кроме собственного замера.

## Архитектурные соглашения

### Разделение Revit-side / Win-side

Ключевое разделение, тянущееся через `BHS` и `BimHouseApp`: сборки, загружаемые *в процесс
Revit* (жёстко привязаны к версии API), и внешние процессы/утилиты, которые версии Revit не
знают. Не смешивайте их в одном проекте — у них разные TFM и разные жизненные циклы.
Общение между ними в `BHS` организовано через gRPC.

### Слоистость framework'а

Раскладка `source/` восходит к `BimHouseApp`, но **все имена сборок несут префикс `BHS.`** —
в отличие от оригинала, где Revit-слой назывался `Revit.Abstractions` и подобным.

> **Почему префикс обязателен.** Revit 2024 грузит все add-in в **один AppDomain**, изоляции
> там нет. Сборка с родовым именем вроде `Revit.Abstractions.dll` — это столкновение, ждущее
> чужого вендора с тем же именем; победит загрузившийся первым, и отлаживать это будет
> невозможно. Префикс стоит ноль и снимает целый класс отказов. То же соображение стоит за
> метрикой полифиллов BCL в разделе про конфликт сборок.

| Каталог | Ось TFM | Роль |
|---|---|---|
| `Shared/BHS.Shared` | `net48;net8.0;net10.0` | код, не знающий ни о Revit, ни о стороне процесса |
| `Shared/BHS.Settings` | `net48;net8.0;net10.0` | слоистые настройки с диска, свой читатель JSON, наблюдение за файлами. **Ни одной ссылки на пакеты** — это половина, которая едет внутрь Revit |
| `Shared/BHS.Settings.Configuration` | то же | те же файлы как `IConfigurationSource`. Отдельно по той же причине, что и у транспорта: `Microsoft.Extensions.*` в Revit-side не пускают |
| `Shared/BHS.Logging` | `net48;net8.0;net10.0` | `ILog`, маршрутизатор, приёмники: файл, `Trace`, консоль. **Ни одной ссылки на пакеты.** Единственная зависимость — `BHS.Settings`; обратной быть не должно, `BHS.Settings` не логирует |
| `Shared/BHS.Grpc.NamedPipes` | `net48;net8.0-windows;net10.0-windows` | форк `GrpcDotNetNamedPipes` 3.1.0, пересобранный против `System.Memory` 4.0.1.1. Исходники апстрима дословно; вся разница в файле проекта |
| `Shared/BHS.Transport` | `net48;net8.0-windows;net10.0-windows` | канал между сторонами: `.proto`, имена, три слоя доверия, реестр экземпляров, издатель конфигурации |
| `Shared/BHS.Transport.Configuration` | то же | `IConfigurationSource` поверх канала. Отдельно, чтобы издатель не тащил `Microsoft.Extensions.*` в AppDomain Revit |
| `Revit/BHS.Revit.Abstractions` | Revit | контракты, за которыми прячутся различия версий API, плюс контракты хоста: `IRevitContext`, `IRevitApiPump`, `IFeatureServices`, `HostRegistry`, `CommandEntryPoint<T>` |
| `Revit/BHS.Revit.Common` | Revit | базовые реализации и утилиты поверх Revit API |
| `Revit/BHS.Revit.Host` | Revit | `RevitAddInApplication` и всё, что между вызовом `OnStartup` и работающей фичей: настройки, лог, памп, реестр, слой настроек модели |
| `Revit/BHS.Revit.Probe` | Revit | проба: служит канал изнутри Revit и докладывает, что в его AppDomain |
| `Revit/BHS.Revit.Probe.Feature` | Revit | подставная фича: команда, которую проба запускает нажатием кнопки. Отдельная сборка **и есть** проверка ленивости — по ней видно, загружена она или нет |
| `WinSide/BHS.Revit.Launch` | `net10.0-windows` | поднять Revit и дождаться, когда он скажет, что готов. Вынуто из прогона пробы, который остался его проверкой |
| `WinSide/BHS.WinSide` | `net10.0-windows` | фоновое приложение: держит канал и реестр, поднимает и гасит Revit по запросу. Пользовательский процесс, не служба |
| `Revit/BHS.Revit.Probe.Runner` | `net10.0-windows` | прогон пробы. Не грузится в Revit и не на оси Revit; лежит рядом, потому что две половины — один инструмент |
| `Frontend/WPF/BHS.UI.*` | чистая .NET | `Abstractions`, `Framework`, `UI`, `Translations` |
| `Features/<Домен>/BHS.<Домен>*` | Revit | плагины как feature-модули |
| `Features/MEP.Cabling/BHS.MEP.Cabling.Routing` | `net48;net8.0;net10.0` | ядро маршрутизации: поиск, сеть, результат. **Ни одного типа Autodesk** — это и есть гарантия потока, а не вкус |
| `Features/MEP.Cabling/BHS.MEP.Cabling.Revit` | Revit | единственная сторона, у которой есть `Document`: читает носители и цепи, наводит трансформацию связи, отдаёт снимок. Ничего не ищет |
| `Features/MEP.Cabling/BHS.MEP.Cabling.Ui` | `net48;net8.0-windows;net10.0-windows` | экран прогона. На чистой оси по той же причине, что и ядро: вью-модель ведут через границу потоков, и здесь тип `Document` нельзя тронуть, потому что его нет. `-windows` — из-за WPF |
| `Features/MEP.Cabling/BHS.MEP.Cabling.Feature` | Revit | то, что издание грузит по нажатию. Отдельная сборка затем, чтобы до нажатия она в AppDomain не попадала |
| `BHS.FullEdition` (корень `source/`) | Revit | первое издание: хост-класс, точка входа, класс доступности, объявление ленты |
| `BHS.<Издание>` (корень `source/`) | Revit | host-проект, точка входа `IExternalApplication` |

Framework — это `BHS.Shared`, `BHS.Revit.*` и `BHS.UI.*`; плагины — это `Features/*`.
Зависимость идёт только в одну сторону: features → framework, никогда наоборот.

**Слои заводятся по мере появления реального потребителя, а не заранее.** В `BimHouseApp`
проект `Revit.Base` так и остался пустым, а `Revit.Common` содержал один файл. Пустой каталог
в дереве — не задел, а обещание, которое некому выполнить.

### Мультиверсионность Revit

Два механизма, применять в этом порядке предпочтения:

1. **Константы препроцессора** от SDK (`#if REVIT2026_OR_GREATER`) — для точечных различий API.
2. **Version-suffixed файлы** (`Foo.2026.cs`) — приём из `BimHouseApp/Directory.Build.targets`,
   где по `RevitVersion` из компиляции исключаются все версии, кроме целевой. Применять,
   когда различия слишком велики для `#if`.

### Локализация

`SatelliteResourceLanguages` в экосистеме = `en-US;en-GB;ru-RU`, `NeutralLanguage=en`.
Строки UI — в ресурсах (`UI.Translations`), не в коде.

## Идентификация вендора

Значения, используемые в соседних решениях для `.addin` и путей установки:
`VendorId` = `BimHouseSoftware`, каталог вендора = `BHS`,
описание = `BimHouse Software by alex@pototskiy.net`. Каждый add-in требует **собственного
уникального `AddInId`** (GUID) — не копируйте GUID из соседних проектов.
